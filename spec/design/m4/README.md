# yuzhu M4 基本設計（インデックスとクエリ）

M4 のゴールは**インデックスと問い合わせ**です。PostgreSQL の nbtree に準拠した B+Tree、PRIMARY KEY / UNIQUE / SERIAL（シーケンス）、JOIN・集約・サブクエリ・集合演算・WITH、ルールベース最適化と EXPLAIN を作り、そのために M1〜M3 の内部構造（列参照の表現、論理プランと物理プランの分離）を M4 の冒頭で作り直します。あわせて numeric・`char(n)`・`timestamp` 系・COPY FROM STDIN を前倒しで入れ、psql の `\dt` `\dn` `\di` `\ds` `\l` と pgbench（`-i` と tpcb-like）が動くところまでを範囲とします。PostgreSQL 17 が正解です。

- 要件定義: <https://claude.ai/code/artifact/9381e901-9f2a-49a4-9bb2-479295dde6e2>
- 前提: `spec/design/m1.md`・`m2.md`・`m3.md`（M2 と M3 は実装が進行中。M4 の設計は M3 の設計どおりに完成した状態を前提にする）、`QUESTIONS.md`（Q-010〜Q-014）、`PROGRESS.md`、調査 `spec/research/m4-btree.md`・`m4-query.md`・`research-pg-types.md`・`pg-compat-tools.md`
- 章の書式は M3 の設計書に倣う（範囲、決定、ディスク形式、契約、処理の流れ、モジュール仕様、テスト、実装の分担と工数、未検証の点、確認事項、00 への変更提案）。

## 主な設計判断（要約）

- **処理系列**: AST → Bound（`Var`）→ 論理プラン（`ColId`）→ ルール → 物理プラン（`PhysCol`）→ Executor。式の木は `Expr<C, Q>` の単一定義から 3 つの型別名を作り、層ごとの許可は `validate` で守る（D-1、D-2）。
- **B+Tree**: nbtree 準拠（high key、right-link、ヒープ TID のタイブレーク）。切り詰め・重複排除・項目の削除は作らず、構造変更は全画像の 1 レコード `BTREE_PAGES`（ブロック数 `3h + 1`）で、未完了分割を作らない（D-7）。
- **PK / UNIQUE / シーケンス**: 一意インデックス + `pg_constraint`、一意性検査は `WaitFor` を返せる形（D-8）。シーケンスは 1 ページのリレーションをその場で上書きし、`SEQ_LOG` で 32 個先まで記録、払い出した値を二度払い出さない（D-9）。SERIAL / IDENTITY は解析時の書き換え（D-10）。
- **問い合わせ**: HashJoin / NestedLoopJoin / NestedLoopParam、HashAggregate / Aggregate / GroupAggregate、PostgreSQL と同じ範囲のサブクエリの結合化と CTE のインライン規則（D-13〜D-16）。統計なしの規則ベース最適化と、インデックスのヒューリスティクス選択（D-17、D-18）。スピルなし、`yuzhu.query_mem_limit` で `53200`（D-19）。
- **EXPLAIN**: テキスト形式のみ、`COSTS OFF` の書式は PG と同じで、プランの選び方は一致しない。InitPlan は問い合わせ階層の根の子、SubPlan は式を表示したノードの子（D-20）。deparse を EXPLAIN と `pg_get_expr` が共有（D-21）。
- **周辺**: numeric は `yuzhu-numeric` の統合、`char(n)` は別の `Datum` 変種、COPY FROM STDIN（テキスト）、手書きの正規表現エンジン、受け付けるだけの GUC 162 件と `55P02` の 188 件（D-3〜D-6、D-22）。
- **完了条件**: psql の `\dt` `\dn` `\di` `\ds` `\l` と `\d シーケンス`、pgbench の `-i` と tpcb-like の完走、差分ランダムテストの固定シード 0 件と長時間の一度の完走、クラッシュ試験、共有 slt、isolation（01 §3。`\d tbl` は M4 では動かない任意項目）。

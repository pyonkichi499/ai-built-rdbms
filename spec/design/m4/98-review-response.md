# yuzhu M4 設計 98: レビュー対応

M4 の設計書（00〜11 章）に対するレビュー指摘（37 件）を**指摘ごとに実在確認**し、実在したものを該当の章に反映した記録です。確認は、章の本文の突き合わせ（grep と該当行の読み取り）と、**PostgreSQL 17.11 の実機**（サンドボックスの `127.0.0.1:55432`。`psql -E` で SQL を採取し、`SET` / 正規表現 / COPY / 集約の位置を実際に流した）で行った。却下・一部反映の理由は「結論」の列に書いた。反映した場所には本文中に `R-nn`（または「レビュー対応 R-nn」）の印を付けた。

- 指摘は同じ問題を別の観点から繰り返したものが多いので、**R-nn は問題単位**にまとめた（元の指摘の数は右端）。R-01 は 3 件（`01-scope-decisions.md` の不在を 00・11・ディレクトリの 3 か所から指摘）、R-03 は 3 件、R-04 と R-09 は 2 件。合計 37 件が R-01〜R-31 の 31 件になる。
- 結論の凡例: **反映** = 実在し、章を直した。**一部反映** = 実在したが指摘の修正案どおりではなく、実機または他章の決定に合わせた別の形にした。**却下** = 実在しなかった（この回は 0 件）。
- **確認の方法**の凡例: 【実機】= 本セッションで PostgreSQL 17.11 に流して確かめた。【指摘どおり】= 指摘が書いた実機の結果を採用した（本セッションでは再現していない）。【本文】= 章の本文の突き合わせ。

## 2. 一部反映・判断を加えた点（まとめ）

- **R-02（00 の統合）**: 指摘どおりに 00 を全面的に書き直すと、11 §7.4 の採否が「△」「×」の提案（例: `ExplainNode.plan_id` の不採用、`uses_params()` の扱い、`IndexStore::insert` の `detail`）と二重管理になる。主要な決定を 00 に直接反映し、残りは §1.4 と 11 を正とする形にした。これで「並列実装者が 00 だけを読んで誤る」リスクは、指摘の具体例（`yuzhu-fuzz-sql`、`ExplainNode`、`3h + 1`、D-11・D-12、K の日数）について解消した。
- **R-17（整数 GUC の丸め）**: 指摘の規則（0 から遠い方へ丸める）は実機と合わない。`2.5` が `2` になるので `rint`（偶数丸め）。
- **R-19（`\d tbl` の担当）**: 担当の割り当てを求める指摘だが、`\d tbl` は完了条件ではないので任意の WP にした。必須にするかはユーザー確認（99 の M4-Q145）。
- **R-10（バッファ数）**: 2 つの式のどちらを正にするかを決める指摘。`3h + 4`（余裕込み）を正とし、§9 と U31 を合わせた。余裕の `+3` の根拠は 06 に明記された実装上のピン（ヒープページ・メタ）で、数の確定は実装時の未検証（06 §9）。

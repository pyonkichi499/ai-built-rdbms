# yuzhu M2 基本設計（Rust 実装）

M2 のゴールは、データを**ディスクに永続化**することです。正常に停止して再起動すれば、コミットしたデータとテーブル定義がすべて残っている状態にします。具体的には、8KB ページ、バッファプール、ヒープ、リレーションごとのファイル、テーブルとして持つシステムカタログ、UPDATE / DELETE、initdb を実装します。この文書は M1 の `m1.md` と同じく、並列に動く実装者全員が従う**契約**です。

- 要件定義: <https://claude.ai/code/artifact/9381e901-9f2a-49a4-9bb2-479295dde6e2>
- 前提: `spec/design/m1.md`（M1 の契約）、`spec/design/m1-changes.md`（M1 実装中の変更）
- 調査資料（根拠）: `spec/research/`
  - `m2-page-heap.md` ページ・タプルの形式、TOAST、FSM、チェックサム
  - `m2-buffer-io.md` I/O 抽象化、ストレージマネージャ、バッファプール
  - `m2-catalog.md` システムカタログ、initdb、データディレクトリ、キャッシュ
  - `m2-dml-exec.md` UPDATE / DELETE、ROLLBACK の方式、TableStore と executor の変更
  - `m3-mvcc.md`、`m3-wal.md`、`m3-recovery.md` M3 の調査。M2 で決めたディスク形式を M3 で変えずに済むよう、ここでの推奨を先取りしている
- 迷ったら **PostgreSQL 17 と同じ挙動**を選ぶ。判断が分かれる点は推奨案で進め、`QUESTIONS.md` に記録する。この文書の仮決めは第 9 節「確認事項」にまとめた。
- PostgreSQL のソースは REL_17_STABLE を参照する。URL は `https://github.com/postgres/postgres/blob/REL_17_STABLE/<path>` の形で書く（以下 `PG:<path>` と略す）。「（未検証）」と付けた記述は、ソースや実機で確かめていない。

## 0. 調査間の食い違いと、この設計での決定

4 本の調査（と M3 の調査）には、推奨が食い違う点があった。この設計では次のように決めた。

| # | 論点 | 選択肢（出典） | 決定 | 理由 |
|---|---|---|---|---|
| D1 | ROLLBACK と文の原子性 | (a) M1 の undo ログを TID 単位に広げる（page-heap §2.9）<br>(b) xmin/xmax と永続化したコミットログ（clog）で可視性を判定する（dml-exec 案 B） | **(b)** | M3 で捨てるコードがほとんど出ない。ダーティリードが M2 で解消する。大きな UPDATE でも前イメージをメモリに溜めずに済む。steal（未コミットのページの追い出し）を最初から安全に許せる |
| D2 | XID の幅とタプルヘッダ | (a) PostgreSQL と同じ 23 バイト、32 ビット XID、combo CID（page-heap、dml-exec）<br>(b) 64 ビット XID、cmin と cmax を別々に持つ 35 バイト（m3-mvcc §5.2、§10） | **(b)** | タプルの形式は M2 で固定し、以後は変えない（依頼の条件）。32 ビット XID のままだと、M5 で周回（wraparound）対策の緊急 VACUUM、xidStopLimit をすべて作る必要がある。そこにバグがあるとデータが消える。64 ビットなら周回は事実上起きない。combo CID の表も要らなくなる。代わりに 1 タプルあたり 12 バイト大きくなり、PostgreSQL とはバイナリの形式が違う（もともと互換は狙っていない）。**ただし「凍結が完全に不要」ではない**: clog を切り詰める（M5）には、古い XID を参照するタプルが残っていないことを保証する必要があり、M5 の VACUUM は xmin を `FROZEN` に書き換えるか `HEAP_XMIN_COMMITTED` などのヒントを確定させる「凍結に相当する処理」を持つ。不要になるのは周回の期限に追われる緊急の処理だけ（§6.7.2、M2-Q2） |
| D3 | 並行性の制御 | (a) M1 と同じく、文の実行全体を 1 本の Mutex で直列化する<br>(b) DDL だけデータベース単位の書き込みロックにする（catalog §7.2）<br>(c) 単一ライターロックをトランザクションの終了まで持つ（dml-exec §3、m3-mvcc §4.2） | **(c)** | M3 の「単一ライター + 複数リーダー」をそのまま前倒しできる。並行更新の再評価（EvalPlanQual）もデッドロックも起きない。読み取りは書き込みと並行して動く |
| D4 | 制御ファイル | (a) 一時ファイル + rename（catalog §4.2、buffer-io §6.2）<br>(b) `global/pg_control`（dml-exec §7.2）<br>(c) `global/yuzhu_control` の 2 スロット上書き方式（m3-recovery §3.2） | **(c)** | M3 で形式を変えずに済む。ディレクトリ操作を含まないので障害モデルが単純になる。任意のバイト境界での torn write にも耐える |
| D5 | ページヘッダの版数 | `PG_PAGE_LAYOUT_VERSION` と同じ 4（buffer-io §5.9）／yuzhu 独自の 1（page-heap §2.2） | **yuzhu 独自の 1** | D2 によりタプルの形式が PostgreSQL と異なる。同じ版数を名乗ると誤解を招く |
| D6 | ヒントビット | M2 では設定しない（dml-exec §2.4）／M3 で設定する（m3-mvcc §6） | **M2 は `XMAX_INVALID` 以外を読みも書きもしない** | 可視性は毎回 clog を引いて判定する。clog はメモリにキャッシュする。ヒントビットを dirty 扱いにするかどうかと、チェックサムとの関係は M3 で決める（M2-Q5）。**書き方は M2 で決めておく**: フレームは `RwLock<Box<Page>>` なので、PostgreSQL のように共有ラッチのままヒントを書くことは `forbid(unsafe_code)` では書けない。M3 以降のヒントは `PinnedBuffer::try_write()` で排他ラッチが取れたときだけ、`PageWriteGuard::page_mut_hint()` で立てる（§4.3、§6.3） |
| D7 | チェックサム | M2 から常に有効（page-heap、buffer-io）／M3 ではデータページのチェックサムを持たない（m3-wal §2.8） | **M2 から常に有効** | WAL がない M2 でも、torn write やビット反転を黙って読まずに検出できる。M3 でヒントビットを入れるときは「ヒントだけの変更ではページを dirty にしない」か、FPI を出すかを選ぶ（M2-Q5） |
| D8 | psql の `\dt` | LEFT JOIN と正規表現を M2 に前倒しする（catalog §2.4） | **前倒ししない。M2 で動かすのは `\l` まで** | JOIN を入れるとアナライザのスコープを複数テーブルに広げる必要があり、M4 の作業と重なる。`\dt` は M4 で JOIN と一緒に動かす（M2-Q8） |
| D9 | relfilenode の型 | `rel_number: Oid`（dml-exec）／`RelFileNumber` の新型（buffer-io） | **`RelFileNumber(u32)`** | OID と取り違えるバグを型で防ぐ |
| D10 | スキャンカーソル | ピンを持ち続けるカーソル／ページ単位でデコードして `VecDeque` に溜め、ピンもラッチも持ち越さない（dml-exec §6.1） | **後者** | executor にライフタイムを持ち込まない。自分自身とのラッチのデッドロックや、ピンの漏れが原理的に起きない |
| D11 | `server_version` | 16.0（M1、Q-004）／17.0（catalog §2.3） | **17.0** | カタログを PG17 の列構成にする。psql の `\d` には 17 専用の分岐がないことが確認されている |
| D12 | 新しいページの判定 | `pd_upper == 0` だけ／ページ全体が 0 | **`pd_upper == 0` なら全 8192 バイトが 0 であることを検査し、違えば `XX001`。全 0 のページにはチェックサムを入れずに書く** | PostgreSQL の `PageIsVerifiedExtended` と `PageSetChecksumCopy` と同じ（PG:src/backend/storage/page/bufpage.c）。後から変えるとディスク上の既存ページが不正になる（§3.3、§6.4） |
| D13 | リレーションのファイルの削除 | 即座に全セグメントを消す／最初のセグメントを 0 バイトに切り詰めて残し、次のチェックポイントで消す | **後者** | M3 のクラッシュリカバリで、同じ relfilenode を再利用した新しいリレーションに古い WAL を適用しないため（PostgreSQL の `mdunlink`。PG:src/backend/storage/smgr/md.c）。M2 から同じ規則にしておく（§6.2） |
| D14 | 失敗しうるページの変更 | 規約なし／クリティカルセクション | **`page_mut()` の後に失敗しうる処理を書かない。`CriticalSection` の中のエラーと panic はクラスタの Panic に昇格する** | 書きかけのページが dirty のまま書き出されるのを防ぐ。M3 の WAL とページの一致の前提（PostgreSQL の `START_CRIT_SECTION`。§6.3） |
| D15 | マイルストーン間のデータディレクトリ互換 | M2 のデータを M3 以降でも読む／initdb のやり直しを求める | **M5 まではマイルストーンをまたぐ互換を保証しない**。`format_version` か `catalog_version` を上げたら initdb のやり直し | ページ・タプル・clog の形式は M2 で固定するが、カタログの中身（M3 の WAL 関連、M5 の 64 ビットの frozenxid など）は変わりうる。互換の変換を作る費用に見合わない（M2-Q20） |

## 1. M2 の範囲

### 1.1 機能

| 分類 | M2 で対応するもの |
|---|---|
| 永続化 | 8KB ページ、リレーションごとのファイル（1GB セグメント）、バッファプール（clock-sweep）、ヒープ、ページチェックサム、正常停止時のチェックポイント、`CHECKPOINT` 文、定期チェックポイント |
| トランザクション | 永続化した XID カウンタ、コミットログ（`pg_xact/`）、スナップショット（Read Committed、文ごとに取り直す）、xmin/xmax/cmin/cmax による可視性判定、単一ライターロック |
| カタログ | 共有カタログ 3 つと、データベースごとのカタログ 10 個をヒープテーブルとして持つ（§6.8）。OID・名前・列の並びは PG17 と同じ。SQL から SELECT できる |
| データベース | 1 つのクラスタに template1 / template0 / postgres を置く。接続時に `pg_database` で接続先を決める。CREATE DATABASE は M5 だが、そのためのディレクトリ構成とコピー処理は M2 で作る |
| ツール | `yuzhu-initdb`（データディレクトリの作成）、`yuzhu-server -D <dir>` |
| psql | `\l` が動く（§6.10）。`\dt` と `\d` は M4 |

- **「`\l` が動く」の定義**: psql 17 の `listAllDbs`（PG:src/bin/psql/describe.c）が送るクエリを yuzhu に流すと、「Access privileges」列以外の全列が、C ロケールで initdb した PostgreSQL 17 と一致する。さらに実物の psql 17 で `psql -X -c '\l'` が終了コード 0 で 3 行を出す（§7.1、§7.4）。psql 18 以降で `listAllDbs` が変わったかは確かめていない（未検証）。M2 の対象は psql 17 とする。

### 1.2 SQL（M1 からの追加）

| 分類 | 追加するもの |
|---|---|
| DML | `UPDATE [ONLY] t [[AS] alias] SET col = expr\|DEFAULT [, ...] [WHERE cond]`、`DELETE FROM [ONLY] t [[AS] alias] [WHERE cond]` |
| ユーティリティ | `CHECKPOINT` |
| 式 | `E'...'`（M1 では任意だったもの。`\l` が使う）、スキーマで修飾した関数名（`pg_catalog.f(...)`）とテーブル名（`pg_catalog.pg_class`） |
| システム列 | `ctid`、`xmin`、`cmin`、`xmax`、`cmax`、`tableoid` を SELECT で参照できる（値は PostgreSQL と一致しないので、slt では使わない） |
| 関数 | `pg_get_userbyid`、`pg_encoding_to_char`、`array_length`、`array_to_string`、`pg_table_is_visible`、`format_type`、`pg_get_expr`、`current_schema()` のカタログ参照化（§6.10） |

**M2 では対応しないもの**（実行すると `0A000`）: `UPDATE ... FROM`、`DELETE ... USING`、`WHERE CURRENT OF`、`RETURNING`、`SET (a, b) = (...)`、`TRUNCATE`、`ALTER TABLE`、`CREATE SCHEMA`、`CREATE DATABASE`、`VACUUM`、`SAVEPOINT`。JOIN、集約、サブクエリは M4 のまま。

- OID は pg_type.dat の記憶に基づく（未検証）。実装前に .dat で確かめる。
- M2 では、`pg_type` の `typreceive`・`typsend`・`typmodin`・`typmodout`・`typanalyze`・`typsubscript` をすべて 0 にする。対応する関数（`int4recv`、`varchartypmodin`、`array_subscript_handler` など）を pg_proc に入れずに済み、`bytea`・`_cstring` の行も要らなくなる（PG との差。M2-Q13。Extended Query の M5 で埋める）。

### 1.4 M2 が保証すること・しないこと

- **保証する**: 正常停止（`SIGTERM` の smart shutdown、`SIGINT` の fast shutdown）の後に起動すれば、停止前にコミットしたデータとテーブル定義がすべて残り、コミットしていないものは残らない。ROLLBACK したデータは再起動後も戻ってこない。
- **保証しない**: 異常終了（`kill -9`、`SIGQUIT`、OS のクラッシュ、電源断）の後のデータ。COMMIT はディスクに何も書かない（fsync もしない）。クラッシュ時の整合性は M3 の WAL で保証する。
- **異常終了を検出したら起動を拒否する**。制御ファイルの `state` が `ShutDown` でなければ、`--ignore-unclean-shutdown` を付けない限り起動しない（§5.1）。黙って壊れたデータを読ませないため。
- 読み込んだページのチェックサムやヘッダが壊れていたら、必ず `XX001` を返す。壊れたデータを黙って返さない。

## 2. クレートとモジュールの構成

│   │   ├── mod.rs

**依存の方向**（下位は上位を `use` しない）:

```
error, types, util, interrupt
  ← sql
  ← catalog::{mod, builtin, schema}            （型と静的な表だけ。SystemColumn もここ）
  ← storage::vfs ← control, datadir             （制御ファイル、OidAllocator、ディレクトリのコピー。Vfs だけを使う）
  ← storage::{smgr, page, checksum} ← storage::buffer ← storage::heap ← storage::heap_store ← storage::stack
  ← txn::{mod, clog, manager}                   （storage::vfs と control を使う。heap は txn::{Xid, Snapshot} と Clog を使う）
  ← catalog::{rows, store, cache, reader}       （storage と txn を使う）
  ← analyzer ← planner ← executor
  ← checkpoint, bootstrap, engine, session
```

- `storage::heap` は可視性判定のために `txn::{Xid, CommandId, Snapshot}` と `txn::clog::Clog` を使う。逆に `txn` は `storage::vfs` と `control` 以外の storage に依存しない。型の循環を避けるため、`Xid`・`CommandId`・`Snapshot` は `txn/mod.rs` に置き、ロジックを持たない。`Transaction` は `WriterGuard`（`Arc<TxnManager>` を持つ）を含むので `txn/manager.rs` に置き、`txn/mod.rs` から再エクスポートする。
- `TxnManager` は `Arc<ControlFileHandle>` を持つ。`control` は `storage::vfs` の直上で txn より下の層に置く（§4.3a）。`datadir::OidAllocator` も同じ層。
- `SystemColumn` は analyzer と planner の両方が使うので `catalog/mod.rs` に置く（§4.6）。
- `datadir::copy_database_dir` はバッファプールを知らない。コピー前に対象のバッファを書き出すのは呼び出し側（engine / bootstrap）の責任（§6.9.3）。
- `catalog/mod.rs`（`TableDef` などの型）は storage より下、`catalog/store.rs` などは storage より上。同じモジュール名の中で層が分かれる点に注意する。
- `sql` はカタログにもストレージにも依存させない（M1 と同じ）。

**外部クレート**:

- yuzhu-core は M2 でも**外部依存なし**（std だけで書く）。`std::os::unix::fs::FileExt`（`read_exact_at` / `write_all_at`）と `std::fs::File::try_lock`（Rust 1.89 で安定化、未検証: 版数）で足りる。
- yuzhu-server は M1 の依存に加えて `signal-hook`（シグナルの受信）を使う（M2-Q6）。
- dev-dependency に `proptest` を足してよい（テスト用途）。

**コーディング規約（M2 で追加）**:

1. **`Drop` の中でディスクに書いたり fsync したりしない**。終了処理は必ず明示的な関数（`Cluster::shutdown` など）で行う。Drop で書き出すと、テストでの「クラッシュ」がクラッシュにならないため（buffer-io §3.4）。ロックの解放とピンの解除は Drop で行ってよい。
2. ファイル操作はすべて `Vfs` を通す。`std::fs` を直接使ってよいのは `storage/vfs/local.rs` だけ。
3. ページのバイト列は `u16::from_le_bytes(page[12..14].try_into().unwrap())` のようなアクセサで読み書きする。構造体をページに重ねる手段（transmute など）は `forbid(unsafe_code)` で使えないし、使わない。整列は問わない（`from_le_bytes` で読むので、1 バイトヘッダの `oidvector` の u32 の並びが整列していなくてもよい）。
4. すべての数値は**リトルエンディアン固定**で書く。
5. **数値の変換と clippy**: ワークスペースは `clippy::pedantic` を warn にし、CI は `-D warnings` で動く。バイト形式を扱う次の 4 つのモジュールに限り、ファイル先頭の `#![allow(clippy::cast_possible_truncation, clippy::cast_lossless)]` を許す: `storage/page.rs`、`storage/heap/tuple.rs`、`storage/checksum.rs`、`txn/clog.rs`。これらでも値の範囲は事前に検査してから `as` を使う。ほかのモジュールでは `u16::try_from(x)` を使う（失敗しうるなら `Error::internal` に変換）。
6. **Debug**: `missing_debug_implementations` が warn なので、公開する型（`PinnedBuffer`、各ガード、`Cluster`、`Session`、`StorageStack` など）にはすべて `Debug` を付ける（derive できなければ手書き）。トレイトオブジェクトにするトレイト（`TableStore`、`Vfs`、`VfsFile`、`WalFlush`、`CatalogReader`）は `Debug` をスーパートレイトにする。
7. **Mutex / RwLock の poison**: yuzhu-core の `std::sync` のロックは `util::sync::lock(&m) -> Result<MutexGuard<_>>` などを通して取る。poison されていたら `Severity::Panic`（`XX000 lock poisoned`）を返す。`Drop` の中だけは `PoisonError::into_inner` で続行してよい（その panic はすでに接続スレッドの `catch_unwind` で捕まり、クラスタを poison している。§6.3.4）。
8. **ページを書き換える手順**: 失敗しうる検査（タプルヘッダの読み取り、`satisfies_update`、空き容量の確認、形式化）は、すべて `page_mut()` を呼ぶ前に終える。`page_mut()` の後に `?` を書かない。避けられないときは `CriticalSection`（§6.3）で囲む。
9. **ストレージバリアの再入禁止**: 同じスレッドで共有のストレージバリアを二重に取らない（std の `RwLock` は書き手が待っていると新しい読み手を待たせる実装なので、DROP のコミットが待っている間に再入するとデッドロックする。未検証: Linux の futex 実装の細部）。`buffer/track.rs` のスレッドローカルの表で検出し、デバッグビルドでは panic する。
10. **ストレージバリアを持っている間は、`ResultSink` にもソケットにも書かない**。結果は M1 と同じく溜めてから、バリアを外した後で送る（遅いクライアントが DROP のコミットとライターロックを止めないため）。

## 3. ディスク上の形式

### 3.1 データディレクトリ

```
$DATA/
├── YUZHU_VERSION            データディレクトリの形式の版。中身は "1\n"
├── yuzhu.pid                ロックファイル（§3.9）
├── global/
│   ├── yuzhu_control        制御ファイル（8192 バイト、§3.2）
│   ├── 1262                 pg_database（共有カタログ。ファイル名 = relfilenode）
│   ├── 1260                 pg_authid
│   └── 1213                 pg_tablespace
├── base/
│   ├── 1/                   template1（データベースの OID ごとのディレクトリ）
│   │   ├── YUZHU_VERSION    "1\n"
│   │   ├── 1259  1249  1247  1255  2615  2617  2605  2601  2604  2606    カタログ
│   │   ├── 16384            ユーザーテーブル（relfilenode）
│   │   └── 16384.1          2 番目のセグメント（1GB を超えた分）
│   ├── 4/                   template0
│   └── 5/                   postgres
├── pg_xact/                 コミットログ（§3.8）
└── pg_wal/                  予約（M3）。M2 は空のディレクトリを作るだけ
```

- パスの規則は PostgreSQL の `relpath()` と同じにする（PG:src/include/common/relpath.h、<https://www.postgresql.org/docs/17/storage-file-layout.html>）。
  - `spc_oid == 1664`（pg_global）なら `global/<relfilenode>`、`1663`（pg_default）なら `base/<db_oid>/<relfilenode>`。
  - フォークの接尾辞: main = なし、fsm = `_fsm`、vm = `_vm`、init = `_init`。M2 で使うのは main だけ。ほかは名前だけ予約する（FSM / VM は M5 の VACUUM で入れる）。
  - セグメント番号 n ≥ 1 は `.<n>`。1 セグメント = `RELSEG_SIZE` ブロック（既定 131072 = 1GB）。`RELSEG_SIZE` は initdb のテスト用オプションで変えられ、制御ファイルに記録する。
- テーブル空間（`pg_tblspc/`）は作らない。`RelFileLocator` には最初から `spc_oid` を持たせるので、後でレイアウトを変える必要はない。
- データディレクトリの権限は 0700 とする。

### 3.2 制御ファイル `global/yuzhu_control`

大きさは 8192 バイト固定。**スロット A をオフセット 0、スロット B をオフセット 4096 に置く**。各スロットは次の形式（512 バイト。残りは 0）。m3-recovery §3.2 の形式に、M2 で必要な項目（オフセット 104 以降）を足したもの。

| オフセット | 型 | フィールド | M2 での値 |
|---|---|---|---|
| 0 | `[u8; 8]` | `magic` | `b"YUZHUCTL"` |
| 8 | u32 | `format_version` | 1 |
| 12 | u32 | `catalog_version` | `CATALOG_VERSION_NO`（`YYYYMMDDN` 形式。初版は 2026100401）。カタログの形式を変えたら上げる |
| 16 | u64 | `generation` | 書くたびに 1 増やす |
| 24 | u64 | `system_identifier` | initdb 時に生成（時刻と PID から作る。乱数クレートは使わない） |
| 32 | u32 | `state` | 0 = Startup、1 = ShutDown、2 = ShuttingDown、3 = InCrashRecovery（M3）、4 = InProduction |
| 36 | u32 | `page_size` | 8192 |
| 40 | u32 | `wal_segment_size` | 16777216（M3 用。M2 では検査だけ） |
| 44 | u32 | `flags` | bit0 = full_page_writes（M2 は 0）、bit1 = page_checksums（**M2 は常に 1**） |
| 48 | i64 | `time` | 更新時刻（UNIX 秒、表示用） |
| 56 | u64 | `checkpoint_lsn` | 0（M3） |
| 64 | u64 | `redo_lsn` | 0（M3） |
| 72 | u64 | `next_xid` | XID の先取りの上限（§6.7.3）。この値以上の XID はまだ使われていない |
| 80 | u64 | `oldest_xid` | 3（M5 の VACUUM で使う） |
| 88 | u32 | `next_oid` | OID の先取りの上限（§6.9.2） |
| 92 | u32 | `timeline` | 1（将来用） |
| 96 | u64 | `min_recovery_lsn` | 0（将来用） |
| 104 | u32 | `rel_seg_blocks` | 1 セグメントのブロック数（既定 131072） |
| 108 | u32 | `data_layout_version` | 1（ページの `pd_pagesize_version` の下位バイトと同じ） |
| 112 | u64 | `builtin_hash` | 組み込みの型・関数・演算子・キャストの表から計算したハッシュ（§6.8.5） |
| 120 | — | 予約 | 0 |
| 508 | u32 | `crc32c` | オフセット 0〜507 の CRC32C |

- **書き込み**: 2 つのスロットのうち `generation` が小さい方（または無効な方）に、`generation = 現在値 + 1` で書き、`sync_data` する。成功して初めて新しい内容になったとみなす。
- **読み込み**: 両スロットを読み、`magic`・`crc32c`・`format_version` が正しいもののうち `generation` が大きい方を採用する。両方とも無効なら起動を拒否する（`FATAL XX001 invalid control file`。文言は yuzhu 独自）。
- **起動時の検査**: `catalog_version`、`page_size`、`rel_seg_blocks`（ビルド時の上限との整合）、`data_layout_version`、`builtin_hash`、`flags` の page_checksums が一致しなければ、`FATAL` で起動を拒否し、ヒントに「initdb をやり直してください」と出す（PostgreSQL の `CATALOG_VERSION_NO` の運用と同じ。PG:src/include/catalog/catversion.h）。
- **更新は 1 か所を通す**: `ControlFileHandle`（§4.3a）がメモリ上の唯一の写しと、最後に書いたスロットと generation を持つ。XID の先取り、OID の先取り、チェックポイント、state の変更の 4 経路は、すべて `ControlFileHandle::update(|c| ...)` で行う。`update` は 1 つの Mutex の中で「写しを複製 → クロージャで変更 → 検査 → 書き込みと `sync_data` → 成功したら写しを置き換える」を行う。スロットの選択はファイルを読み直さず、メモリ上の generation で決める。
- `update` は `next_xid` と `next_oid` が下がらないこと（`next_oid` は周回の 16384 への戻りを除く）を検査し、破れていたら内部エラーにして書かない。唯一の例外は停止のチェックポイント（`CheckpointKind::Shutdown`）で、`next_xid` を先取りの上限から「ちょうどの値」に下げる。このときは全セッションが終わっていて、以後 XID は割り当てられない（`update_for_shutdown` という別の関数にして、例外を型で区別する）。
- 制御ファイルの書き込みか `sync_data` が失敗したら `Severity::Panic`（再試行しない。fsync の失敗と同じ扱い。§6.2）。メモリ上の写しは更新しない。
- **LSN の予約（M3 用）**: M3 の最初の有効な LSN は必ず 0 より大きくする（PostgreSQL も WAL はセグメント 1 から始まる）。`checkpoint_lsn == 0` は「WAL を持たないクラスタ（M2 で作ったもの）」を意味する。D15 により M3 は M2 のデータディレクトリを読まない（`format_version` を上げる）ので、この値で分岐する必要は M3 でも生じない見込み。
- initdb は両スロットを書く（A は generation 1、B は全部 0）。ファイルを作ったら `sync_all` と `global/` の `sync_dir` を行う。
- CRC32C は反転多項式 `0x82F63B78`、初期値 `0xFFFF_FFFF`、最後にビット反転。テストベクタ `crc32c(b"123456789") == 0xE306_9283`（m3-wal §2.10。未検証）。

### 3.3 ページ（8192 バイト）

ページヘッダは 24 バイトで、フィールドの意味と並びは PostgreSQL の `PageHeaderData` と同じ（PG:src/include/storage/bufpage.h、確認済み）。ただし `pd_lsn` は u64 一つにまとめ、すべてリトルエンディアンで書く。

| オフセット | 大きさ | 名前 | 型 | yuzhu での扱い |
|---|---|---|---|---|
| 0 | 8 | `pd_lsn` | u64 | M2 では常に 0。M3 で WAL の LSN を入れる |
| 8 | 2 | `pd_checksum` | u16 | **M2 から常に計算する**（§6.4） |
| 10 | 2 | `pd_flags` | u16 | `PD_HAS_FREE_LINES = 0x0001`、`PD_PAGE_FULL = 0x0002`、`PD_ALL_VISIBLE = 0x0004`。M2 では立てない。`0x0007` 以外のビットが立っていたら破損 |
| 12 | 2 | `pd_lower` | u16 | 空き領域の先頭（行ポインタ配列の末尾） |
| 14 | 2 | `pd_upper` | u16 | 空き領域の末尾（最も前にあるタプルの先頭） |
| 16 | 2 | `pd_special` | u16 | ヒープは 8192。B+Tree（M4）は special 領域を使う |
| 18 | 2 | `pd_pagesize_version` | u16 | `0x2000 \| 1`（= `0x2001`）。上位バイトがページサイズ、下位バイトが yuzhu のレイアウト版数 1 |
| 20 | 4 | `pd_prune_xid` | u32 | M2 では 0。M5 の HOT pruning のヒントとして、64 ビット XID の**下位 32 ビット**を入れる（ヒントなので、上位は現在の XID から復元する。PostgreSQL の `FullTransactionIdFromAllowableAt` と同じ考え方） |
| 24 | 4×n | 行ポインタ配列 | | §3.4 |

- 不変条件（読み込み時に検査し、破れていたら `XX001`）: `24 <= pd_lower <= pd_upper <= pd_special <= 8192`、`pd_special` が 8 の倍数、`pd_pagesize_version == 0x2001`、`(pd_lower - 24)` が 4 の倍数。
- **全バイト 0 のページは「新しいページ」として正当**とする（D12）。ファイルを伸ばした直後にクラッシュすると残りうるため。使う前に初期化する。チェックサムは検査しない。
  - 判定: `pd_upper == 0` なら、**8192 バイトがすべて 0 であることを確かめる**。1 バイトでも 0 でなければ `XX001`（ビット反転などで `pd_upper` だけが 0 になったページを素通りさせない）。PostgreSQL の `PageIsVerifiedExtended` が `PageIsNew` のときに全 0 を確かめるのと同じ（PG:src/backend/storage/page/bufpage.c）。
  - 書き出し: 全 0 のページには**チェックサムを入れない**（PostgreSQL の `PageSetChecksumCopy` と同じ。同じファイル）。拡張直後で初期化前のページが追い出されても、ディスク上は全 0 のままになる。
  - `Page::is_new()` は `pd_upper == 0` を返す。§6.4 の `verify` を通ったページについてだけ「全 0」と同じ意味になる。
- ヒープページの初期化: `pd_lower = 24`、`pd_upper = 8192`、`pd_special = 8192`、`pd_pagesize_version = 0x2001`、ほかは 0。

### 3.4 行ポインタ（4 バイト、u32 LE）

| ビット | 名前 | 意味 |
|---|---|---|
| 0–14 | `lp_off` | タプルのページ内オフセット |
| 15–16 | `lp_flags` | 0 = `LP_UNUSED`、1 = `LP_NORMAL`、2 = `LP_REDIRECT`、3 = `LP_DEAD` |
| 17–31 | `lp_len` | タプルの長さ（パディングを含まない） |

- `u32 = lp_off | (lp_flags << 15) | (lp_len << 17)`。PostgreSQL の C のビットフィールド（PG:src/include/storage/itemid.h）と同じ並びのはずだが（未検証）、yuzhu ではこの表を正とする。
- M2 で使うのは `LP_UNUSED` と `LP_NORMAL` だけ。`LP_DEAD` と `LP_REDIRECT` は M5（VACUUM、HOT）で使う。
- 行ポインタの番号（1 始まり）が TID のオフセット番号になる。**一度使った番号は M2 では再利用しない**（VACUUM まで再利用しないという PostgreSQL の性質に合わせる）。

### 3.5 ヒープタプルヘッダ（35 バイト + NULL ビットマップ + パディング）

決定 D2 により、XID を 64 ビットで持ち、cmin と cmax を別々のフィールドにする（m3-mvcc §10）。フィールドの意味とビットの値は PostgreSQL の `HeapTupleHeaderData`（PG:src/include/access/htup_details.h、確認済み）に合わせる。

| オフセット | 大きさ | 名前 | 型 | 内容 |
|---|---|---|---|---|
| 0 | 8 | `t_xmin` | u64 | 挿入したトランザクションの XID |
| 8 | 8 | `t_xmax` | u64 | 削除・更新したトランザクションの XID。0 = なし |
| 16 | 4 | `t_cmin` | u32 | 挿入したコマンド ID（挿入したトランザクションの中でだけ意味を持つ） |
| 20 | 4 | `t_cmax` | u32 | 削除したコマンド ID（削除したトランザクションの中でだけ意味を持つ）。xmax がなければ 0 |
| 24 | 4 | `t_ctid.block` | u32 | 自分自身、またはより新しい版の TID のブロック番号 |
| 28 | 2 | `t_ctid.offset` | u16 | 同じくオフセット番号 |
| 30 | 2 | `t_infomask2` | u16 | 下位 11 ビット = 列数（`HEAP_NATTS_MASK = 0x07FF`）。`HEAP_KEYS_UPDATED = 0x2000`、`HEAP_HOT_UPDATED = 0x4000`、`HEAP_ONLY_TUPLE = 0x8000`。`0x1800` は使わない（立っていたら破損） |
| 32 | 2 | `t_infomask` | u16 | 下表 |
| 34 | 1 | `t_hoff` | u8 | ヘッダ長（ビットマップとパディングを含む）。8 の倍数 |
| 35 | ⌈natts/8⌉ | `t_bits` | | NULL ビットマップ（`HEAP_HASNULL` のときだけ）。列 i（0 始まり）が非 NULL ならバイト `i/8` のビット `i%8` が 1 |
| … | | パディング | | 0 で埋めて `t_hoff` まで |

`t_infomask`（値は PostgreSQL と同じ）:

| 名前 | 値 | M2 での扱い |
|---|---|---|
| `HEAP_HASNULL` | 0x0001 | 書く・読む |
| `HEAP_HASVARWIDTH` | 0x0002 | 書く（可変長の列に非 NULL の値があるとき） |
| `HEAP_HASEXTERNAL` | 0x0004 | 予約（TOAST）。立っていたら破損 |
| `HEAP_XMAX_KEYSHR_LOCK` | 0x0010 | 予約（M5 の行ロック） |
| `HEAP_COMBOCID` | 0x0020 | **使わない**（立っていたら破損）。cmin と cmax を別々に持つため |
| `HEAP_XMAX_EXCL_LOCK` | 0x0040 | 予約（M5） |
| `HEAP_XMAX_LOCK_ONLY` | 0x0080 | 予約（M5） |
| `HEAP_XMIN_COMMITTED` | 0x0100 | 予約（M3 のヒントビット）。M2 は書かず、読んでも無視する |
| `HEAP_XMIN_INVALID` | 0x0200 | 同上 |
| `HEAP_XMAX_COMMITTED` | 0x0400 | 同上 |
| `HEAP_XMAX_INVALID` | 0x0800 | **挿入時に立てる**（xmax がないことを示す。PostgreSQL の `heap_prepare_insert` と同じ。PG:src/backend/access/heap/heapam.c 2341 行付近で確認）。削除・更新で外す |
| `HEAP_XMAX_IS_MULTI` | 0x1000 | 予約（M5） |
| `HEAP_UPDATED` | 0x2000 | UPDATE で作った新版に立てる |
| `0x0008`、`0x4000`、`0x8000` | | 使わない（PostgreSQL でも廃止済み）。立っていたら破損 |

- `t_hoff` の計算: NULL がなければ `MAXALIGN(35) = 40`。NULL ありで列数が 1〜40 なら `MAXALIGN(35 + ⌈natts/8⌉) = 40`、41〜104 列なら 48。
- **列数（natts）はタプルごとに持つ**。将来の `ALTER TABLE ADD COLUMN` で既存のタプルを書き換えずに済む（タプルの natts より後ろの列は NULL として読む）。
- `MaxHeapAttributeNumber = 1600`（CREATE TABLE の上限。超えたら `54011 tables can have at most 1600 columns`。PG:src/backend/catalog/heap.c 468 行で確認）。1600 列でも `t_hoff = MAXALIGN(35 + 200) = 240` で u8 に収まる。

### 3.6 列の値の符号化

列の値は、型の `typlen` / `typalign`（`pg_type` の値と同じ）に従って並べる。

| 型 | OID | typlen | typalign | ディスク上の表現 |
|---|---|---|---|---|
| bool | 16 | 1 | c | 0x00 / 0x01 |
| "char" | 18 | 1 | c | 1 バイト |
| name | 19 | 64 | c | 64 バイト固定。UTF-8 で最大 63 バイト、残りは 0 埋め（NUL 終端）。63 バイトへの切り詰めは字句解析（識別子。NOTICE 42622 を出す）と `types::sys` の name の入力関数で行い、UTF-8 の文字境界を守る（PostgreSQL の `truncate_identifier` / `namein` と同じ。未検証: 細部）。`form_tuple` は 63 バイトを超える値を受け取ったら内部エラー |
| int2 | 21 | 2 | s | i16 |
| int4 | 23 | 4 | i | i32 |
| int8 | 20 | 8 | d | i64 |
| oid、regproc | 26、24 | 4 | i | u32 |
| xid、cid | 28、29 | 4 | i | u32（xid はカタログの `relfrozenxid` などで使う 32 ビットの値。64 ビット XID の下位 32 ビット。M2 では表示用で、何の判定にも使わない。M5 で clog の切り詰めに使う 64 ビットの値の持ち方は §6.7.2 と M2-Q2） |
| tid | 27 | 6 | s | ブロック番号 u32 + オフセット u16 |
| float4 | 700 | 4 | i | `f32::to_bits()`。NaN のビットもそのまま保存する |
| float8 | 701 | 8 | d | `f64::to_bits()` |
| text、varchar、pg_node_tree | 25、1043、194 | -1 | i | varlena + UTF-8 のバイト列。typmod（varchar の長さ）はデータに入れない |
| oidvector | 30 | -1 | i | varlena + u32 の並び（yuzhu 独自。PostgreSQL の配列ヘッダは持たない） |

**varlena**（PostgreSQL のリトルエンディアン形式と同じ。PG:src/include/varatt.h、確認済み）:

| 先頭バイト | 種類 | 長さ |
|---|---|---|
| `xxxxxxx1`（`0x01` ちょうどを除く） | 1 バイトヘッダ | `(b >> 1) & 0x7F`（ヘッダの 1 バイトを含む。最大 127） |
| `0x01` | TOAST の外部参照 | 予約。**読んだら `XX001`** |
| `xxxxxx00` | 4 バイトヘッダ | `(u32 >> 2) & 0x3FFF_FFFF`（ヘッダの 4 バイトを含む） |
| `xxxxxx10` | 4 バイトヘッダ・圧縮 | 予約。**読んだら `XX001`** |

**書き込みの手順**（`heap_fill_tuple` 相当）:

```
off = t_hoff                                   // タプル先頭からのオフセット
for 各列:
    if NULL: ビットマップのビットを 0 にして次へ
    if typlen == -1:
        if データ長 + 1 <= 127:                 // 1 バイトヘッダ。整列しない
            buf[off] = ((データ長 + 1) << 1) | 1; off += 1; データを書く
        else:
            off = align(off, typalign); u32 ((データ長 + 4) << 2) を書く; データを書く
    else:
        off = align(off, typalign); 固定長の値を書く
```

- 読み出し（`heap_deform_tuple` 相当）では、varlena の列の位置で `buf[off] == 0` なら整列のパディングなので `align(off, typalign)` まで進める。そうでなければ（1 バイトヘッダの先頭は必ず奇数）その位置で読む。PostgreSQL の `att_align_pointer` と同じ規則（page-heap §1.6）。このため、**タプルの領域は必ず 0 で初期化してから値を書く**。
- 1 タプルの上限: 形式化した長さが `MaxHeapTupleSize = 8192 - MAXALIGN(24 + 4) = 8160` を超えたら、ページに触る前に `54000 row is too big: size N, maximum size 8160`（PG:src/backend/access/heap/hio.c と同じ文言）。**TOAST は実装しない**（M2-Q11）。カタログの行も同じ制限を受ける。

### 3.7 例

`CREATE TABLE t (a int4, b text, c int8, d bool)` に `(1, 'hello', NULL, true)` を挿入する。

- NULL があるので `HEAP_HASNULL`、text があるので `HEAP_HASVARWIDTH`、xmax はないので `HEAP_XMAX_INVALID`。`t_infomask = 0x0803`、`t_infomask2 = 4`。
- ビットマップは a・b・d が非 NULL なので `0b0000_1011 = 0x0B`。35 + 1 = 36 → `t_hoff = 40`。

| オフセット | バイト | 内容 |
|---|---|---|
| 0–7 | xmin（u64） | |
| 8–15 | `00 ×8` | xmax = 0 |
| 16–19 | cmin（u32） | |
| 20–23 | `00 00 00 00` | cmax = 0 |
| 24–29 | 自分の TID | t_ctid |
| 30–31 | `04 00` | t_infomask2 |
| 32–33 | `03 08` | t_infomask |
| 34 | `28` | t_hoff = 40 |
| 35 | `0B` | NULL ビットマップ |
| 36–39 | `00 ×4` | パディング |
| 40–43 | `01 00 00 00` | a = 1（4 境界） |
| 44 | `0D` | b の 1 バイトヘッダ = (5 + 1) << 1 \| 1 |
| 45–49 | `68 65 6C 6C 6F` | "hello"（整列しない） |
| — | | c は NULL なので領域なし |
| 50 | `01` | d = true |

`lp_len = 51`。ページ上では `MAXALIGN(51) = 56` バイトと行ポインタ 4 バイトを使う。この例はそのまま単体テストの固定値にする。

### 3.8 コミットログ `pg_xact/`

- XID 1 つにつき 2 ビット。値は PostgreSQL と同じ: 0 = `IN_PROGRESS`、1 = `COMMITTED`、2 = `ABORTED`、3 = `SUB_COMMITTED`（予約）（PG:src/include/access/clog.h、確認済み）。
- 1 ページ = 8192 バイト = 32768 XID。ページ番号 = `xid / 32768`、ページ内のバイト = `(xid % 32768) / 4`、ビット位置 = `(xid % 4) * 2`（PostgreSQL の `TransactionIdToByte` / `TransactionIdToBIndex` と同じ考え方）。ページヘッダもチェックサムも持たない（PostgreSQL の SLRU と同じ）。
- 1 セグメントファイル = 32 ページ（256KB、1,048,576 XID）。ファイル名はセグメント番号の**大文字 16 進 12 桁**（例 `pg_xact/000000000000`）。PostgreSQL の 4 桁とは違う（64 ビット XID のため。yuzhu 独自）。
- **ファイルがない、またはファイルの末尾より先のページは、全部 0（= IN_PROGRESS）として読む**（m3-recovery §7.2 の推奨と同じ。`CLOG_ZEROPAGE` 相当は作らない）。
- clog のページは書きかけ（torn）でも、すでに立っているビットは古い内容と新しい内容のどちらでも同じ値なので、M3 の REDO で補える。形式の変更は要らない。
- XID 0（無効）は問い合わせてはいけない（内部エラー）。XID 1（Bootstrap）と 2（Frozen）は clog を引かずに COMMITTED とみなす。

### 3.9 その他のファイル

- `YUZHU_VERSION`（最上位と `base/<oid>/`）: テキスト `1\n`。違えば起動を拒否する（`FATAL`、`database files are incompatible with server`、ヒントに版数を出す。PostgreSQL の PG_VERSION の検査に相当）。
- `yuzhu.pid`: 起動中のサーバが持つロックファイル。中身は 4 行（PID、データディレクトリの絶対パス、起動時刻の UNIX 秒、ポート番号）。`Vfs::lock_file` で排他ロック（`flock` 相当）を取り、取れなければ `FATAL lock file "yuzhu.pid" already exists`、ヒント `Is another yuzhu-server (PID N) running in data directory "D"?`（PostgreSQL の postmaster.pid の文言に合わせる）。ロックはプロセスが終われば OS が外すので、異常終了後に残ったファイルは上書きしてよい。停止時に削除する。

- **システム列の参照の番号**: analyzer は参照されたシステム列を出現順に `system_columns` に積み、`ColumnRef` の index を `natts + i`（i は `system_columns` の中の位置）にする。planner はこの並びをそのまま `SeqScan.system_columns` に写し、UPDATE / DELETE では末尾に `Ctid` を足す。
- **Update / Delete の入力行の形**: planner は Filter の上に Project を置き、入力行を必ず「対象テーブルの全ユーザー列（attnum 順）+ 末尾に ctid」にそろえる（WHERE で参照した `xmin` などの列はここで落ちる）。Update / Delete ノードはこの形だけを前提にする。
- **regproc の出力**（§4.2）: `types::io::output_text` は `Datum::Oid` を数値で出す。列の型が regproc のときは、executor の出力段（`Output` の行を作る所。H2）が `catalog::builtin` の静的な表で §4.2 の規則に従って名前に変える。`types::io` には `output_text_with(d, ty, regproc_name: &dyn Fn(Oid) -> Option<String>)` の口だけを置く。

## 5. 処理の流れ

### 5.1 サーバの起動

```
Cluster::open(vfs, opts)
  1. yuzhu.pid のロックを取る（取れなければ FATAL）。中身を書く
  2. YUZHU_VERSION を検査
  3. 制御ファイルを読む（§3.2）。定数を検査
  4. state != ShutDown なら:
       ignore_unclean_shutdown でなければ FATAL "database system was not properly shut down"
         （ヒント: "yuzhu M2 has no crash recovery. Start with --ignore-unclean-shutdown to start anyway (data may be inconsistent)."）
       指定されていれば WARNING をログに出して続ける
  5. StorageStack::new（StorageManager、BufferPool（NoWal）、Clog（next_xid のページを読み込む）、HeapStore）、
     TxnManager（next_xid = control.next_xid、xid_limit = 同じ値）、OidAllocator（next_oid = control.next_oid）を作る
  6. 共有カタログ（pg_database、pg_authid）を読めることを確かめる
  7. control.update(|c| c.state = InProduction)
  8. チェックポインタスレッドを起動する（Weak<Cluster> を渡す）
yuzhu-server: 待ち受けを開始する
```

### 5.2 文の実行（Session）

```
execute_simple(sql)
  ├─ sql::parse → 空なら EmptyQuery（M1 と同じ）
  ├─ 文ごとに:
  │   ├─ Failed 状態なら ROLLBACK / COMMIT 以外は 25P02（M1 と同じ）
  │   ├─ トランザクション制御（BEGIN / COMMIT / ROLLBACK）、SET / SHOW → M1 と同じ。COMMIT / ROLLBACK は §5.3
  │   ├─ CHECKPOINT → cluster.checkpoint()（ストレージバリアを持たずに呼ぶ）
  │   └─ それ以外（SELECT / VALUES / INSERT / UPDATE / DELETE / CREATE TABLE / DROP TABLE）:
  │       1. 書き込む文（INSERT / UPDATE / DELETE / CREATE / DROP）で、txn.writer が None なら
  │          txn_mgr.begin_write(session_id, lock_timeout) → txn.xid と txn.writer を設定
  │       2. barrier = txn_mgr.statement_barrier()
  │       3. gen = db.cache.generation()                     ← スナップショットより先に読む
  │       4. snap = txn_mgr.snapshot(txn.xid, txn.cid)
  │       5. catalog = StatementCatalog { snapshot: &snap, gen_at_snapshot: gen, bypass_cache: txn.catalog_dirty, .. }
  │       6. DML / SELECT: analyze → plan → build → next() ループ（行ごとに check_interrupts）。
  │          結果の行は Output に溜める（sink には書かない。§2 規約 10）
  │          DDL: §5.4
  │       7. barrier を解放する（この後で Output を sink に送る）
  │       8. buffer::assert_no_pins()
  │       9. 成功なら txn.command_counter_increment()。暗黙トランザクションの最後の文なら §5.3 のコミット
  │      10. 失敗なら: 暗黙トランザクションなら §5.3 のアボート。ブロック内なら Failed 状態にする
  │          （アボート処理は ROLLBACK のとき）。Severity::Panic なら FATAL を送って接続を閉じる
  └─ エラーが起きたら残りの文は実行しない（M1 と同じ）
```

- M1 の「文が失敗したらその文だけ undo する」はなくなる。PostgreSQL の意味論では、文の失敗はトランザクション全体の中断と同じことになるため（`m1.md` §4.1。dml-exec §1.3）。
- 読み取りだけの文はライターロックを取らない。書き込み中のトランザクションがあっても待たずに動き、その未コミットの変更は見えない。
- **ライターロックはスナップショットより先に取る**。こうすると、スナップショットを取ってから自分が更新するまでの間に、他者のコミット済みの更新が割り込むことはない（dml-exec §3.2）。

### 5.3 コミットとアボート

```
commit(txn)                                       ※ ストレージバリアを持たない状態で呼ぶ
  if let Some(xid) = txn.xid:
     1. txn_mgr.commit(xid):  proc の Mutex の中で clog.set_status(xid, Committed) → 実行中一覧から外す
        （ロック順序 proc → Clog。set_status は I/O をしない。失敗したら Severity::Panic）
     2. txn.catalog_dirty なら cluster.invalidate_all_catalog_caches()（全データベースのキャッシュ。M2 は全消去で足りる）
     3. txn.pending_unlinks が空でなければ:
          g = txn_mgr.exclusive_barrier()   ← 実行中の文がすべて終わるのを待つ
          各 rel: storage.unlink_storage(rel)（バッファを捨て、挿入先のヒントを消し、D13 の方式で消す）
          g を解放
     4. txn.writer を解放する（待っているセッションを起こす）
  txn をリセットする（cid = 0 など）

abort(txn)
  if let Some(xid) = txn.xid:
     1. txn_mgr.abort(xid):  clog.set_status(xid, Aborted) → 実行中一覧から外す
     2. txn.pending_creates が空でなければ、exclusive_barrier の下で unlink_storage
     3. txn.writer を解放する
  txn をリセットする
```

- clog への書き込みはメモリ上だけ。ディスクに書くのはチェックポイントと停止のとき。
- アボートで clog に ABORTED を書くのは診断のため。書かなくても、「実行中一覧になく、COMMITTED でもない XID」は中断扱いになる（§6.6）。
- キャッシュの無効化は、clog に記録して実行中一覧から外した**後**に行う。逆にすると、他のセッションがコミット前の古い行でキャッシュを作り直してしまう（catalog §7.3）。
- `pending_unlinks` の処理でエラーが起きても、コミットは取り消さない（WARNING を出す。PostgreSQL も同じ）。
- XID を割り当てた時点で `clog.ensure_page_for(xid)` 済みなので（§6.7.1）、手順 1 は I/O をせず失敗しない。それでも失敗したら（内部の不整合）`Severity::Panic` にする。「実行中一覧から外す前に失敗したコミット」という中間状態は作らない。
- `WriterGuard` が `commit` / `abort` を経ずに Drop された場合（panic など）は、§4.5 の安全網がメモリ上のアボートを行う。

### 5.4 CREATE TABLE と DROP TABLE

手順を組み立てるのは I（`session.rs`）。I は F の `CatalogStore` と G の `Cluster` の公開 API だけを呼ぶ。書き込みの `WriteCtx` は必ず `txn.write_ctx()` から得る（`cid_used` を立てるため。§4.5）。

```
CREATE TABLE（ライターロックとストレージバリアを持った状態）
  1. アナライズ（M1 と同じ。列の型、制約の名前、DEFAULT・CHECK の式の検査）。列数 > 1600 なら 54011
  2. スキーマの決定: 修飾なしなら search_path の最初に存在する名前空間（M2 では public）。
     pg_catalog を指定されたら 42501 permission denied to create "pg_catalog.t"
  3. 同じ名前空間に同名のリレーションがあれば 42P07（IF NOT EXISTS なら NOTICE 42P07 を出して終わる）
  4. oid = db.catalog.get_new_relation_oid(cluster.oid_allocator())。locator = (1663, db_oid, RelFileNumber(oid))。
     pg_class の OID の重複と、ファイル（D13 の 0 バイトの残骸を含む）の存在を確かめて取り直す
     （PostgreSQL の GetNewRelFileNumber と同じ考え方。§6.9.2）
  5. storage.create_storage(locator)、txn.pending_creates に積む
  6. w = txn.write_ctx()?; catalog.create_table(&w, snap, spec)（§6.8.3。pg_attrdef / pg_constraint の OID は
     get_new_oid(2604) / get_new_oid(2606) で取る）
  7. txn.catalog_dirty = true

DROP TABLE t [, ...]
  1. 名前解決（なければ 42P01、IF EXISTS なら NOTICE 00000 `table "t" does not exist, skipping`）
  2. システムカタログなら 42501 permission denied: "pg_class" is a system catalog（PG:src/backend/commands/tablecmds.c、確認済み）
  3. catalog.drop_table(w, snap, def)（pg_constraint → pg_attrdef → pg_attribute → pg_class の順に行を消す）
  4. txn.pending_unlinks に locator を積む（ファイルはコミット時に消す）
  5. txn.catalog_dirty = true
```

- PostgreSQL の `RelationCreateStorage` / `RelationDropStorage` / `smgrDoPendingDeletes` と同じ方式（PG:src/backend/catalog/storage.c）。
- M1 の `UndoEntry::DroppedTable { rows }`（行をすべてコピーして持つ）は不要になる。
- 同じトランザクションで CREATE TABLE の直後の文から INSERT できるのは、文の区切りで `command_counter_increment` し、自分が書いたカタログの行が次の文のスナップショットから見えるようになるため。

### 5.5 UPDATE と DELETE

```
UPDATE t SET a = a + 1 WHERE b > 0
  plan: Update { rel, input: Project { Filter { SeqScan { system_columns: [.., Ctid] }, b > 0 }, ユーザー列 + ctid },
                 assignments, checks, not_null }
  Update ノード（入力 1 行ごと。入力の形は §4.7 のとおり「全ユーザー列 + ctid」に限る）:
    1. check_interrupts
    2. 末尾の Datum::Tid を取り出す。旧行 = 先頭の natts 列
    3. SET の各式を旧行に対して評価する（SET a = b, b = a は入れ替えになる）
    4. 新行 = 旧行のコピーに評価した値を上書きしたもの
    5. 全列の NOT NULL を検査（23502）→ 全 CHECK を評価（23514）。Failing row には新行を出す
    6. storage.update(rel, w, snap, tid, &新行)
         Ok → 件数 +1
         SelfModified { cmax } → cmax == 現在の cid なら飛ばす（件数に数えない）。違えば 27000
           "tuple to be updated was already modified by an operation triggered by the current command"
         それ以外 → 内部エラー（単一ライターなので起きない）
  タグ: UPDATE n

DELETE FROM t WHERE ...
  Delete ノード: 末尾の TID を取り出して storage.delete。結果の扱いは UPDATE と同じ。タグ: DELETE n
```

- Halloween 問題（自分が書いた新版を同じ文のスキャンが拾う）は、コマンド ID で防ぐ。新版の `cmin` は現在の cid で、スナップショットの `curcid` と同じなので、可視性判定（§6.6）の「自分が挿入し、`cmin >= curcid` なら見えない」で読まれない。`INSERT INTO t SELECT * FROM t` も同じ仕組みで正しくなる。
- 制約の検査はヒープを書く前に行う（PostgreSQL の `ExecUpdateAct` → `ExecConstraints` と同じ。PG:src/backend/executor/execMain.c）。違反したら、それまでに更新した行もトランザクションの中断で消える。

### 5.6 チェックポイント

```
checkpoint::run(parts, kind)                  ※ Cluster::checkpoint と shutdown はこれを呼ぶだけ
  lock checkpoint_lock（同時に 1 つ）
  1. g = txn_mgr.statement_barrier()          ← DROP の後始末と並行しないようにする
  2. pool.flush_all_for_checkpoint()          開始時点で dirty なページをタグ順に書く（BufferSync 相当）
  3. g を解放
  4. clog.flush()
  5. smgr.sync_pending()                      ハンドルごと取り出して fsync（§6.2）。失敗したら Panic（§6.3.4）
  6. (next_xid, xid_limit) = txn.xid_counters()、next_oid = oids.limit() を読む（proc と OID の Mutex はここで外れる）
  7. Periodic / Explicit: control.update(|c| { c.next_xid = max(c.next_xid, xid_limit); c.next_oid = max(c.next_oid, next_oid) })
     Shutdown:            control.update_for_shutdown(|c| { c.next_xid = next_xid; c.next_oid = next_oid; c.state = ShutDown })
  8. smgr.finish_pending_unlinks()            D13 の残骸を消す（失敗は WARNING）
```

- 手順 6 と 7 の順序が要点: proc の Mutex を持ったまま制御ファイルの Mutex を取らない（§5.9 の「XID 採番 → 制御ファイル」と逆向きになるため）。値を取り出してから書く。読んだ値が古くなっても（その間に XID の先取りが進んで制御ファイルが先に書かれても）、`max` を取って書くので巻き戻らない。
- 手順 8 は手順 5 の後に行う。M3 では、残骸の削除は REDO 点が進んだ後（そのリレーションの WAL がもう再生されない時点）でなければならない。

- 契機は (1) `CHECKPOINT` 文、(2) チェックポインタスレッドの定期実行（`checkpoint_timeout` ごと）、(3) 停止時。
- M2 のチェックポイントは、クラッシュ時の整合性を保証しない（書いている最中に他のトランザクションがコミットしうる）。正常停止のチェックポイントだけが整合した状態を作る。

### 5.7 停止

| シグナル | 種類 | 動作（PostgreSQL と同じ。<https://www.postgresql.org/docs/17/server-shutdown.html>） |
|---|---|---|
| `SIGTERM` | smart | 新しい接続を `FATAL 57P03 the database system is shutting down` で拒否し、既存の接続がすべて切れるのを待つ |
| `SIGINT` | fast | 新しい接続を拒否し、既存のセッションに停止を通知する。実行中のトランザクションは中断する |
| `SIGQUIT` | immediate | チェックポイントをせずに直ちに終了する（次の起動は拒否される。テストでクラッシュを模擬するのに使う） |

```
fast shutdown
  1. 待ち受けを止める（以後の接続は 57P03）
  2. 各セッションの InterruptFlag を立て、ソケットを shutdown(Read) する
       アイドルのセッション: 読み込みが EOF で戻る → FATAL 57P01 "terminating connection due to administrator command" を送って閉じる
       実行中のセッション: 次の check_interrupts で 57P01（FATAL）→ アボート → 閉じる
  3. すべての接続スレッドの終了を待つ（各スレッドは Session::terminate を呼んでいる）
  4. cluster.shutdown():
       チェックポインタスレッドを止めて join する（以後、定期チェックポイントは走らない）
       → control.update(state = ShuttingDown) → checkpoint::run(Shutdown)（最後に state = ShutDown を書く）
       → yuzhu.pid を消してロックを外す
     途中で I/O エラーが起きたら state を ShutDown にしない（次の起動は拒否される）
```

### 5.8 initdb

`yuzhu-initdb -D <dir> [-U <superuser>] [--no-sync]`。エンコーディングは UTF8、ロケールは C に固定する。

```
bootstrap::initdb(vfs, opts)
  1. dir が存在しないか空であることを確かめる。0700 で作る
  2. global/、base/、base/1/、pg_xact/、pg_wal/ を作る。YUZHU_VERSION を書く
  3. template1（OID 1）をブートストラップする。SQL は使わず、schema.rs と rows.rs から直接ヒープに書く:
       各カタログのファイルを作る（共有は global/、ほかは base/1/）
       行を入れる: pg_namespace → pg_authid → pg_tablespace → pg_am → pg_type → pg_proc → pg_operator
                  → pg_cast → pg_class（13 カタログ分）→ pg_attribute（13 カタログの列とシステム列）
                  → pg_database（template1、template0、postgres の 3 行）
       すべての行は xmin = Xid::BOOTSTRAP(1)、cmin = 0（どのスナップショットからも見える）
       OID を自動で振るもの（pg_cast の行）は `(castsource, casttarget)` の昇順に 10000 から振る（決定的にするため）
  4. 全バッファを書き、各ファイルを fsync する（--no-sync なら省く）
  5. base/1/YUZHU_VERSION を書く
  6. base/1/ を base/4/（template0）と base/5/（postgres）にコピーする
     （M5 の CREATE DATABASE と同じ関数 `datadir::copy_database_dir(vfs, 1, dst, !no_sync)`。バッファは手順 4 で書き出し済み）
  7. pg_xact/ は空のまま（XID 1 と 2 は clog を引かない）
  8. 最後に制御ファイルを書く（state = ShutDown、next_xid = 3、next_oid = 16384）。
     制御ファイルの存在を「initdb が最後まで終わった」印にする。途中で失敗したらディレクトリを消す
```

- `-U` の既定は環境変数 `USER`（なければ `postgres`）。PostgreSQL の既定（OS のユーザー名）に合わせる。テストのスクリプトは `-U postgres` を付ける。
- pg_database の 3 行: template1 は `datistemplate = t, datallowconn = t`、template0 は `t, f`、postgres は `f, t`（PG の `make_template0` / `make_postgres` と同じ）。

### 5.9 ロックの順序

上の段から下の段へだけ取る（buffer-io §5.2 を全体に広げたもの）。

| 順 | ロック | 規則 |
|---|---|---|
| 1 | ライターロック（`TxnManager.writer` の所有） | トランザクションの終了まで持つ。待つのはまだ持っていないセッションだけ。`writer` の内部 Mutex は Condvar の待ちと所有者の書き換えにだけ使い、**XID の割り当て（proc）の前に外す** |
| 2 | `checkpoint_lock` | チェックポイントだけが取る |
| 3 | ストレージバリア（`TxnManager.barrier`） | 文の実行中は共有、DROP の後始末は排他。**排他を取るときは自分は共有を持っていないこと**。同じスレッドで共有を二重に取らない（§2 規約 9） |
| 4 | コンテンツラッチ（ページ） | ピンを持っているときだけ。**M2 のヒープは 2 つのページのラッチを同時に持たない**（§6.5.3）。M3 以降で複数取るなら同じリレーションのブロック番号の小さい順。追い出しの書き出しが犠牲のフレームに取る共有ラッチは `try_read` で取り（取れなければ別の犠牲を探す）、この順序の検査から外す |
| 5 | リレーション拡張ロック（smgr の内部） | `BufferPool::extend` の内部だけで取る。呼び出し側はラッチを持っていないこと |
| 6 | バッファのマッピング表のパーティション | 一度に 1 つ。持ったまま I/O しない |
| 7 | 葉のロック: `Frame.header`、`TxnManager.proc`、`Clog` の内部、`CatalogCache` の内部、制御ファイルの Mutex、OID 採番の Mutex、smgr の `rels` / `pending_sync` / `pending_unlink`、挿入先のヒント表 | 持ったまま他のロックを取らず、I/O もしない。例外は次の 3 つだけ: **OID 採番 → 制御ファイル**、**proc（XID 採番）→ 制御ファイル**、**proc → Clog の内部**（XID の割り当て時の `ensure_page_for` とコミット / アボートの `set_status`。どちらも I/O なし）。制御ファイルの Mutex は I/O（書き込みと sync）を伴うが、その下で他のロックは取らない |

- ライターロックを待つセッションはほかに何も持っていない。ストレージバリアの共有を持つ文は、ライターロックを待たない（ライターロックは手順 1 で先に取る）。したがってデッドロックしない。
- 制御ファイルを proc の Mutex の中で書くのは XID の先取りのとき（`XID_PREFETCH` 個に 1 回）だけ。その間スナップショットの取得は止まるが、頻度が低いので許す（PostgreSQL も XidGenLock の下で ExtendCLOG の I/O をする）。チェックポイントは逆向き（制御ファイル → proc）を作らないよう、値を先に読む（§5.6）。

## 6. モジュールごとの仕様

### 6.1 vfs

- buffer-io §3 の通り。`LocalVfs` は `std::fs::File` と `std::os::unix::fs::FileExt` で実装する。`sync_dir` はディレクトリを開いて `sync_all`。`lock_file` は `File::try_lock`（取れなければ `WouldBlock`。§4.3 の変換規則。`File::try_lock` が `std::fs::TryLockError` を返すことは rustc 1.96 で確認済み、安定化の版数は未検証）。
- O_DIRECT、`posix_fallocate`、`posix_fadvise` は使わない（std にない）。拡張は 0 埋めの書き込みで行う。
- 開いたファイル数の上限管理（PostgreSQL の VFD）は M2 では作らない。

### 6.2 smgr

- ブロック番号からの位置: `segno = blk / rel_seg_blocks`、`offset = (blk % rel_seg_blocks) * 8192`。
- `nblocks` はメモリにキャッシュする（1 プロセスなので常に正しい）。リレーションを初めて開いたときに、セグメントを順に開いて求める。最後以外のセグメントがちょうど `rel_seg_blocks` ブロックでなければ `XX001`。最後のセグメントの末尾がブロック境界でなければ、端数を切り捨てて WARNING を出す。
  - **リカバリモード（M3 用の予約）**: `set_recovery_mode(true)` の間は、短いセグメント k の後ろに k+1 があっても `XX001` にせず、k を 0 埋めで `rel_seg_blocks` ブロックまで伸ばす（クラッシュ後は拡張の fsync の順序が保証されないため。PostgreSQL の `EXTENSION_CREATE_RECOVERY` 相当。PG:src/backend/storage/smgr/md.c）。M2 は異常終了後の起動を拒否するので、`--ignore-unclean-shutdown` のときだけ有効にする。
  - `extend_to(rel, fork, blk)` は、ブロック `blk` が存在しなければ `blk` まで 0 埋めで伸ばす（M3 の REDO で `read_buffer_zeroed` が使う）。
- エラーと SQLSTATE は buffer-io §7 の表に従う。主なもの:
  - EOF を跨ぐ読み込み: `58030 could not read blocks N..N in file "base/5/16384": read only X of 8192 bytes`
  - ENOSPC: `53100 could not extend file "...": No space left on device`、ヒント `Check free disk space.`。extend で ENOSPC になったら `set_len` で元の長さに戻す
- `create` の後と `unlink` の後に、親ディレクトリを `sync_dir` する。
- **`pending_sync`**: `write_block` と `extend` は、書いたセグメントを**開いたハンドル（`Arc<dyn VfsFile>`）ごと** `pending_sync` に登録する。`unlink` は登録を外す。
- **`sync_pending` の取り出し**: Mutex の中で `std::mem::take` で集合を丸ごと取り出し、Mutex を外してから、取り出した各ハンドルに対して `sync_data` する。取り出した後に書かれたセグメントは新しい集合に登録され、次のチェックポイントで fsync される（PostgreSQL の `sync_cycle_ctr` と同じ目的。PG:src/backend/storage/sync/sync.c）。fsync が失敗したら Panic（再登録はしない）。パスを開き直さないので、取り出しの後に DROP のコミットがファイルを消しても `NotFound` にならない（unlink 後のハンドルへの fsync は成功する。§4.3）。
- **`unlink`（D13）**: (1) 登録された `pending_sync` を外す、(2) 2 番目以降のセグメントを消す、(3) 最初のセグメントを `set_len(0)` で切り詰めて `sync_data`、(4) 親ディレクトリを `sync_dir`、(5) `pending_unlink` に積む。残骸は `finish_pending_unlinks`（チェックポイントの最後）で消す。PostgreSQL の `mdunlinkfork` が最初のセグメントを次のチェックポイントまで残すのと同じ（PG:src/backend/storage/smgr/md.c のコメント。未検証: 行番号）。こうすると、同じ relfilenode が次のチェックポイントまで再利用されない（`exists` が true を返すため）。
- 異常終了で `pending_unlink` が失われると、0 バイトの残骸がディスクに残る。害はない（`exists` が true なので OID の取り直しの対象になるだけ）。消すのは M5 の VACUUM か、将来の孤児ファイルの掃除。
- **fsync の失敗は再試行しない**。`broken` を立てて `Severity::Panic`、`58030 could not fsync file "...": ...` を返す（PostgreSQL の `data_sync_retry = off` と同じ。<https://www.postgresql.org/docs/17/runtime-config-error-handling.html>）。以後の書き込みはすべて拒否する。

### 6.3 buffer

buffer-io §5 の設計をそのまま採る。要点:

1. **フレーム**: `Mutex<FrameHeader>`（タグ、valid、dirty、**just_dirtied**、io_in_progress、io_error、checkpoint_needed、pin_count、usage_count）、`Condvar`（I/O 待ち）、`RwLock<Box<Page>>`（コンテンツラッチ。§4.3）。マッピング表は 16 分割の `Mutex<HashMap<BufferTag, FrameId>>`。
2. **置換**: clock-sweep。usage_count の上限は 5、ピンのたびに +1。全フレームを一巡して見つからなければ `XX000 no unpinned buffers available`（PG:src/backend/storage/buffer/freelist.c）。
3. **read_buffer**: buffer-io §5.5 の手順。I/O 中はマッピング表のロックを持たない。同じタグを同時に読もうとしたら、I/O は 1 回だけ行い、ほかは `Condvar` で待つ。読み込んだら §6.4 の検査をし、失敗したらタグを外してフレームを free list に戻し、`XX001 invalid page in block N of relation base/D/R` を返す。
4. **書き出し（`flush_frame`）は 1 か所にまとめる**。手順（PostgreSQL の `BM_JUST_DIRTIED` と同じ。PG:src/include/storage/buf_internals.h、PG:src/backend/storage/buffer/bufmgr.c の `FlushBuffer` / `TerminateBufferIO`。PG17 での名前は未検証）:
   1. ピン → ヘッダの Mutex の中で `io_in_progress = true`、**`just_dirtied = false`**（ほかの書き出しが I/O 中なら Condvar で待ち、終わって dirty でなければ何もしない）
   2. 共有ラッチを取る（`RwLock::read` が poison で `Err` なら**決して書かず** `Severity::Panic`）→ スレッドローカルの 8KB の作業領域にコピー → 共有ラッチを外す
   3. `wal.flush_to(page_lsn)`（M2 は何もしない）
   4. コピーが全 0 なら何もしない。そうでなければチェックサムを入れる（D12）
   5. `smgr.write_block`
   6. ヘッダの Mutex の中で: 成功なら **`just_dirtied` が false のときだけ dirty を落とす**。失敗なら dirty はそのまま、`io_error = true`（項目 11）。`io_in_progress = false` にして Condvar で起こす

   こうすると、手順 2 のコピーの後に別のスレッドがページを書き換えた印（`just_dirtied`）が消えない。M3 で WAL-before-data を入れるときは、ここだけを変える。
5. **dirty の記録**: `PageWriteGuard::page_mut()` を呼んだら、ガードの Drop で、**コンテンツラッチを外す前に**ヘッダの Mutex の中で `dirty = true; just_dirtied = true` にする（ガードのフィールドの Drop 順に頼らず、`Drop::drop` の本体で明示的に行ってからラッチのガードを手放す）。panic のアンワインド中（`std::thread::panicking()`）の Drop では dirty を立てず、フレームを poison 扱い（ラッチが poison される）にする。
6. **プールの大きさ**: 既定 16384 フレーム（128MB。PostgreSQL の `shared_buffers` の既定と同じ）。起動時に `shared_buffers >= 16` かつ `shared_buffers >= 2 * max_connections` を検査し、満たさなければ起動を拒否する（PostgreSQL の下限に倣う。未検証）。テストでは小さい値（例 32）と小さい `max_connections` を使って追い出しを起こす。
7. **ピンの追跡**: `PinnedBuffer` は `!Send`。スレッドローカルの表でピンとラッチを数え、文の終わりに `assert_no_pins()`。`cfg(debug_assertions)` のビルドでは（yuzhu-server の結合テストでも効くよう `cfg(test)` ではなく）、ピン漏れ、同じフレームの二重ラッチ、ラッチ順序の違反、ストレージバリアの再入を panic で検出する（`RwLock` の再入は黙ってハングするため）。
8. **poison**: 書き込みラッチを持ったまま panic すると、ページが書きかけのまま残る。poison されたラッチを見つけたら（`read` / `write` / `try_write` / `flush_frame` / 追い出しのどこでも）`Severity::Panic`（`XX000 buffer content lock poisoned`）でクラスタを止める。**poison されたフレームは決して書き出さない**（チェックポインタは別スレッドなので、Panic でプロセスが終わる前に壊れたページを書きうるため）。
9. **クリティカルセクション（D14）**: ページの変更は「失敗しうる検査をすべて終える → `CriticalSection::enter` → `page_mut()` で書き換える → ガードを Drop → セクションを抜ける」の順で行う（§2 規約 8）。セクションの中で `Err` が起きたら `escalate` で `Severity::Panic` に変え、クラスタを poison する。中で panic したら、セクションの Drop が `std::thread::panicking()` を見てクラスタを poison する。poison されたクラスタでは `flush_frame` も追い出しも書き込みをしない（`is_poisoned` を手順 1 で確かめる）。PostgreSQL の `START_CRIT_SECTION` の中のエラーが PANIC になるのと同じ（PG:src/backend/access/heap/heapam.c の `heap_update` など）。
10. **拡張（`BufferPool::extend`）**: (1) smgr の拡張ロックを取る、(2) 新しいブロック番号 `n = nblocks` を決め、マッピング表に `(rel, fork, n)` のフレームを **I/O 中として先に予約**する（同じタグが既にあれば内部エラー）、(3) `smgr.extend` で 0 のブロックを書く（`nblocks` が増える）、(4) フレームを valid（中身は 0）にして I/O 中を解き、拡張ロックを外す、(5) ピンして返す。予約が先なので、`nblocks` が増えた直後に別スレッドが同じタグを `read_buffer` しても、予約済みのフレームの I/O 完了を待つだけで二重に登録されない。失敗したら予約を外して free list に戻す。
11. **追い出しと付け替え（犠牲のフレームの再利用）**: PG16 以降と同じく「犠牲のフレームの古いタグを外してから新しいタグを登録する」方式で、パーティションのロックは一度に 1 つしか持たない（PG:src/backend/storage/buffer/bufmgr.c の `GetVictimBuffer` / `InvalidateVictimBuffer`。PG17 の関数名は未検証）。次の不変条件を守る:
    - (a) 犠牲が dirty なら、ピンしたまま `flush_frame` で書く（共有ラッチは `try_read`。取れなければ別の犠牲を探す）。書いた後にまた dirty になっていたら、書き直すか別の犠牲を探す（やり直し）。
    - (b) 古いタグを外す直前に、古いタグのパーティションのロックとヘッダの Mutex の中で「`pin_count == 1`（自分だけ）かつ dirty でない」をもう一度確かめる。崩れていれば外さずに別の犠牲を探す。
    - (c) 古いタグを外したら、フレームを「タグなし・自分だけがピン」にしてからパーティションのロックを外す。新しいタグのパーティションに登録しようとして、すでに他のスレッドが同じタグを登録していたら、犠牲のフレームを free list に戻し、相手のフレームをピンして使う。
    - これらを破ると、同じタグが 2 つのフレームに載る（二重のマッピング）か、dirty の印が消える（lost write）。
12. **書き出しの失敗（EIO、`ShortWrite`、ENOSPC）**: PostgreSQL の `BM_IO_ERROR` と同じく（PG:src/include/storage/buf_internals.h）、書き込みに失敗したフレームは **valid かつ dirty のまま残し**、`io_error = true` を立てる。追い出しの途中なら、そのフレームは使わずに別の犠牲を探す。次の書き出しの機会にブロック全体を書き直す。`ShortWrite` は EIO と同じに扱う（部分的に書かれたブロックは次の全体の書き直しで上書きされる）。他人のコミット済みのページを持つフレームを、書けなかったからといって捨てたり再利用したりしない。全フレームが書けない dirty で埋まれば `no unpinned buffers available` になる。
13. **ヒントビット（M3 以降）**: 共有ラッチの下では書かない。`try_write()` で排他ラッチが取れたときだけ、`page_mut_hint()` で立てる（D6）。

#### 6.3.4 Panic の扱い

- `Severity::Panic` のエラー（fsync の失敗、制御ファイルの書き込みの失敗、ラッチや Mutex の poison、クリティカルセクションの中のエラー）を受けた session は、`cluster.poison()` を呼び、クライアントに FATAL を送って接続を閉じる。
- 接続スレッドの `catch_unwind` で捕まえた panic も、`cluster.poison()` を呼ぶ（共有の状態が書きかけかもしれないため。PostgreSQL のバックエンドの異常終了で postmaster が全体を再起動するのと同じ考え方）。
- **監視して終了するのは yuzhu-server の専用ループ（J）だけ**。待ち受けのループ（100ms ごとに停止の要求を確かめる。§6.12）で `cluster.is_poisoned()` も確かめ、立っていたらチェックポイントをせずに終了コード 3 で終わる。yuzhu-core のチェックポインタスレッドは監視しない（poison なら何も書かずに次の周期を待つ）。制御ファイルの `state` は `InProduction` のままなので、次の起動は拒否される。
- プロセスを `std::process::exit` で落とすのは `yuzhu-server` だけにする（yuzhu-core のテストを落とさないため）。

### 6.4 page と checksum

```rust
pub struct Page(pub [u8; BLCKSZ]);   // フレームの中身は Box<Page>（§4.3）

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum LpFlags { Unused = 0, Normal = 1, Redirect = 2, Dead = 3 }
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct ItemId { pub off: u16, pub flags: LpFlags, pub len: u16 }   // §3.4 の u32 を分解したもの

impl Page {
    pub fn init_heap(&mut self);
    pub fn is_new(&self) -> bool;                    // pd_upper == 0（verify 済みなら全 0 と同じ意味）
    pub fn is_all_zero(&self) -> bool;
    pub fn lsn(&self) -> u64;  pub fn lower(&self) -> u16;  pub fn upper(&self) -> u16;  pub fn special(&self) -> u16;
    pub fn max_offset(&self) -> u16;                 // 行ポインタの数
    /// off は 1 始まり。off が 0 か max_offset を超える、または lp_off + lp_len > pd_special などの
    /// 範囲外なら PageError::BadItem（呼び出し側で XX001 に変換する。panic しない）
    pub fn item_id(&self, off: u16) -> std::result::Result<ItemId, PageError>;
    /// LP_NORMAL のタプルのバイト列。範囲は item_id と同じ規則で検査する
    pub fn item(&self, off: u16) -> std::result::Result<&[u8], PageError>;
    pub fn item_mut(&mut self, off: u16) -> std::result::Result<&mut [u8], PageError>;
    /// 入らなければ None。MAX_HEAP_TUPLES_PER_PAGE を超えても None
    pub fn add_item(&mut self, data: &[u8]) -> Option<u16>;
    pub fn free_space(&self) -> usize;               // 新しい行ポインタ 1 つ分を引いた値（PageGetHeapFreeSpace 相当）
    /// ヘッダの不変条件 + 全 0 の検査（D12）+ チェックサム。
    /// crate の Result<T> エイリアスと衝突しないよう std::result::Result と書く
    pub fn verify(&self, blkno: BlockNumber) -> std::result::Result<(), PageError>;
}
pub fn page_checksum(page: &[u8; BLCKSZ], blkno: BlockNumber) -> u16;
```

- `verify` の手順: (1) `pd_upper == 0` なら全 8192 バイトが 0 であることを確かめて Ok（違えば `NotAllZero`）、(2) ヘッダの不変条件（§3.3）、(3) チェックサム。行ポインタの範囲は `item_id` が呼ばれるたびに検査する（チェックサムが通っても、yuzhu 自身のバグで壊れたページはありうるため）。

- `add_item`: 必要量 = `MAXALIGN(len) + 4`。入れば `pd_upper -= MAXALIGN(len)`、領域を 0 で埋めてからコピー、行ポインタ `{off: pd_upper, flags: NORMAL, len}` を末尾に足し、`pd_lower += 4`。UNUSED の行ポインタは再利用しない（§3.4）。
- **チェックサム**は PostgreSQL の `pg_checksum_page`（PG:src/include/storage/checksum_impl.h、確認済み）をそのまま移植する:
  - ページを u32（リトルエンディアンで読む）の `[32][64]` の配列とみなす。`sums[j]` を `checksumBaseOffsets[j]`（32 個の定数。ソースからそのまま写す）で初期化する。
  - 各 `i`（0..64）、各 `j`（0..32）について `tmp = sums[j] ^ data[i][j]; sums[j] = tmp.wrapping_mul(16777619) ^ (tmp >> 17)`。続けて値 0 で 2 周回す。
  - `result = sums[0] ^ ... ^ sums[31]`。`pd_checksum` を 0 とみなして計算する。
  - `checksum = result ^ blkno`（リレーション内の通し番号。セグメント内の番号ではない）、`(checksum % 65535) + 1` を u16 で返す。
  - x86_64 / aarch64 はリトルエンディアンなので、同じバイト列に対して PostgreSQL と同じ値になる。単体テストでは、PostgreSQL のソースから手で計算した固定値（全 0 以外の既知のページ）と比べる。
- 書き出し時にコピーへチェックサムを入れ（全 0 のページには入れない。D12）、読み込み直後に検証する。メモリ上のページの `pd_checksum` は気にしない。

### 6.5 heap

#### 6.5.1 tuple.rs

```rust
pub fn form_tuple(desc: &TupleDesc, row: &[Datum], w: &WriteCtx, flags: TupleFlags) -> Result<Vec<u8>>;
pub fn deform_tuple(desc: &TupleDesc, bytes: &[u8]) -> Result<Row>;
pub struct TupleHeader { pub xmin: Xid, pub xmax: Xid, pub cmin: CommandId, pub cmax: CommandId,
                         pub ctid: Tid, pub infomask2: u16, pub infomask: u16, pub hoff: u8 }
impl TupleHeader { pub fn read(bytes: &[u8]) -> Result<TupleHeader>; pub fn write(&self, bytes: &mut [u8]); }
```

- 形式は §3.5、§3.6。読み込み時の検査（`t_hoff` が 8 の倍数で `35 + ビットマップ` 以上、使わないビットが立っていない、列が `lp_len` を越えない）に失敗したら `XX001`。
- タプルの natts が `desc.attrs.len()` より大きければ `XX001`。将来の `DROP COLUMN` は PostgreSQL と同じく `attisdropped` の列を desc に残すので、正常な状態では起きない。natts が小さければ、後ろの列を NULL として読む（§3.5）。
- `TupleFlags`（`form_tuple` の引数）: `pub struct TupleFlags { pub updated: bool }`（`HEAP_UPDATED` を立てるか）。

#### 6.5.2 hio.rs（挿入先の選択）

- FSM は作らない（M2-Q17）。リレーションごとに、メモリ上の「挿入先ページのヒント」（`Mutex<HashMap<RelFileLocator, BlockNumber>>`）を持つ。
- 挿入: ヒント（なければ `nblocks - 1`、0 ブロックなら拡張）のページを排他ラッチで開き、`is_new` なら初期化し、入れば入れる。入らなければ**ラッチを外してから** `pool.extend` で新しいページを足し、その排他ラッチを取って入れ、ヒントを更新する（ラッチを持ったまま `extend` を呼ばない。§5.9）。
- リレーションを消したら（`unlink_storage`）、ヒントの表からそのリレーションのエントリを消す（同じ relfilenode が再利用されたときに古いブロック番号を指さないため）。
- M2 には VACUUM がないので、削除や UPDATE で空いた領域は再利用されない（そもそも xmax が立っただけのタプルは物理的に残る）。

#### 6.5.3 操作

| 操作 | タプルに書くこと |
|---|---|
| insert | `xmin = w.xid`、`xmax = 0`、`cmin = w.cid`、`cmax = 0`、`ctid = 自分の TID`（置いた後で書く）、`infomask |= XMAX_INVALID` |
| delete | 旧版を `satisfies_update` で検査（下記）。Ok なら `xmax = w.xid`、`cmax = w.cid`、`infomask &= !(XMAX_INVALID \| XMAX_COMMITTED \| XMAX ロック系)`、`infomask2 |= HEAP_KEYS_UPDATED`（PostgreSQL の `heap_delete` と同じ） |
| update | 旧版を同じく検査。新版を insert と同じ値 + `HEAP_UPDATED` で作り、**旧版と同じページに入ればそこへ**、入らなければ §6.5.2 の手順で置く。旧版に delete と同じ値を書き、`ctid = 新版の TID` にする。`HEAP_KEYS_UPDATED` は立てない（インデックスがないため）。`HEAP_HOT_UPDATED` / `HEAP_ONLY_TUPLE` も立てない |

- **update のラッチの手順**（固定。2 つのページのラッチを同時に持たない）:
  1. 新版を `form_tuple` で作る（失敗しうる処理はここまでに終える。§2 規約 8）。
  2. 旧ページをピンして排他ラッチを取り、旧版のヘッダを読み、`satisfies_update` で判定する。`Ok` でなければラッチを外して結果を返す（ページは変えていない）。
  3. 旧ページに新版が入るなら、同じラッチのまま `CriticalSection` に入り、新版を置き、旧版に xmax / cmax / ctid（新版の TID）を書く。終わり。
  4. 入らなければ旧ページのラッチを外す。§6.5.2 の手順で新版を別のページに置く（新版の ctid は自分自身）。その後で旧ページを再び排他ラッチし、`CriticalSection` の中で旧版に xmax / cmax / ctid を書く。単一ライターなので、ラッチを外していた間に旧版を他者が変えることはなく、再判定は要らない（M5 の複数ライターでは、旧版のタプルロックか再判定が要る）。
  - 手順 4 の途中の状態（新版は置いたが旧版にまだ xmax がない）を他のスナップショットが見ても、新版の xmin は実行中なので新版は見えず、旧版だけが見える。
  - M3 で、両方のページを番号順にラッチして WAL レコードを 1 つ書く形に変える（PostgreSQL の `heap_update`。PG:src/backend/access/heap/heapam.c）。そのときの順序規則は §5.9 の 4。
- `satisfies_update(tuple, snap)`（PostgreSQL の `HeapTupleSatisfiesUpdate` の縮小版）。「実行中」は**スナップショットの `xip` ではなく、生の実行中一覧（`TxnManager::is_in_progress`）**で判定する（PostgreSQL の `TransactionIdIsInProgress` と同じ。M5 の複数ライターで差が出る）:
  - xmin が見えない（§6.6 の判定で不可視）→ `Invisible`
  - xmax なし、または xmax が中断扱い（`is_in_progress(xmax)` が false で、clog が COMMITTED でない。クラッシュで IN_PROGRESS のまま残ったものを含む）→ `Ok`
  - xmax == 自分の XID → `SelfModified { cmax }`
  - xmax が実行中（他人）→ `BeingModified`（M2 では起きない）
  - xmax がコミット済み → `ctid != 自分` なら `Updated`、そうでなければ `Deleted`（M2 では起きない）
- 1 行の上限は §3.6（54000）。

#### 6.5.4 scan.rs

- `HeapScan` はこのファイルで定義する（§4.4）。
- `begin_scan` でブロック数を固定する（PostgreSQL の `rs_nblocks` と同じ。heapam.c）。スキャン中に伸びたブロックは読まない。
- `scan_next`: `buf` が空なら、次のブロックをピンして共有ラッチを取り、行ポインタを順に見て、`LP_NORMAL` のタプルを可視性判定し、**見えるものをすべて `HeapTuple` にデコードして `buf` に積む**。ラッチとピンを外してから 1 行返す。`is_new` のページは空として扱う。
- ラッチもピンも `scan_next` の呼び出しをまたいで持たない（D10）。

### 6.6 可視性判定（visibility.rs）

PostgreSQL の `HeapTupleSatisfiesMVCC`（PG:src/backend/access/heap/heapam_visibility.c）から、ロックだけの xmax、MultiXact、サブトランザクション、ヒントビット、`HEAP_MOVED` を除いたもの。M3 でもこのまま使う。

```text
committed_in_snapshot(x, snap):            // x がスナップショット時点でコミット済みか
    if x == BOOTSTRAP || x == FROZEN: return true
    if x >= snap.xmax:                return false
    if x ∈ snap.xip:                  return false
    return clog.status(x) == Committed     // IN_PROGRESS のまま残った XID（クラッシュや停止時に実行中だったもの）は中断扱い

xmax_invalid(t) = t.xmax == 0 || (t.infomask & XMAX_INVALID) != 0

visible(t, snap):
    if Some(t.xmin) == snap.own_xid:
        if t.cmin >= snap.curcid:            return false    // この文以降に自分が挿入した
        if xmax_invalid(t):                  return true
        if Some(t.xmax) == snap.own_xid:     return t.cmax >= snap.curcid   // この文以降に自分が削除した → まだ見える
        return true                                           // 他人の xmax（M2 では起きない）
    if !committed_in_snapshot(t.xmin, snap): return false
    if xmax_invalid(t):                      return true
    if Some(t.xmax) == snap.own_xid:         return t.cmax >= snap.curcid
    if !committed_in_snapshot(t.xmax, snap): return true      // 削除者が実行中・中断・未来
    return false
```

- **clog を見るのは、必ずスナップショットの判定の後**（m3-mvcc §0 の 2）。
- スナップショットの取得（`TxnManager::snapshot`）は `proc` の Mutex の中で行う: `xmax = next_xid`、`xip = running − {own}`（ソート済み）、`xmin = min(running ∪ {next_xid})`。XID の割り当てと実行中一覧への追加は同じ Mutex の中で行うので、`xmax = next_xid` で正しい。
- XID 0 の xmin は破損（`XX001`）。

### 6.7 txn

#### 6.7.1 単一ライターロック

- `begin_write(session_id, timeout)`: (1) `writer` の Mutex を取り、空くまで `Condvar` で待つ（`lock_timeout` が 0 でなければその時間まで）。所有者を自分にして **Mutex を外す**。(2) `proc` の Mutex の中で、必要なら XID を先取りして制御ファイルに書き（§6.7.3）、`xid = next_xid`、`clog.ensure_page_for(xid)`、`next_xid += 1`、`running` に入れる。(3) `WriterGuard` を返す。(2) が失敗したら所有者を外して Condvar で起こしてからエラーを返す。
- ロックはトランザクションの終了（§5.3）で解放する。`WriterGuard` の Drop でも解放する（安全網。終わっていないトランザクションはメモリ上でアボートしてから解放する。§4.5）。
- 時間切れは `55P03 canceling statement due to lock timeout`。その文はエラーになり、トランザクションの扱いは通常のエラーと同じ。
- **影響**（M2-Q3）: 書き込むトランザクションは同時に 1 つだけ。BEGIN の中で INSERT したまま放置すると、ほかのセッションの書き込みはすべて待つ。読み取りは待たない。

#### 6.7.2 clog

- §3.8 の形式。ページは必要になったら読み込み、メモリに保持する（M2 では上限なし。1 億 XID で約 25MB。切り詰めは M5 の VACUUM と一緒に入れる）。
- **XID の割り当て時にページを確保する**（PostgreSQL の `ExtendCLOG`。PG:src/backend/access/transam/varsup.c の `GetNewTransactionId` から呼ばれる）。`open` で `next_xid` を含むページを読み込んでおけば、以後に割り当てる XID のページは常に新しいページ（0 で作る）なので、`ensure_page_for` も `set_status` も I/O をしない。M2 はページを追い出さない。M5 でページの追い出しを入れるときも「実行中の XID のページは追い出さない」を守る。
- `status` は過去の XID のページを読むことがある（I/O しうる）。`status` は `proc` の Mutex の中では呼ばない。
- `flush`: Mutex の中で、dirty なページのコピーを取り、**同時に dirty を落とす**。Mutex を外してからファイルに書き、書いたファイルを `sync_data` する。書き込みか sync が失敗したら `Severity::Panic`（dirty を戻して再試行する案もあるが、fsync の失敗は再試行しない規則（§6.2）にそろえる）。こうすると、コピーの後に `set_status` が同じページを変えても dirty の印が消えない（§6.3 の lost write と同じ型の問題）。ファイルがなければ作る（`pg_xact/` を `sync_dir`）。
- **clog の切り詰め（M5）と凍結**: 切り詰めるには、切り詰める範囲の XID を参照するタプルがなくなっている必要がある。M5 の VACUUM はタプルの xmin を `FROZEN` に書き換える（または `HEAP_XMIN_COMMITTED` / `HEAP_XMIN_INVALID` を確定させる）処理を持ち、各リレーションの「これより古い XID は残っていない」境界を 64 ビットで記録する。`pg_class.relfrozenxid` / `pg_database.datfrozenxid` は PostgreSQL と同じ 32 ビットの `xid` 型で、上位 32 ビットを復元できない（VACUUM されないテーブルが 2^32 以上遅れると曖昧になる）ため、**64 ビットの境界はこれらの列には頼らない**。持ち方（yuzhu 独自のカタログ、または `xid8`（OID 5069。未検証）の列）は M5 で決める。D15 により、そのときの catversion の変更は initdb のやり直しで吸収する（M2-Q2）。

#### 6.7.3 XID の採番と永続化

- `next_xid` と `xid_limit` をメモリに持つ。割り当てで `next_xid == xid_limit` になったら、`control.update(|c| c.next_xid = max(c.next_xid, xid_limit + XID_PREFETCH))` で**制御ファイルを書いて sync してから** `xid_limit` を進め、割り当てる。書き込みが失敗したら `xid_limit` は進めない（`update` は Panic を返す）。
- 起動時は `next_xid = xid_limit = control.next_xid`（先取りした分は捨てる）。正常停止のチェックポイントでは、`control.next_xid = next_xid`（ちょうどの値）を書く。
- XID は決して再利用しない。再利用すると、以前に中断扱いになったタプルが、新しいトランザクションのコミットで見えてしまう（dml-exec §4.3）。64 ビットなので周回は扱わない。

#### 6.7.4 コマンド ID

- 文ごとに、書き込んだときだけ進める（PostgreSQL の `CommandCounterIncrement` が `currentCommandIdUsed` を見るのと同じ。PG:src/backend/access/transam/xact.c）。
- 上限は `u32::MAX - 1`。超えたら `54000 cannot have more than 2^32-2 commands in a transaction`。

#### 6.7.5 ストレージバリア

- `RwLock<()>`。文の実行中（手順 2〜7）は共有で持つ。チェックポイントのバッファ書き出し中も共有で持つ。コミットの `pending_unlinks` とアボートの `pending_creates` の処理は排他で持つ。
- 目的: ファイルを消すときに、そのリレーションのページを読んでいる（ピンしている）文やチェックポイントがないことを保証する。
- ガードは文を実行する関数のスコープの中だけで持ち、構造体に保存しない（`'static` 版は作らない）。同じスレッドで二重に取らない（§2 規約 9）。`Cluster::connect` と `Session::new` はバリアを取らない（共有カタログの読み取りはファイルを消される心配がない）。
- バリアを持っている間は sink に書かない（§2 規約 10）。
- **影響**（M2-Q14）: PostgreSQL では、コミットしていない DROP TABLE は AccessExclusiveLock でほかの SELECT を待たせる。yuzhu M2 では待たせず、ほかのセッションは MVCC で古い定義を読み続ける。DROP のコミットは、実行中の文が終わるのを待つ。M5 でリレーション単位のロックを入れるときに PostgreSQL と同じにする。

- DROP TABLE では、`conrelid`・`adrelid`・`attrelid` で従属する行を直接探して消す（M2 には pg_depend がない）。

#### 6.8.4 DEFAULT と CHECK の式

- 列名と型は PG に合わせて `adbin` / `conbin`（`pg_node_tree`）にするが、**中身は利用者が書いた式の SQL テキスト**とする（M1 の Q-006 と同じ。catalog §6.2 の案 A）。読むときにパースとアナライズをやり直す。
- `pg_get_expr(adbin, adrelid)` は中身をそのまま返す。PostgreSQL の出力（`(a > 0)` など、ruleutils.c の正規形）とは一致しない（M2-Q9）。M4 で `\d` に対応するときに、アナライズ済みの式を逆変換した正規形に移る（catversion を上げる）。

#### 6.8.5 組み込みの型・関数・演算子・キャスト

- **実行時の名前解決は M2 でも静的な表（`builtin.rs`）を引く**。カタログのテーブルは SQL から見るための写し。
- 両者のずれを防ぐため、`rows.rs` が作る pg_type・pg_proc・pg_operator・pg_cast の初期行を正規の形に並べてバイト列にし、FNV-1a 64 ビットでハッシュした値を `builtin_hash` とする。initdb が制御ファイルに書き、起動時に一致を確かめる（違えば initdb のやり直しを求めて起動を拒否する）。
- `builtin.rs` に足す項目（catalog §5.3）:
  - `BuiltinType`: `typalign`、`typstorage`、`typcategory`（既存）、`typelem`、`typcollation`、`array_oid`（既存）、入出力関数の pg_proc OID
  - `BuiltinOperator`: `proc_oid`（`oprcode`）、`oprkind`、`com` / `negate`（任意）
  - `BuiltinCast`: `CastMethod::Function` に関数の OID（`castfunc`）
  - `BuiltinFunction`: `volatility`（`provolatile`）、`prosrc`（Rust の実体の名前）
- M2 で足す演算子とキャスト（OID は `.dat` から取る）:
  - `oid`: `= <> < <= > >=`。キャスト int4→oid（暗黙、バイナリ）、int8→oid（暗黙、関数）、oid→int4（代入、バイナリ）、oid→int8（代入、関数）
  - `regproc`: oid との相互のバイナリキャスト（暗黙）
  - **バイナリキャスト（`castmethod = 'b'`）はビットをそのまま読み替え、範囲を検査しない**: `(-1)::oid` は 4294967295、`4294967295::oid::int4` は -1（PostgreSQL と同じ）。int8→oid の関数キャスト（`int8_to_oid` 相当）は範囲を検査し、範囲外は `22003`（未検証: PG の文言）。
  - `name`: `= <> < <= > >=` を (name, name)、(name, text)、(text, name) について。キャスト text→name・name→text（暗黙、関数）、varchar→name（暗黙）、name→varchar（代入）
  - `"char"`: `= <> < <= > >=`。キャスト "char"→text（暗黙）、text→"char"（代入）、"char"↔int4（明示）
  - `xid`: `=`、`<>`、`xid = int4`。`cid`: `=`。`tid`: `= <> < <= > >=`
  - 型の入出力関数への I/O 変換キャスト（任意の型 → text の明示キャスト）は M1 の `CastMethod::InOut` で扱う

#### 6.8.6 キャッシュと名前解決

- **pg_catalog の 13 カタログ**は、`schema.rs` から作った `TableDef` を釘付け（nailed）で使う。カタログを読むためにカタログを読む必要はない。
- 名前解決の順序: 修飾なしなら pg_catalog（静的な表）→ search_path の各名前空間（M2 では public だけ）。`pg_catalog.x` と修飾されたら静的な表だけを見る。
- ユーザーテーブルの `TableDef` はデータベースごとの `CatalogCache` に置く。外れたら、文のスナップショットで pg_class → pg_attribute → pg_attrdef → pg_constraint を順次走査して組み立てる（M2 はインデックスがないが、カタログは小さいので問題にならない）。
- **キャッシュに入れてよい条件**: 文の開始時（スナップショットを取る前）に読んだ generation が、入れる時点の generation と同じこと。コミットの手順（clog → 実行中一覧 → generation を進める）と合わせると、古い定義を入れることはない（catalog §7.3 の 5 を、スナップショットの取得時点に合わせて強めたもの）。
- 「存在しない」ことはキャッシュしない。
- このトランザクションがカタログを変更していれば（`txn.catalog_dirty`）、キャッシュを使わずに自分のスナップショットでカタログを読む。キャッシュにはコミット済みの定義しか入っていないため。
- コミット時にカタログを変更していれば、`Cluster::invalidate_all_catalog_caches()` で全データベースのキャッシュを `invalidate_all` する（単一ライターなので、変更するトランザクションは同時に 1 つしかない）。
- `CatalogCache` の generation は HashMap と同じ `RwLock` の中にある（§4.6）。`insert` は write ロックの中で generation を比べてから入れ、`invalidate_all` は write ロックの中で消去と加算を行う。`generation()` は read ロックで読む。

#### 6.8.7 カタログへの書き込みの制限

- カタログの読み書きは、必ずユーザーテーブルと同じヒープ API（スナップショット付きのスキャン、`insert` / `delete` / `update`）を通す。カタログ専用の「直接書き換える」経路を作らない（M3 以降でも DDL のトランザクションが自動的に正しくなるため）。
- ユーザーによる、OID が 16384 未満のリレーションへの INSERT / UPDATE / DELETE は `42501 permission denied for table pg_class` で拒否する。PostgreSQL のスーパーユーザーはカタログを DML で書き換えられるので、これは yuzhu 独自の挙動（キャッシュと静的な表がずれるため禁止する。M2-Q12）。文言は PostgreSQL が一般ユーザーに返すもの（`aclcheck_error` の `permission denied for table %s`。未検証）に合わせ、将来の一般ユーザーの挙動と一致させる。DROP の `"pg_class" is a system catalog`（§5.4）とは別の文言。SELECT は許す。
- pg_authid は全ユーザーが SELECT できる（M2 はスーパーユーザーしかいない）。PostgreSQL は `rolpassword` があるので一般ユーザーには読ませない（`pg_roles` ビューを使わせる）。M5 で一般ロールと SCRAM を入れるときに権限を付ける（TODO。M2-Q13）。

### 6.9 engine、datadir、control

#### 6.9.1 接続

```
Cluster::connect(database, user)
  1. 共有カタログのスナップショット（own なし）で SharedCatalogStore から pg_database を引く（ストレージバリアは取らない）。なければ FATAL 3D000 database "x" does not exist
  2. datallowconn = false なら FATAL 55000 database "template0" is not currently accepting connections
     （PG:src/backend/utils/init/postinit.c、確認済み）
  3. pg_authid を引く。なければ FATAL 28000 role "x" does not exist（PG:src/backend/utils/init/miscinit.c、確認済み）。
     rolcanlogin = false なら FATAL 28000 role "x" is not permitted to log in（pg_database_owner で接続するとこれになる。テストに使う）
  4. DatabaseHandle を databases から取る（なければ作る）
```

- M1 の「データベースは 1 つ」という制約はなくなる。template1 と postgres の両方に接続できる。
- `current_database()` は接続先の名前。`session_user` / `current_user` は接続時のユーザー名。

#### 6.9.2 OID の採番

- クラスタ全体で 1 つのカウンタ（`Mutex<(next, limit)>`）。`next == limit` になったら `limit += OID_PREFETCH` として制御ファイルを書いて sync してから渡す。起動時は `next = limit = control.next_oid`。
- 16384 から使い、u32 の上限で 16384 に戻す。`OidAllocator::next_raw` はカウンタから取るだけで、重複は検査しない。
- **重複の検査は `CatalogStore::get_new_oid(oids, catalog_oid)`**（§4.6）: その OID を使うカタログだけを、**全ての版が見える条件**（PostgreSQL の `GetNewOidWithIndex` が使う SnapshotAny 相当。PG:src/backend/catalog/catalog.c。SnapshotAny の部分は未検証）で順次走査し、同じ `oid` の行が 1 つでもあれば取り直す。削除済みでもまだ物理的に残っている行（M2 は VACUUM がないので全て残る）と、未コミットの行とも重複させない。文のスナップショットで走査すると、DROP 済みのテーブルの OID を再び割り当て、古いスナップショットの読み手が古い定義のまま引く（M2-Q14）ことがありうるため。
  - pg_class の OID: `get_new_relation_oid`（pg_class の重複 + ファイルの存在。§5.4 の手順 4）
  - pg_attrdef の OID: `get_new_oid(oids, 2604)`、pg_constraint の OID: `get_new_oid(oids, 2606)`
  - M4 で OID のインデックスを作ったら、走査をインデックスの検索に替える。

#### 6.9.3 データベースのコピー

- `datadir::copy_database_dir(vfs, src, dst, sync)`: `base/<src>/` の全ファイルを `base/<dst>/` に読み書きでコピーし、`sync` なら各ファイルとディレクトリを fsync する。**Vfs だけを使い、バッファプールを知らない**。呼び出し前に対象のバッファをディスクに書いておくのは呼び出し側の責任。M2 では initdb だけが使う（バッファは §5.8 の手順 4 で書き出し済み）。
- M5 の CREATE DATABASE（PostgreSQL の `STRATEGY = FILE_COPY` 相当）では、呼び出し側（engine）が「チェックポイント → コピー → WAL レコード → チェックポイント」の順に行う（PG:src/backend/commands/dbcommands.c。未検証）。この関数のシグネチャはその前提で固定し、チェックポイントを内部で取らない。

### 6.10 sql、analyzer、関数

- パーサ:
  - `UPDATE`、`DELETE`、`CHECKPOINT` の構文（§1.2）。`UPDATE ... FROM`、`DELETE ... USING`、`WHERE CURRENT OF`、`RETURNING`、`SET (a, b) = ...` は構文として受け付け、アナライザが `0A000` を返す。
  - `E'...'` のエスケープ（`\n`、`\t`、`\\`、`\'`、`\xHH`、`\ooo`）。
  - 修飾した関数名 `schema.func(...)`。`pg_catalog` 以外のスキーマの関数は `42883`。
- アナライザ（dml-exec §6.4 の表に従う）:

| 項目 | 挙動 |
|---|---|
| 存在しない SET 列 | `42703 column "x" of relation "t" does not exist`（位置付き） |
| 同じ列への 2 回の代入 | `42601 multiple assignments to same column "a"` |
| システム列への代入 | `0A000 cannot assign to system column "ctid"` |
| WHERE の型 | bool でなければ `42804 argument of WHERE must be type boolean, not type integer` |
| SET の値 | 代入キャスト（`m1.md` §5.2 と同じ経路）。できなければ `42804 column "a" is of type integer but expression is of type boolean` |
| `SET t.a = 1` | `42703`（PostgreSQL の挙動は未検証。slt に入れる前に確かめる） |
| システム列の参照 | `ctid`、`xmin`、`cmin`、`xmax`、`cmax`、`tableoid` を列名として解決する。ユーザー列に同名があればユーザー列が優先（PostgreSQL ではシステム列と同名の列は作れない: `42701 column name "xmin" conflicts with a system column name`。CREATE TABLE でこれを検査する） |
| `*` | システム列を含まない |

- SeqScan の `system_columns` には、問い合わせで参照したシステム列だけを入れる。UPDATE / DELETE では最後に `Ctid` を足す。
- 関数（OID は `pg_proc.dat` の値。未検証のものはなし: catalog §5.3 で確認済み）:

| 関数 | OID | 挙動 |
|---|---|---|
| `pg_get_userbyid(oid) → name` | 1642 | `pg_authid` から名前。なければ `unknown (OID=N)`（未検証。PG:src/backend/utils/adt/acl.c の `pg_get_userbyid` で確かめてから slt に入れる）。`FnKind::Context` |
| `pg_encoding_to_char(int4) → name` | 1597 | PostgreSQL の符号化方式の名前の表（PG:src/common/encnames.c の `pg_enc2name_tbl`。0 = `SQL_ASCII`、6 = `UTF8` など）をそのまま写す。範囲外は空文字列 |
| `array_length(anyarray, int4) → int4` | 2176 | strict。M2 では引数が常に NULL なので本体は `0A000` |
| `array_to_string(anyarray, text) → text` | 395 | 同上 |
| `pg_table_is_visible(oid) → bool` | 2079 | catalog §8 の定義。`FnKind::Context`（`CatalogReader::visible_namespaces` を使う） |
| `format_type(oid, int4) → text` | 1081 | 型名（`integer`、`character varying(10)` など SQL の表記）。strict ではない（PostgreSQL と同じ）。例: `format_type(1043, 14)` → `character varying(10)`、`format_type(18, NULL)` → `"char"`、`format_type(99999, NULL)` → `???`、`format_type(NULL, NULL)` → NULL |
| `pg_get_expr(pg_node_tree, oid) → text` | 1716 | 中身をそのまま返す |

- `anyarray` の引数には、配列型（`typcategory = 'A'`）の値と NULL が一致する（最小限の多相）。
- psql の `\l`（catalog §2.2 のクエリ）が動くこと（定義は §1.1）。`Access privileges` 列は PostgreSQL では template0 / template1 で非 NULL（`=c/postgres` など）で、yuzhu は NULL なので値が違う（M2-Q13）。
- **M2 で psql の `\dt` を実行したとき**: psql が送るクエリは LEFT JOIN を含むので、アナライザが `0A000 JOIN is not supported yet`（M1 と同じ文言の系統）を返す。psql はそのエラーを表示する。M4 で `\dt` を動かすには、JOIN のほかに `c.relkind IN ('r','p','')`（`"char"` の空文字列 → 0）、`n.nspname !~ '^pg_toast'`（正規表現。手書きか `regex` クレートかは M4 で決める。M2-Q8）、`n.nspname <> 'information_schema'` が要る。

### 6.12 yuzhu-server

- 起動: `yuzhu-server -D <dir> [--config path] [--listen] [--port] [--max-connections] [--shared-buffers 128MB] [--checkpoint-timeout 300] [--ignore-unclean-shutdown] [--log-level]`。データディレクトリは `-D` → 設定ファイルの `data_directory` → 環境変数 `YUZHU_DATA` の順で決める。どれもなければエラー。
- シグナル: `signal-hook` の `Signals` を専用スレッドで受け、`SIGTERM`（smart）、`SIGINT`（fast）、`SIGQUIT`（immediate）を停止の調停役（`shutdown.rs`）に伝える。
- 待ち受け: `TcpListener` をノンブロッキングにし、100ms ごとに停止の要求と `cluster.is_poisoned()` を確かめる（poison の監視はここだけ。§6.3.4）。
- 接続の登録: 各接続の `TcpStream::try_clone()` と `InterruptFlag` を登録表に持つ。fast shutdown では、フラグを立ててから `shutdown(Shutdown::Read)` する（§5.7）。
- 接続スレッドは、終了の経路（正常、エラー、`catch_unwind` で捕まえた panic）のすべてで `Session::terminate()` を呼ぶ。panic のときは先に `cluster.poison()` を呼ぶ（§6.3.4）。
- 終了コード: 正常停止 0、起動の拒否 1、Panic 3。
- `yuzhu-initdb` は同じクレートの 2 つ目のバイナリ（`src/bin/yuzhu-initdb.rs`）。引数は `-D`、`-U`、`--no-sync`、テスト用の隠しオプション `--rel-seg-blocks N`。

### 7.2 再起動をまたぐテスト（`tests/restart/`）

- 配置: `tests/restart/<シナリオ>/NN-<名前>.slt`。フェーズの間でサーバを再起動する。
- 実行: `tests/run.sh --target pg|yuzhu --restart tests/restart/<シナリオ>`。各フェーズごとにランナーのプロセスを起動し直す（再起動後の接続の張り直しをランナーに頼らないため）。
  - `pg`: `tests/pg.sh restart`（`docker restart`。smart shutdown）
  - `yuzhu`: `tests/yuzhu.sh restart`（`SIGINT` で fast shutdown → 終了を待つ → 同じデータディレクトリで起動 → 待ち受けを待つ）
- シナリオ:
  1. CREATE / INSERT / UPDATE / DELETE をコミット → 再起動 → 値が残っている
  2. BEGIN → UPDATE → ROLLBACK → 再起動 → 元の値（clog の永続化）
  3. 大きなテーブル（テスト用にプールを小さくしたサーバで、プールより大きいもの）で BEGIN → 全行 UPDATE → ROLLBACK → 再起動 → 元の値（steal されたページにある未コミットの版が見えない）
  4. BEGIN → CREATE TABLE → ROLLBACK → 再起動 → テーブルがない
  5. DROP TABLE をコミット → 再起動 → ない
  6. `connection other` で開いたトランザクションに未コミットの変更を残したまま停止 → 再起動 → その変更はない（`pg` は smart shutdown なので、このフェーズの最後にランナーが終わってから再起動される。yuzhu も同じ）
- `tests/yuzhu.sh`: `start [--port N] [--data DIR] [--shared-buffers N]`（データディレクトリがなければ `yuzhu-initdb -U postgres --no-sync` を実行）、`stop [smart|fast|immediate]`、`restart`、`status`。`pg.sh` と同じ形にする。

## 9. 確認事項

ユーザーの不在中に仮決めしたことです。仮決めのままでよいか確認してください。変更する場合は、ディスク形式に関わるもの（M2-Q2、Q5、Q15）は実装の前に決めるのが望ましいです。

- **M2-Q1 ROLLBACK の方式**: M1 の undo ログ方式をやめ、M2 から xmin/xmax と永続化したコミットログ（`pg_xact/`）で ROLLBACK と文の原子性を実現します（D1）。これで M1 の既知の制約だったダーティリードは M2 で解消します（Q-003 の前倒し）。代わりに、削除・更新された古い版や中断された行は M5 の VACUUM まで領域を取ったまま残ります。
- **M2-Q2 タプルヘッダの形式（ディスク形式）**: XID を 64 ビットにし、cmin と cmax を別々に持つため、タプルヘッダは PostgreSQL の 23 バイトより大きい 35 バイトになります（D2。M3 の MVCC 調査の推奨を先取り）。周回（wraparound）の期限に追われる緊急 VACUUM や xidStopLimit が不要になる代わりに（ただし M5 で clog を切り詰めるための「凍結に相当する処理」は必要です。その境界の 64 ビットの値は、32 ビットの `relfrozenxid` 列には頼らず M5 で別に持ちます。§6.7.2）、1 行あたり 12 バイト（8 バイト境界で揃えると多くの場合 16 バイト）大きくなり、1 ページに入る最大の行数は 291 から 185 に減ります。PostgreSQL と同じ 32 ビット + 凍結にしたい場合は、M2 の実装前に変える必要があります。
- **M2-Q3 単一ライターロック**: 書き込むトランザクションは同時に 1 つだけにします（D3。M3 の方針の前倒し）。BEGIN の中で書き込んだまま放置すると、ほかのセッションの書き込みはすべて待ちます（読み取りは待ちません）。`lock_timeout` で待ちを打ち切れます。複数ライターは M5 です。
- **M2-Q4 クラッシュ時の保証**: M2 は正常停止の後だけを保証します。COMMIT はディスクに書きません。異常終了の後は起動を拒否し、`--ignore-unclean-shutdown` を付ければ（整合性の保証なしで）起動できます。クラッシュ時の保証は M3 の WAL で入れます。
- **M2-Q5 ページチェックサム**: M2 から常に有効で、無効にできません（PostgreSQL 17 の initdb の既定は無効）。M3 でヒントビットを入れるときに、「ヒントビットだけの変更ではページを dirty にしない」方式か、PostgreSQL の `wal_log_hints` と同じくページ全体を WAL に書く方式かを選びます（M3 の WAL 調査はチェックサムなしを提案していましたが、M2 では有効にする判断をしました）。
- **M2-Q6 `signal-hook` の追加**: `SIGTERM` / `SIGINT` で正常停止するには、シグナルを受け取る仕組みが要ります。標準ライブラリだけでは unsafe なしに書けないため、yuzhu-server に `signal-hook` クレートを追加します（CLAUDE.md の「周辺用途」の一覧にはない種類の依存です）。
- **M2-Q7 server_version を 17.0 に上げる（Q-004 の改訂）**: カタログを PG17 の列構成にそろえるので、名乗る版も 17.0 にします。psql の `\d` には 17 専用の分岐がないことを確認済みです。
- **M2-Q8 psql の対応範囲**: M2 で動かすのは `\l` までにします（psql 17 で確かめます。§1.1）。`\dt` には LEFT JOIN と正規表現が要るので、JOIN と一緒に M4 で動かします（前倒しする案もあり、その場合は 2〜3 日増えます）。M4 の確認事項として、`!~` の正規表現を手書きするか `regex` クレートを使うか（CLAUDE.md の「周辺用途」に当たるか）を決める必要があります（QUESTIONS.md への転記を依頼します）。
- **M2-Q9 DEFAULT / CHECK の式の保存形式**: `pg_attrdef.adbin` / `pg_constraint.conbin` には、利用者が書いた式の SQL テキストをそのまま入れます（Q-006 の継続）。`pg_get_expr` の出力が PostgreSQL の正規形（`(a > 0)` など）と違います。M4 で正規形に移ります。
- **M2-Q10 組み込みオブジェクトの扱い**: 型・関数・演算子・キャストの名前解決は、M2 でも Rust の静的な表を引きます。カタログの `pg_type` などは SQL から見るための写しで、ずれはハッシュで検出して起動を拒否します。
- **M2-Q11 TOAST なし**: 1 行が約 8KB（8160 バイト）を超えると `54000 row is too big` になります。PostgreSQL なら圧縮や TOAST で格納できる大きな値も、yuzhu ではエラーです。共有テストは 8KB を超える行を使わないことにします。
- **M2-Q12 システムカタログへの DML の禁止**: `pg_class` などへの INSERT / UPDATE / DELETE を `42501 permission denied for table pg_class` で拒否します。PostgreSQL のスーパーユーザーは書き換えられますが、yuzhu ではキャッシュや静的な表とずれるためです。
- **M2-Q13 カタログの PostgreSQL との差**: 次の点が PostgreSQL と違います。(1) ユーザーテーブルと一部のカタログの行型（`reltype`）を作らない（6 つのカタログの複合型だけ持つ）、(2) 配列型は一部（`_aclitem` など 5 つ）だけ持つ、(3) ACL 系の列（`datacl` など）は常に NULL（`\l` の「Access privileges」列も空）、(4) `pg_type` の `typreceive`・`typsend`・`typmodin`・`typmodout`・`typanalyze`・`typsubscript` と `pg_operator` の `oprrest`・`oprjoin` は 0、(5) pg_language がないので `pg_proc.prolang = 12` が参照先のない値になる、(6) pg_authid を全ユーザーが読める（M5 で直す）、(7) pg_cast の OID の値。`public` の所有者は `pg_database_owner`（6171）の行を足して PostgreSQL と一致させました。
- **M2-Q14 DROP TABLE と読み取りの並行性**: PostgreSQL では、コミット前の DROP TABLE はほかのセッションの SELECT を待たせます。yuzhu M2 では待たせず、ほかのセッションは古い定義でテーブルを読み続けます（MVCC で見えるため）。DROP のコミットは、実行中の文が終わるのを待ってからファイルを消します。M5 でリレーション単位のロックを入れるときに PostgreSQL と同じにします。
- **M2-Q15 制御ファイルの形式（ディスク形式）**: `global/yuzhu_control` に 2 つのスロットを持ち、交互に上書きする方式にします（M3 のリカバリ調査の推奨を先取り）。ファイル名と中身は PostgreSQL の `pg_control` とは違います。
- **M2-Q16 接続時のロールの確認**: 接続時に `pg_authid` を見て、存在しないユーザー名は PostgreSQL と同じく `28000 role "x" does not exist` で拒否します（認証は trust のまま）。M1 ではどんなユーザー名でも接続できました。initdb の `-U` の既定は OS のユーザー名なので、テストでは `-U postgres` を付けます。
- **M2-Q17 空き領域の管理**: FSM（空き領域マップ）は作らず、新しい行はリレーションの最後のページに追加します。削除した行の領域は M5 の VACUUM まで再利用されないので、更新や削除を繰り返すとファイルは大きくなる一方です。
- **M2-Q18 バッファプールの既定サイズ**: 128MB（16384 フレーム。PostgreSQL の `shared_buffers` の既定と同じ）。`--shared-buffers` で変えられます。
- **M2-Q19 システム列**: `ctid`、`xmin` などを SELECT で参照できるようにしますが、値が PostgreSQL と一致しないので、共有テスト（slt）では使いません。`xmin` / `xmax` は 64 ビットの XID の下位 32 ビットを返します。
- **M2-Q20 マイルストーン間のデータディレクトリ互換**（D15）: M5 までは、M2 で作ったデータディレクトリを M3 以降のサーバで読むことは保証せず、`format_version` か `catalog_version` が変わったら initdb のやり直しを求めます。ページ・タプル・clog・制御ファイルの形式は M2 で固定しますが、カタログの中身（M5 の 64 ビットの frozenxid の持ち方など）は変わりうるためです。データを持ち越したい場合は `pg_dump` 相当の手段を別途用意する必要があります（M2 の範囲外）。
- **M2-Q21 リレーションのファイルの遅延削除**（D13）: DROP TABLE のコミットやアボートした CREATE TABLE のファイルは、すぐには消さず、最初のセグメントを 0 バイトに切り詰めて次のチェックポイントまで残します（PostgreSQL と同じ）。異常終了するとこの 0 バイトのファイルが残りますが、害はありません。

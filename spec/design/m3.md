# yuzhu M3 基本設計（Rust 実装）

M3 のゴールは**トランザクションの耐久性**です。M2 は「正常に停止すれば、コミットしたものが残る」ところまでを保証しました。M3 は `kill -9`・OS のクラッシュ・電源断の後でも、**クライアントに COMMIT の完了を返したトランザクションはすべて残り、それ以外は一切見えない**ことを保証します。そのために REDO のみの WAL、ファジーチェックポイント、full page write（FPW）、コミットごとの fsync、クラッシュリカバリを実装し、決定的な障害注入と `kill -9` の 2 層のクラッシュ試験で確かめます。あわせて、M2 までで後回しにしたトランザクションの意味論（READ ONLY、AND CHAIN、セーブポイントのエラー、タイムアウト、キャンセル）を PostgreSQL にそろえます。この文書は `m1.md`・`m2.md` と同じく、並列に動く実装者全員が従う**契約**です。

- 要件定義: <https://claude.ai/code/artifact/9381e901-9f2a-49a4-9bb2-479295dde6e2>
- 前提: `spec/design/m1.md`、`m1-changes.md`、`spec/design/m2.md`（M2 の契約。この文書は M2 からの差分として書く）
- 調査資料（根拠）: `spec/research/`
  - `m3-wal.md` WAL の形式とライター
  - `m3-recovery.md` チェックポイント、制御ファイル、リカバリ、クラッシュ試験
  - `m3-mvcc.md` 可視性、コミットの順序、チェックポイントとの排他
  - `m3-tx-semantics.md` ユーザーから見えるトランザクションの意味論（PostgreSQL 17.11 の実機確認つき）
  - `m4-btree.md` §5 B+Tree の分割の WAL（`MAX_BLOCK_REFS` の根拠）
- 迷ったら **PostgreSQL 17 と同じ挙動**を選ぶ。判断が分かれる点は推奨案で進め、第 10 節「確認事項」にまとめた（`QUESTIONS.md` への転記を依頼する）。
- PostgreSQL のソースは REL_17_STABLE を参照し、`PG:<path>` と略す（`https://github.com/postgres/postgres/blob/REL_17_STABLE/<path>`）。「（未検証）」と付けた記述は、ソースや実機で確かめていない。

## 0. M2 との突き合わせと、調査間の食い違いの決定

### 0.1 M2 がすでに持っているもの（M3 で作り直さない）

M2 は M3 の調査の推奨を大きく前倒しした。M3 の作業はそれを前提にする。

| 機能 | M2 の状態 | M3 で行うこと |
|---|---|---|
| MVCC（xmin/xmax、64 ビット XID、cmin/cmax 分離、可視性判定） | 実装済み（m2 §3.5、§6.6） | 変更しない（ヒントビットも M3 では立てない。D7） |
| コミットログ `pg_xact/` | 実装済み。チェックポイントと停止時に fsync | WAL のコミット / アボートレコードの REDO で再構成する経路を足す |
| 単一ライターロック | 実装済み（`lock_timeout` つき） | FIFO 化、キャンセル・`statement_timeout`・停止要求で待ちを中断、ブロック状態の観測 |
| 制御ファイル（2 スロット） | 実装済み。`checkpoint_lsn` / `redo_lsn` は予約 | 使い始める。`format_version` を 2 に上げる（D25） |
| チェックサム付き 8KB ページ、`pd_lsn` | `pd_lsn` は常に 0 | WAL の終端 LSN を入れる |
| `WalFlush` トレイト、`set_lsn`、`read_buffer_zeroed`、`extend_to`、`set_recovery_mode`、`CriticalSection` | 口だけ置いてある | 実装して使う |
| チェックポイント | 停止時以外は整合性を保証しない | ファジーチェックポイントにする（D9） |
| 異常終了後の起動 | 拒否（`--ignore-unclean-shutdown` で強行） | クラッシュリカバリを行って起動する。オプションは廃止 |
| トランザクショナルな SET、SET LOCAL、ParameterStatus を RFQ 直前に差分送信、Query 途中の BEGIN が先行文を取り込む | M1 で実装済み（m1 §4.1、§5.4、m1-changes C-15/C-16） | 変更しない（回帰テストだけ足す） |

### 0.2 決定

| # | 論点 | 選択肢（出典） | 決定 | 理由 |
|---|---|---|---|---|
| D1 | M3 の範囲 | 要件の M3（MVCC・clog・単一ライター・WAL）をそのまま作る／M2 の前倒しを前提に WAL とリカバリに絞る | **後者** | MVCC・clog・単一ライターは M2 で実装済み。M3 は WAL・チェックポイント・リカバリ・クラッシュ試験と、残りの意味論（§1.2）に集中する |
| D2 | WAL の物理形式 | PostgreSQL と同じ 8KB の WAL ページ + 継続レコード／WAL ページなし、レコードはセグメントをまたがない（m3-wal §2.1） | **後者** | 読み書きの実装が大幅に減る。古い残骸の識別は `prev` と CRC、セグメントヘッダ、再利用しないセグメントで代替できる |
| D3 | レコードヘッダの XID の幅 | u32 で 24 バイト（m3-wal §2.3。MVCC 資料と要調整と注記）／u64 | **u64。ヘッダは 32 バイト** | M2 の D2 で XID は 64 ビット。下位 32 ビットに切ると REDO で `next_xid` を進められない |
| D4 | `MAX_BLOCK_REFS` | 4（m3-wal §2.3）／32（m4-btree §5.1。分割の連鎖を 1 レコードの全画像で書く） | **32**。あわせて `MAX_RECORD_LEN = 1 MiB`、WAL セグメントの最小を 2 MiB にする | M4 の B+Tree が「未完了分割」を作らない方式を選べるようにする。32 ブロックの全画像（約 263KB）と各ブロックの差分データ（`KEEP_DATA`）が入る大きさを 1 MiB で確保する。レコードはセグメントをまたがないので、最小セグメントは最大レコードの 2 倍にする。ヘッダの `nblocks` は u8 で足りる |
| D5 | ヒープレコードのタプル | PostgreSQL と同じく固定ヘッダを省いて REDO で組み立て直す／タプル全体のバイト列を載せる（m3-wal §2.1） | **タプル全体** | REDO がバイト列のコピーで済み、形式化のコードを 2 か所に持たない。1 レコードあたり 35 バイト程度増えるだけ |
| D6 | clog の WAL | `CLOG_ZEROPAGE` を書く（m3-wal §2.4 の rmgr 表）／書かない（m3-recovery §8、M2 §3.8） | **書かない。clog の rmgr は作らない** | M2 で「ファイルがない・末尾より先のページは全 0」と決めた。clog はコミット / アボートレコードの REDO だけで再構成する |
| D7 | ヒントビット | M3 で立てる（m3-mvcc §6）／立てない（M2 D6） | **M3 でも立てない** | チェックサムが常に有効なので、立てるならヒントだけの変更でも FPI（`XLOG_FPI_FOR_HINT` 相当）を書く必要がある（M2-Q5）。clog はメモリにキャッシュしており、M3 で性能上の必要がない。M5 の VACUUM（凍結に相当する処理）と一緒に入れる。レコード種別だけ予約する |
| D8 | データページのチェックサム | M3 では持たない（m3-wal §2.8）／M2 から常に有効（M2 D7） | **M2 のまま常に有効** | m3-recovery §5.4 も推奨。FPI の画像は書き出し時にチェックサムを入れ直すので WAL 側の扱いは変わらない |
| D9 | チェックポイントの方式 | 書き込みを止める簡易版／PostgreSQL と同じファジー方式（m3-recovery §7.3） | **ファジー。オンラインでは `CHECKPOINT_REDO` レコードを置いてその開始位置を REDO 点にする** | M5 で作り直さずに済む。追加の工数は 1〜2 日。REDO 点に必ず有効なレコードがあるので読み手が単純になる（PG17 と同じ） |
| D10 | コミットとチェックポイントの競合 | 対策なし／`DELAY_CHKPT_START` 相当のゲート（m3-mvcc §4.3） | **コミットゲート（`RwLock`）を置く**。コミットは WAL 挿入から clog 更新まで共有、チェックポイントは REDO 点の決定の間だけ排他 | ゲートがないと「コミットレコードは REDO 点より前なのに、チェックポイントが書いた clog にはまだ COMMITTED がない」状態でクラッシュし、コミットが消える |
| D11 | ページを dirty にする時機 | M2 のとおりガードの Drop 時／`page_mut()` を呼んだ時点 | **`page_mut()` の時点（M2 §6.3 の 5 を変更）** | Drop 時だと「WAL を挿入した（LSN < REDO 点）がまだ dirty でない」隙間にチェックポイントのバッファ走査が入り、そのページを書かずにチェックポイントが完了しうる。PostgreSQL も `MarkBufferDirty` を `XLogInsert` の前に呼ぶ（PG:src/backend/access/transam/README の "Write-Ahead Log Coding"） |
| D12 | XID と OID の永続化 | `XLOG_NEXTOID` レコード（m3-recovery §8）／M2 の制御ファイルへの先取りを続ける | **M2 の先取りを続ける。加えて REDO で見た XID の最大値 + 1 まで `next_xid` を進める** | 実装済みで、制御ファイルの値だけで「使われうる XID・OID の上限」が分かる。REDO の最大値は二重の保険（不変条件の検査にもなる） |
| D13 | リカバリ開始時のデータディレクトリの fsync | 調査には記述なし／PostgreSQL の `SyncDataDirectory` と同じく全ファイルを fsync | **全ファイルとディレクトリを fsync してから REDO する** | `kill -9` の後は、OS のページキャッシュにだけある WAL やページが見える。それを前提に REDO（適用済みと判定して飛ばす）した後で電源が落ちると、飛ばした変更が失われる（PG:src/backend/access/transam/xlog.c の `StartupXLOG` が `SyncDataDirectory` を呼ぶ。未検証: 呼ぶ条件の細部） |
| D14 | REDO でファイルやブロックがない | 黙って飛ばす／PostgreSQL の invalid page の追跡（m3-recovery §4.3） | **追跡する**。後の unlink / truncate の REDO で消し、REDO の終わりに残っていれば起動を拒否する | WAL とファイルの食い違い（本物の破損）を黙って見逃さない |
| D15 | 孤児ファイルの掃除 | リカバリ後にカタログにないファイルを消す（m3-recovery §7.4、m3-tx-semantics §6.2）／しない | **M3 ではしない** | 全データベースのカタログを起動時に読む処理が要り、誤って生きたファイルを消す危険がある。PostgreSQL もしない。0 バイトや中断したトランザクションのファイルが残るだけで害はない（M3-Q5） |
| D16 | DDL と読み取りの競合 | テーブル単位の簡易ロック（m3-mvcc §8）／ロックなし（m3-tx-semantics §5.4） | **ロックなし（M2 のストレージバリアのまま）** | テーブルロックを入れると、単一ライターロックと組み合わさってデッドロックが起きうる（m3-tx-semantics §5.4 の例）。M5 で待ちグラフと一緒に入れる |
| D17 | D13 の残骸の削除時機 | M2 のとおり次のチェックポイントの最後に全部消す／そのチェックポイントの REDO 点より前に積まれたものだけ消す | **後者（unlink サイクル）** | REDO 点より後に積まれた残骸を消すと、そのチェックポイントからの REDO が DROP より前の古いレコードを、同じ relfilenode を再利用した新しいリレーションに当てうる（M2 §5.6 の注記を具体化） |
| D18 | WAL セグメントの再利用 | 名前を変えて再利用（PG の既定）／しない（m3-wal §2.1） | **しない。新しいセグメントは 0 埋めしてから rename で置く** | 古い残骸を有効なレコードと誤認する余地を構造的になくす |
| D19 | リカバリ後の WAL の末尾 | そのまま書き継ぐ／末尾以降を 0 で埋め、後続のセグメントを消す（m3-wal §2.9、m3-recovery §8） | **後者** | 途中まで書かれたレコードの残骸を、次のクラッシュの REDO で誤読しない |
| D20 | FPW の判定の場所 | ロック外で判定してロック内で検証・やり直し（PG）／挿入 Mutex の中で判定（m3-wal、m3-recovery） | **挿入 Mutex の中** | やり直しのループが要らない。M5 で挿入を並列化するときに PG 方式へ移る。そのため API は「(ページ, フラグ, 差分) を登録し、画像を付けるかは WAL 層が決める」形にする |
| D21 | UPDATE の WAL | M2 のとおり 2 ページを別々のラッチで変更／両ページをブロック番号順にラッチして 1 レコード | **後者（M2 §6.5.3 の予告どおり）** | 新版の挿入と旧版の xmax 設定が別レコードだと、間でクラッシュしたときの状態が増える |
| D22 | セーブポイント | ブロック内では 3 つとも `0A000`（m3-tx-semantics §9）／`SAVEPOINT` だけ `0A000`、`RELEASE` / `ROLLBACK TO` は `3B001` | **後者** | セーブポイントは作れないので、`RELEASE x` / `ROLLBACK TO x` は PostgreSQL でも必ず「`savepoint "x" does not exist`」になる。PostgreSQL と完全に一致する |
| D23 | 分離性テストのブロック判定 | 時間で判定／`pg_isolation_test_session_is_blocked(int4, int4[])` を実装（m3-tx-semantics §12.2） | **関数を実装する**。そのために `int4[]` の最小限（テキスト入出力だけ）を足す | 時間による判定は不安定。PostgreSQL と同じ SQL で両方に流せる |
| D24 | タイムアウトとキャンセル | M5 以降／M3（m3-tx-semantics §5.3） | **M3** | ライターロックを持ったまま放置されると全ライターが止まる。救済策（`idle_in_transaction_session_timeout`、キャンセル）を単一ライターと同じ時期に入れる |
| D25 | M2 のデータディレクトリ | 読む／initdb のやり直しを求める（M2 D15） | **制御ファイルの `format_version` を 2 に上げ、1 は起動を拒否する** | M2 のクラスタには WAL がない。M2-Q20 の方針どおり |
| D26 | initdb の書き込み | WAL を書かずに書いて fsync／ブートストラップも WAL を通す | **WAL を通す** | ヒープの書き込み経路を 1 つにできる（「WAL なしで書く」モードを作らない）。最後に停止チェックポイントを書き、そのレコードを制御ファイルが指す |
| D27 | `synchronous_commit` | 実装しない（m3-wal §2.7）／`off` も受け付けて非同期コミット | **SET は受け付けるが、どの値でも同期コミットとして動く** | 値を拒否すると、`SET synchronous_commit = off` を送るツールが失敗する。強い側に倒すので害はない。非同期コミットは clog に `group_lsn` 相当が要り、M6 以降（M3-Q11） |
| D28 | `kill -9` ハーネスのクライアント | `psql` をサブプロセスで呼ぶ／`postgres` クレート | **`postgres` クレート**（M2 で dev-dependency に追加済み） | 依存は増えない |
| D29 | 変異テストのためのスイッチ | なし／本番コードに隠しスイッチ（m3-recovery §9.6） | **`DebugKnobs` を置く**（既定はすべて無効。CLI・設定ファイルからは触れない。テストが `ClusterOptions` で渡す） | ハーネスが壊れを検出できることを確かめるには、本物の経路をわざと壊す必要がある |
| D30 | WAL の書き込み・fsync の失敗 | 再試行／Panic（m3-wal §2.7） | **Panic**（M2 の fsync 失敗と同じ）。クラスタを poison し、サーバは終了コード 3 で終わる。次の起動でリカバリする | Linux の fsync は失敗後に dirty なページを捨てうる |
| D31 | `statement_timeout` の単位 | Query メッセージ全体／文ごと | **文ごと** | PostgreSQL 13 以降と同じ（<https://www.postgresql.org/docs/17/runtime-config-client.html>） |

## 1. M3 の範囲

### 1.1 機能

| 分類 | M3 で対応するもの |
|---|---|
| WAL | REDO のみ。`pg_wal/` の 16 MiB セグメント（initdb で 2 MiB〜1 GiB の 2 の冪を選べる）。レコードはヒープの insert / delete / update、トランザクションのコミット / アボート（削除するファイルの一覧を含む）、リレーションファイルの作成 / 切り詰め、チェックポイント関係、FPI。カタログの変更はヒープのレコードで記録される |
| 耐久性 | コミットごとに WAL を fdatasync（グループコミットは flush の Mutex の取り直しで自然に起きる分だけ）。WAL-before-data。FPW（REDO 点の後の最初の変更でページ全体の画像を載せる。穴は省く） |
| チェックポイント | ファジー。契機は `checkpoint_timeout`（既定 5 分）、REDO 点からの WAL 量（`max_wal_size`、既定 1GB）、`CHECKPOINT` 文、停止、リカバリの終了。書き出しの時間的な分散はしない |
| リカバリ | 起動時に制御ファイル → チェックポイントレコード → REDO 点から WAL の末尾まで REDO → 末尾の片付け → 終了チェックポイント → 接続の受け付け |
| 停止 | M2 の smart（`SIGTERM`）/ fast（`SIGINT`）/ immediate（`SIGQUIT`）。smart と fast は停止チェックポイントを書く。immediate と `kill -9` の後は次の起動でリカバリする |
| クラッシュ試験 | 層 1: `SimVfs` の決定的な障害注入（I/O の N 番目でクラッシュ、未 sync の書き込みの消失・部分的な残存・torn）。層 2: 実プロセスの `kill -9` ハーネス。両方で不変条件 I1〜I12 を検査し、変異テストでハーネス自体を検証する |
| ツール | `yuzhu-waldump`（WAL のレコードを人が読める形で出す）、`yuzhu-initdb --wal-segment-size` |

### 1.2 SQL とセッション（M2 からの追加）

| 分類 | 追加するもの |
|---|---|
| トランザクション特性 | `BEGIN` / `START TRANSACTION` の `READ ONLY` / `READ WRITE` / `[NOT] DEFERRABLE`（受け付けるだけ）、`SET TRANSACTION ...`、`SET SESSION CHARACTERISTICS AS TRANSACTION ...`、設定 `transaction_read_only`・`default_transaction_read_only`・`transaction_isolation`・`default_transaction_isolation` |
| 終了 | `COMMIT AND CHAIN` / `ROLLBACK AND CHAIN`（`END`、`ABORT` も同じ） |
| セーブポイント | `SAVEPOINT x` / `RELEASE [SAVEPOINT] x` / `ROLLBACK TO [SAVEPOINT] x` を構文として受け付け、PostgreSQL と同じ順序でエラーを返す（§6.11.3） |
| タイムアウト・キャンセル | `statement_timeout`（57014）、`lock_timeout`（55P03）、`idle_in_transaction_session_timeout`（FATAL 25P03）、`idle_session_timeout`（FATAL 57P05）、CancelRequest（57014） |
| 関数 | `pg_backend_pid()`、`pg_sleep(float8)`、`pg_isolation_test_session_is_blocked(int4, int4[])` |
| 型 | `void`（2278。`pg_sleep` の戻り値）、`int4[]`（1007。テキスト入出力だけ） |

**M3 でも対応しないもの**: `SAVEPOINT` の実体（サブトランザクション）、`REPEATABLE READ` / `SERIALIZABLE`（`0A000`。M5）、`PREPARE TRANSACTION`（`0A000`）、`transaction_timeout`（PG17 の新設定。`42704`）、`pg_stat_activity`、`pg_current_xact_id()` などの `xid8` 系、`synchronous_commit = off` の非同期動作、ヒントビット、孤児ファイルの掃除。

### 1.3 M3 が保証すること・しないこと

- **保証する**（障害モデルは m3-recovery §9.1）:
  - クライアントが COMMIT の `CommandComplete` を受け取ったトランザクションは、その後どの時点でプロセスが落ちても、電源が落ちても（fsync 済みのデータが残る前提で）、リカバリ後にすべて見える（I1）。
  - コミットを確認していないトランザクションは、全部見えるか全部見えないかのどちらか（I2、I3）。
  - リカバリは冪等で、リカバリ中のクラッシュの後でも同じ結果になる（I9）。
  - 読み込んだページの破損は、FPW で直るもの以外は `XX001` で検出し、黙って返さない（M2 と同じ）。
- **保証しない**: fsync が成功した後のデータの消失（ディスクの故障）、ファイルシステムの破損、`DebugKnobs` を有効にした状態。
- WAL の書き込みか fsync が失敗したら、サーバは直ちに終了する（終了コード 3）。そのとき COMMIT を送っていたクライアントには接続断として見え、コミットされたかどうかは分からない（PostgreSQL と同じ）。

- `wal::redo` は rmgr を知らない。レコードを rmgr ごとの REDO 関数に振り分ける表は `recovery.rs` に置く（heap・txn・smgr_wal・wal::xlog はすべて recovery より下にある）。
- `BufferPool` は `Arc<dyn WalFlush>` を持つ（M2 のまま）。M3 の実装は `wal::Wal` だけ。リカバリ中も同じ `Wal` オブジェクトを使い、モードで動作を変える（§6.3.6）。差し替えの API は作らない。
- yuzhu-core は M3 でも**外部依存なし**。yuzhu-server も新しい依存を足さない。

**コーディング規約（M3 で追加）**:

1. **WAL を書くページ変更の形は 1 つに固定する**（PostgreSQL の README の手順と同じ）: (1) 失敗しうる検査をすべて終える、(2) 対象ページをピンして排他ラッチ（複数なら同じリレーションのブロック番号の小さい順）、(3) `CriticalSection::enter`、(4) `page_mut()` で書き換える（この時点で dirty になる。D11）、(5) `RecordBuilder` に各ページを登録して `wal.insert`、(6) 戻り値の終端 LSN を全ページに `set_lsn`、(7) ガードを Drop、(8) セクションを抜ける。(4)〜(6) の間のエラーは `escalate` で Panic にする。
2. `page_mut()` を呼んだガードを `set_lsn()` なしで Drop したら、デバッグビルドでは panic する（M2 §4.3 の予告どおり）。例外は `page_mut_hint()`（M3 では呼ぶ箇所がない）と、REDO の中で `set_lsn` を呼ぶ経路だけ。
3. `wal.insert` の前後で、ページのラッチ以外のロック（ストレージバリアは除く）を持たない。特にコミットゲートと `proc` の Mutex を持ったまま `wal.insert` を呼ぶのはコミット / アボートだけに限る（§5.9 の順序）。
4. REDO の関数は**決して失敗を飲み込まない**。形式の不正やページとレコードの食い違いは `Severity::Panic` で返し、起動を止める。
5. バイト形式を扱う `wal/record.rs`・`wal/xlog.rs`・`storage/heap/wal.rs`・`storage/smgr_wal.rs`・`txn/xact_wal.rs` に限り、M2 規約 5 の `#![allow(clippy::cast_possible_truncation, clippy::cast_lossless)]` を許す。

## 3. ディスク上の形式

すべてリトルエンディアン。M2 で決めた形式（ページ、タプル、clog、制御ファイルのスロット）は変えない。

### 3.1 データディレクトリ

```
$DATA/
├── YUZHU_VERSION
├── yuzhu.pid
├── global/yuzhu_control     制御ファイル（format_version = 2）
├── base/...
├── pg_xact/
└── pg_wal/                  ★ M3 で使い始める
    ├── 0000000000000001     セグメント（ファイル名 = セグメント番号の大文字 16 進 16 桁）
    ├── 0000000000000002
    └── xlogtemp.<n>         作成中の一時ファイル（起動時に見つけたら消す）
```

### 3.2 LSN とセグメント

- **LSN** は WAL ストリーム上のバイト位置（u64）。セグメント番号 = `lsn / seg_size`、セグメント内の位置 = `lsn % seg_size`。LSN 0 は無効。
- セグメント 0 は使わない。initdb の最初のレコードは `seg_size + SEG_HEADER_SIZE`（16 MiB なら `0x0100_0020`）から始まる（M2 §3.2 の「最初の有効な LSN は 0 より大きい」）。
- `seg_size` は 2 の冪で `2 MiB ≤ seg_size ≤ 1 GiB`（D4）。initdb で決め、制御ファイルの `wal_segment_size` とセグメントヘッダに記録する。起動時に一致しなければ FATAL。
- 表示形式は PostgreSQL と同じ `%X/%X`（上位 32 ビット / 下位 32 ビット。例 `0/1000020`）。

**セグメントヘッダ**（各セグメントファイルの先頭 32 バイト。`SEG_HEADER_SIZE = 32`）:

| オフセット | 型 | フィールド | 値 |
|---|---|---|---|
| 0 | `[u8; 4]` | `magic` | `b"YZWL"` |
| 4 | u16 | `wal_format_version` | 1 |
| 6 | u16 | `flags` | 0（予約） |
| 8 | u64 | `system_identifier` | 制御ファイルと同じ値（別クラスタの WAL の混入を検出） |
| 16 | u64 | `segno` | ファイル名と一致すること |
| 24 | u32 | `segment_size` | 制御ファイルと一致すること |
| 28 | u32 | `crc32c` | オフセット 0〜27 の CRC32C |

- **作成**: `pg_wal/xlogtemp.<segno>` を `CreateNew` で開く → `seg_size` バイトを 0 で書く（1 MiB ずつ）→ ヘッダを書く → `sync_all` → `rename` で正式な名前に → `pg_wal/` を `sync_dir`。0 埋め済みなので、以後の追記は `sync_data` だけでファイル長のメタデータ同期が要らない。
- **削除**: チェックポイントの完了後、REDO 点を含むセグメントより番号の小さいセグメントを消し、`pg_wal/` を `sync_dir` する。削除の失敗は WARNING（正しさに影響しない）。
- 起動時に `xlogtemp.*` が残っていたら消す。

### 3.3 レコードの配置

- 各レコードは 8 バイト境界から始まる。`tot_len` の後ろは次の 8 バイト境界まで 0 で埋める（パディングは `tot_len` に含めない）。
- **レコードはセグメントをまたがない**。挿入位置からセグメントの末尾までに収まらなければ、残りが `RECORD_HEADER_SIZE`（32）以上なら SWITCH レコード（32 バイト）を置き、次のセグメントの `SEG_HEADER_SIZE` の位置から書く。残りが 32 未満なら何も書かない（0 のまま）。
- **終端 LSN**（`end`）= `start + align8(tot_len)`。次のレコードの開始位置は `end` を正規化したもの（`end` がセグメント内で 32 未満の残りしかなければ次のセグメントの先頭 + 32）。ページの `pd_lsn` には `end` を入れる。

**レコードヘッダ**（32 バイト。`RECORD_HEADER_SIZE = 32`）:

| オフセット | 型 | フィールド | 内容 |
|---|---|---|---|
| 0 | u32 | `tot_len` | ヘッダ・ブロック参照・メインデータを含む全体の長さ（パディングを除く）。`32 ≤ tot_len ≤ MAX_RECORD_LEN` |
| 4 | u32 | `crc` | CRC32C。計算順は「本体 `[8, tot_len)` → ヘッダ `[0, 4)`」（PostgreSQL の「本体 → ヘッダ」と同じ考え方） |
| 8 | u64 | `prev` | 直前のレコードの開始 LSN。WAL の最初のレコード（initdb）は 0 |
| 16 | u64 | `xid` | トランザクション ID（64 ビット）。関係なければ 0 |
| 24 | u8 | `rmgr` | リソースマネージャ ID（§3.5） |
| 25 | u8 | `info` | 上位 4 ビット = rmgr ごとの種別、下位 4 ビット = 汎用フラグ（M3 は 0。立っていたら不正） |
| 26 | u8 | `nblocks` | ブロック参照の個数（`0..=MAX_BLOCK_REFS`） |
| 27 | u8 | `reserved` | 0 |
| 28 | u32 | `main_len` | メインデータの長さ |
| 32 | | ブロック参照 × `nblocks` | 下表を順に。整列しない |
| … | `[u8; main_len]` | メインデータ | rmgr ごとの形式（§3.6〜§3.9） |

**ブロック参照**（固定部 24 バイト + 可変部）:

| オフセット | 型 | フィールド | 内容 |
|---|---|---|---|
| 0 | u8 | `block_id` | 0 から連番（参照の並びの位置と一致すること） |
| 1 | u8 | `flags` | `0x01 HAS_IMAGE`、`0x02 HAS_DATA`、`0x04 WILL_INIT`、`0x08 HAS_HOLE`。ほかのビットが立っていたら不正 |
| 2 | u8 | `fork` | `ForkNumber`（M3 は main = 0 だけ） |
| 3 | u8 | `reserved` | 0 |
| 4 | u32 | `spc_oid` | `RelFileLocator` |
| 8 | u32 | `db_oid` | 同上（共有リレーションは 0。M2 §4.3） |
| 12 | u32 | `rel_number` | 同上 |
| 16 | u32 | `block` | ブロック番号 |
| 20 | u32 | `data_len` | 差分データの長さ。`HAS_DATA` でなければ 0 |
| 24 | u16 | `hole_offset` | `HAS_IMAGE` のときだけ。`HAS_HOLE` でなければ 0 |
| 26 | u16 | `hole_length` | 同上 |
| 28 | `[u8; 8192 - hole_length]` | ページ画像 | `HAS_IMAGE` のときだけ。`[0, hole_offset)` と `[hole_offset + hole_length, 8192)` を連結したもの |
| … | `[u8; data_len]` | 差分データ | `HAS_DATA` のときだけ |

- 検査（読み手が不正とみなす条件）: `WILL_INIT` と `HAS_IMAGE` が同時、`HAS_HOLE` なのに `HAS_IMAGE` でない、`hole_offset < 24` または `hole_offset + hole_length > 8192`（`HAS_HOLE` のとき）、`HAS_HOLE` でないのに `hole_offset` / `hole_length` が 0 でない、`HAS_DATA` でないのに `data_len != 0`、全体の長さの合計が `tot_len` と合わない。
- **穴**: ページが「標準の形」（`24 ≤ pd_lower ≤ pd_upper ≤ 8192`）なら `hole_offset = pd_lower`、`hole_length = pd_upper - pd_lower`。長さ 0 なら `HAS_HOLE` を立てない。形が不正なら穴なしで全体を載せる。REDO は穴を 0 で埋めて 8192 バイトに戻す。
- 画像の `pd_checksum` はメモリ上の値のまま（意味を持たない）。REDO で戻したページは、書き出し時にチェックサムが入り直す（M2 §6.4）。

### 3.5 リソースマネージャ

| rmgr | ID | info（上位 4 ビット） | 持ち主 |
|---|---|---|---|
| XLOG | 0 | `0x00 CHECKPOINT_SHUTDOWN`、`0x10 CHECKPOINT_ONLINE`、`0x20 CHECKPOINT_REDO`、`0x30 SWITCH`、`0x40 FPI`、`0x50 NOOP`、`0x60 FPI_FOR_HINT`（予約。M5） | `wal/xlog.rs` |
| XACT | 1 | `0x00 COMMIT`、`0x10 ABORT` | `txn/xact_wal.rs` |
| SMGR | 2 | `0x00 CREATE`、`0x10 TRUNCATE` | `storage/smgr_wal.rs` |
| HEAP | 3 | `0x00 INSERT`、`0x10 DELETE`、`0x20 UPDATE`、`0x30 HOT_UPDATE`（予約）、`0x40 LOCK`（予約。M5）。`0x80 INIT_PAGE` は OR するフラグ | `storage/heap/wal.rs` |

| SEQ | 5 | 予約（M4） | — |

- 未知の rmgr ID・予約の info は、読み手が「不正なレコード」とみなす（= WAL の終わり。M3 のサーバが M4 の WAL を読むことは D15/M2-Q20 により想定しない）。
- `info` が `INIT_PAGE` を含めて 1 バイトに収まるよう、HEAP の種別は上位 4 ビットのうち下位 3 ビット（`0x00`〜`0x70`）だけを使う。

### 3.6 XLOG のメインデータ

**CHECKPOINT_SHUTDOWN / CHECKPOINT_ONLINE**（48 バイト。`nblocks = 0`、`xid = 0`）:

| オフセット | 型 | フィールド | 内容 |
|---|---|---|---|
| 0 | u64 | `redo_lsn` | REDO 点（オンラインなら CHECKPOINT_REDO レコードの開始 LSN。停止なら REDO 点 = 書いた時点の挿入位置） |
| 8 | u64 | `next_xid` | REDO 点の決定後に読んだ `next_xid`（ちょうどの値） |
| 16 | u64 | `oldest_xid` | 3（M5 で使う） |
| 24 | u32 | `next_oid` | REDO 点の決定後に読んだ OID の先取りの上限 |
| 28 | u8 | `kind` | 0 = Shutdown、1 = Online（Periodic / Explicit / WalVolume）、2 = EndOfRecovery |
| 29 | u8 | `flags` | bit0 = full_page_writes |
| 30 | u16 | 予約 | 0 |
| 32 | i64 | `time` | UNIX 秒 |
| 40 | u64 | 予約 | 0 |

- `kind = 0`・`2` のレコードは `info = CHECKPOINT_SHUTDOWN`、`kind = 1` は `CHECKPOINT_ONLINE`。両者が食い違えば不正。
- **CHECKPOINT_REDO / SWITCH**: メインデータなし、`nblocks = 0`（`tot_len = 32`）。
- **FPI**: ブロック参照 1 個以上、すべて `HAS_IMAGE`、メインデータなし。M3 では書く箇所がない（REDO だけ実装する）。M4 の一括構築などで使う。
- **NOOP**: 任意のメインデータ。テストでだけ書く。

### 3.7 XACT のメインデータ

**COMMIT / ABORT**（`16 + 12 × nrels` バイト。`nblocks = 0`、`xid` は正規の XID）:

| オフセット | 型 | フィールド | 内容 |
|---|---|---|---|
| 0 | i64 | `time` | UNIX エポックからのマイクロ秒 |
| 8 | u32 | `nrels` | 後ろに並ぶリレーションの数 |
| 12 | u32 | 予約 | 0 |
| 16 | `[(u32, u32, u32); nrels]` | `rels` | `RelFileLocator`（spc, db, rel）。COMMIT は削除するもの（`pending_unlinks`）、ABORT は作って消すもの（`pending_creates`） |

- `nrels` の上限は「レコードが `MAX_RECORD_LEN` に収まる」こと（約 8.7 万）。超えたら DDL の時点で `54000`（1 トランザクションでそれほど多くのテーブルを作る・消すことは想定しない）。

### 3.8 SMGR のメインデータ

| info | 長さ | 形式 |
|---|---|---|
| `CREATE` | 16 | `spc_oid u32`、`db_oid u32`、`rel_number u32`、`fork u8`、予約 `[u8; 3]` |
| `TRUNCATE` | 20 | 上と同じ 16 バイト + `nblocks u32`（切り詰めた後のブロック数） |

- `xid` は作成・切り詰めを行ったトランザクション（initdb は `Xid::BOOTSTRAP`）。
- M3 で TRUNCATE を出す箇所はない（TRUNCATE 文と VACUUM の切り詰めは M5）。形式と REDO と `smgr.truncate` は M3 で作り、テストする（M5 で WAL 側に手を入れずに済むように）。

### 3.9 HEAP のメインデータとブロック

| 種別 | ブロック | メインデータ |
|---|---|---|
| `INSERT` | blk0 = 対象ページ。`HAS_DATA`（データ = タプル全体のバイト列、`lp_len` バイト）。`INIT_PAGE` なら `WILL_INIT` | 4 バイト: `offnum u16`、`flags u8`（0）、予約 `u8` |
| `DELETE` | blk0 = 対象ページ。データなし | 24 バイト（下表） |
| `UPDATE` | blk0 = 新版のページ（`HAS_DATA` = 新版のタプル全体。`INIT_PAGE` なら `WILL_INIT`）、blk1 = 旧版のページ（新旧が同じページなら省く） | 24 バイト（下表） |

**DELETE のメインデータ**（変更後のヘッダの値をそのまま載せる）:

| オフセット | 型 | フィールド |
|---|---|---|
| 0 | u16 | `offnum` |
| 2 | u16 | `infomask`（変更後） |
| 4 | u16 | `infomask2`（変更後） |
| 6 | u16 | 予約 |
| 8 | u64 | `xmax` |
| 16 | u32 | `cmax` |
| 20 | u32 | 予約 |

**UPDATE のメインデータ**:

| オフセット | 型 | フィールド |
|---|---|---|
| 0 | u16 | `old_offnum` |
| 2 | u16 | `new_offnum` |
| 4 | u16 | `old_infomask`（変更後） |
| 6 | u16 | `old_infomask2`（変更後） |
| 8 | u64 | `old_xmax` |
| 16 | u32 | `old_cmax` |
| 20 | u8 | `flags`（bit0 = SAME_PAGE。blk1 がないことと一致すること） |
| 21 | `[u8; 3]` | 予約 |

- 旧版の `t_ctid` は REDO で `(blk0.block, new_offnum)` にする（メインデータには持たない）。
- タプルの `t_ctid` はタプル本体のバイト列に含まれる（挿入では自分自身、更新の新版も自分自身）。

### 3.10 制御ファイル（M2 §3.2 からの変更）

スロットの形式は変えない。値の意味だけを足す。

| オフセット | フィールド | M3 での値 |
|---|---|---|
| 8 | `format_version` | **2**（1 は「WAL を持たない M2 のクラスタ」として起動を拒否。D25） |
| 32 | `state` | 3 = InCrashRecovery を使い始める |
| 40 | `wal_segment_size` | initdb の値。起動時に検査（2 の冪、2 MiB〜1 GiB） |
| 44 | `flags` | bit0 = full_page_writes = **1**、bit1 = page_checksums = 1 |
| 56 | `checkpoint_lsn` | 最後に完了したチェックポイントのレコードの**開始** LSN |
| 64 | `redo_lsn` | そのチェックポイントの REDO 点 |
| 72 | `next_xid` | M2 と同じ（先取りの上限。停止チェックポイントではちょうどの値） |
| 88 | `next_oid` | M2 と同じ |

- 制御ファイルの書き込みがチェックポイントの**完了点**になる（m3-recovery §2.3）。これより前に落ちれば、前のチェックポイントからリカバリする。WAL のセグメントの削除は必ずこの後。
- `checkpoint_lsn == 0` の制御ファイルは M3 では不正（FATAL）。

## 5. 処理の流れ

### 5.1 ヒープの変更と WAL（D）

```
insert(rel, w, row)
  1. tuple = form_tuple(..)                                    失敗しうる処理はここまで
  2. 挿入先を選ぶ（M2 §6.5.2）。pool.extend はラッチを持たずに呼ぶ
  3. 対象ページを排他ラッチ。入らなければラッチを外して 2 へ
  4. init = page.is_new()
  5. cs = CriticalSection::enter(pool)
       if init: page_mut().init_heap()
       off = page_mut().add_item(tuple)（ctid = (blk, off) を書き込んでから）
       rec = RecordBuilder::new(Heap, HEAP_INSERT | (init ? INIT_PAGE : 0), w.xid)
       b = rec.register_block(tag, guard.page(), STANDARD | (init ? WILL_INIT : NONE))
       rec.block_data(b, タプルのバイト列); rec.main_data(offnum = off)
       end = wal.insert(rec).map_err(|e| cs.escalate(e))?.end
       guard.set_lsn(end.0)
     ガードを Drop → cs を Drop

delete(rel, w, snap, tid)
  1. ピン + 排他ラッチ。ヘッダを読み satisfies_update（M2 §6.5.3）。Ok でなければ結果を返す
  2. cs: xmax / cmax / infomask / infomask2 を書き換え → HEAP_DELETE（blk0 = ページ、main = 変更後の値）→ set_lsn

update(rel, w, snap, tid, new_row)
  1. new = form_tuple(.., updated = true)
  2. 旧ページを排他ラッチ → satisfies_update。Ok でなければ返す
  3. 旧ページに入るなら: cs の中で新版を置き、旧版に xmax / cmax / infomask / ctid を書く
       → HEAP_UPDATE（blk0 = 同じページ、SAME_PAGE、blk1 なし）→ set_lsn。終わり
  4. 入らなければ旧ページのラッチを外す。M2 §6.5.2 の手順で新版の置き場所（ブロック N）を決めてピンする
     （pool.extend はラッチを持たずに呼ぶ）。ラッチはまだ取らない
  5. 旧ページ（ブロック O）と N を、ブロック番号の小さい順に排他ラッチする
  6. 旧版のヘッダを読み直して、手順 2 と同じ状態であることを確かめる（単一ライターなので変わらない。
     変わっていたら内部エラー XX000）。N に入らなければ（同上、起きない）両方のラッチを外して 4 へ
  7. cs: N を（is_new なら初期化して）新版を置く → 旧版に xmax / cmax / infomask / ctid = (N, new_off)
       → HEAP_UPDATE（blk0 = N（INIT_PAGE なら WILL_INIT）、blk1 = O、main）→ 両方に set_lsn
```

- ラッチの順序は §5.9 の 4（同じリレーションのブロック番号の小さい順）。N == O にはならない（手順 3 で処理済み）。
- `WriteCtx.xid` がレコードヘッダの `xid` になる。

### 5.2 文の実行（Session。M2 §5.2 からの変更）

```
execute_simple(sql)
  0. interrupts.clear_cancel()
  ├─ 文ごとに:
  │   a. interrupts.set_statement_deadline(statement_timeout > 0 ? now + statement_timeout : None)
  │   b. Failed 状態なら ROLLBACK / COMMIT / ROLLBACK TO 以外は 25P02（ROLLBACK TO は §6.11.3）
  │   c. トランザクション制御・SET・SHOW・SAVEPOINT 系 → §6.11
  │   d. 書き込む文（INSERT / UPDATE / DELETE / CREATE TABLE / DROP TABLE）:
  │        読み取り専用のトランザクションなら 25006（ライターロックを取る前に判定する）
  │        txn.writer が None なら txn_mgr.begin_write(session_id, &WaitCtl { lock_timeout, interrupts })
  │   e. 以降は M2 §5.2 の手順 2〜10 と同じ（スナップショット、実行、CCI、暗黙トランザクションの終了）
  │      スナップショットを取った文を実行したら txn_snapshot_taken = true（SET TRANSACTION ISOLATION の判定用）
  │   f. interrupts.set_statement_deadline(None)
  └─ M2 と同じ
```

- 書き込む文の判定は**生のパース木の文の種類**で行う（アナライズより前。m3-tx-semantics §5.1）。

### 5.3 コミットとアボート（M2 §5.3 からの変更）

```
commit(txn)                                       ※ ストレージバリアを持たない状態で呼ぶ
  if let Some(xid) = txn.xid:
     1. txn_mgr.commit(xid, &txn.pending_unlinks):
          g = commit_gate.read()                              ← D10
          ins = wal.insert(XACT_COMMIT { time, rels = pending_unlinks }, xid)
          wal.flush(ins.end)                                  ← DebugKnobs::skip_commit_flush で省ける
          proc の Mutex: clog.set_status(xid, Committed) → running から外す
          g を解放
        どの失敗も Severity::Panic（クラスタを poison。クライアントには FATAL）
     2. txn.catalog_dirty なら cluster.invalidate_all_catalog_caches()
     3. pending_unlinks があれば exclusive_barrier の下で unlink_storage（M2 と同じ。WAL は手順 1 のレコードで済み）
     4. writer を解放
  txn をリセット

abort(txn)
  if let Some(xid) = txn.xid:
     1. txn_mgr.abort(xid, &txn.pending_creates):
          ins = wal.insert(XACT_ABORT { time, rels = pending_creates }, xid)
          pending_creates が空でなければ wal.flush(ins.end)
          proc の Mutex: clog.set_status(xid, Aborted) → running から外す
     2. pending_creates があれば exclusive_barrier の下で unlink_storage
     3. writer を解放
  txn をリセット
```

- **順序の根拠**（m3-tx-semantics §5.2、m3-mvcc §4.3）: WAL の永続化 → clog → 実行中一覧 → ライターロックの解放 → `CommandComplete`。clog と実行中一覧の順を逆にすると、可視性判定の「先にスナップショット、後で clog」の前提が崩れる。実行中一覧とロックの順を逆にすると、次のライターが直前のコミットを見ないスナップショットで更新する。
- コミットで削除するファイルは、コミットレコードが永続化した**後**に消す。クラッシュしても REDO が同じ一覧で消す。
- アボートで作ったファイルを消すときは、アボートレコードを先に flush する（消した後でクラッシュしてもレコードが残り、REDO が再作成したファイルをまた消す）。flush しないと REDO が SMGR_CREATE で作り直し、孤児になる（害はないが避けられるので避ける）。
- `WriterGuard` の Drop の安全網（M2 §4.5）は WAL を書かない（Drop で I/O しない規約）。メモリ上でアボートするだけで、クラッシュ時の暗黙のアボートと同じ扱いになる。
- 読み取りだけのトランザクション（XID なし）は WAL を何も書かず、fsync もしない。

### 5.4 DDL（M2 §5.4 からの変更）

```
CREATE TABLE（ライターロックとストレージバリアを持った状態）
  1〜4. M2 と同じ（OID とファイルの存在の確認）
  5. w = txn.write_ctx()?; storage.create_storage(&w, locator)
       → smgr_wal::log_and_create: SMGR_CREATE を挿入（flush しない）→ smgr.create（親ディレクトリを sync_dir）
     txn.pending_creates に積む
  6. catalog.create_table(&w, ..)（カタログの行はヒープのレコードで記録される）
  7. txn.catalog_dirty = true

DROP TABLE: M2 と同じ。ファイルはコミット時（§5.3 の手順 3）に消す。WAL はコミットレコードの rels
```

- SMGR_CREATE を flush しなくてよい理由: そのリレーションのページを書き出すには、ページの LSN（> SMGR_CREATE の LSN）まで WAL を flush する必要がある（WAL-before-data）。ファイルだけ残ってレコードがないのは孤児で害はない。レコードだけ残ってファイルがなければ REDO が作る。

### 5.5 起動とクラッシュリカバリ（R）

```
Cluster::open(vfs, opts)
  1. yuzhu.pid のロック、YUZHU_VERSION の検査（M2 と同じ）
  2. 制御ファイルを開いて検査（format_version = 2、wal_segment_size、そのほか M2 と同じ）
  3. pg_wal/xlogtemp.* を消す
  4. recovery::startup(vfs, control, stack_cfg):
     a. reader = WalReader::open(control.checkpoint_lsn) で 1 レコード読む。
        読めない・XLOG のチェックポイントレコードでない → FATAL XX001
          "could not locate a valid checkpoint record at %X/%X"
        ckpt.redo != control.redo_lsn → FATAL XX001 "checkpoint record is inconsistent with control file"
     b. clean = control.state == ShutDown && ckpt.kind ∈ {Shutdown, EndOfRecovery} && reader.next() == None
     c. clean なら:
          wal = Wal::open_at(ckpt_rec.end, ckpt_rec.start)、stack = StorageStack::new(.., wal, control.next_xid)
          next_xid = control.next_xid、next_oid = control.next_oid
     d. clean でなければ（クラッシュリカバリ）:
          ログ "database system was interrupted; last known up at <time>"
          （state == ShutDown なのに後ろに WAL がある場合は WARNING を足す）
          1) control.update(|c| c.state = InCrashRecovery)
          2) datadir::sync_data_directory(vfs)                         ← D13
          3) wal = Wal::open_for_recovery、stack = StorageStack::new(.., wal, max(control.next_xid, ckpt.next_xid))
             stack.smgr.set_recovery_mode(true)
          4) ctx = RedoCtx { pool, smgr, ext: Arc<Clog>, invalid, next_oid = max(control.next_oid, ckpt.next_oid), knobs }
          5) reader = WalReader::open(ckpt.redo)。ログ "redo starts at %X/%X"
          6) stats = wal::redo::run_redo(ctx, wal, reader, recovery::dispatch, ..)
                各レコード: max_xid = max(max_xid, rec.xid) → dispatch → wal.note_replayed(rec.end)
          7) ctx.invalid.check_empty()?                                  ← D14
          8) (end, reason) = reader.end_of_wal()。ログ "redo done at %X/%X"（最後のレコードの開始）と終わりの理由
          9) wal.finish_recovery(end, reader.last_record_start())        ← D19
         10) smgr.set_recovery_mode(false)
         11) next_xid = max(control.next_xid, ckpt.next_xid, max_xid + 1)、next_oid = ctx.next_oid
             control.update(|c| { c.next_xid = max(c.next_xid, next_xid); c.next_oid = max(c.next_oid, next_oid) })
         12) clog.load_page_for(next_xid)
     e. StartupOutcome を返す
  5. TxnManager（next_xid）、OidAllocator（control.next_oid）、SharedCatalogStore などを作る（M2 と同じ）
  6. クラッシュリカバリをしたなら checkpoint::run(EndOfRecovery) を完了まで待つ
     （REDO で dirty になったページと clog が書かれ、制御ファイルの state が InProduction になる）
  7. clean なら control.update(|c| c.state = InProduction)
  8. 共有カタログを読めることを確かめる。チェックポインタスレッドを起動する（background_checkpointer のとき）
  ログ "database system is ready to accept connections"
```

- クラッシュ時に実行中だった XID には何も書かない（PostgreSQL と同じ暗黙のアボート。m3-recovery §6.5）。リカバリ後の実行中一覧は空なので、clog が COMMITTED でない XID はすべて中断扱いになる（M2 §6.6 の判定そのまま）。
- REDO の途中でクラッシュしても、制御ファイルは `InCrashRecovery` のまま前のチェックポイントを指しているので、次の起動で同じ REDO をやり直す（冪等。I9）。
- REDO の失敗（不正なレコード以外の、ページとレコードの食い違いや I/O エラー）は `Cluster::open` のエラー（FATAL）になり、サーバは終了コード 1 で終わる。データディレクトリは変えない（手で調べられるように）。

### 5.6 チェックポイント（E。M2 §5.6 を置き換える）

```
checkpoint::run(parts, kind)
  lock checkpoint_lock
  0. kind == Periodic かつ「前回のチェックポイントの後に、チェックポイント関係以外のレコードがない」
     （insert_lsn == 前回のチェックポイントレコードの end を正規化したもの）なら、何もせず skipped を返す
  1. REDO 点を決める
     Periodic / Explicit / WalVolume（オンライン）:
        g = txn.commit_gate_exclusive()                ← 進行中のコミットの clog 更新が終わるのを待つ（D10）
        redo = wal.begin_checkpoint_online()           ← CHECKPOINT_REDO を挿入し、REDO 点を更新（以後の FPW の判定に効く）
        cycle = smgr.begin_unlink_cycle()
        g を解放
     Shutdown / EndOfRecovery（他に書き手がいない）:
        redo = wal.begin_checkpoint_quiet(); cycle = smgr.begin_unlink_cycle()
  2. (next_xid, xid_limit) = txn.xid_counters()、next_oid = oids.limit()       ← REDO 点の後に読む
  3. clog.flush()                                       ← DebugKnobs::skip_clog_flush_at_checkpoint で省ける
  4. b = txn.statement_barrier()
     pool.flush_all_for_checkpoint()                    開始時点で dirty なページだけ。各ページの書き出しは
                                                        flush_frame（page_lsn まで WAL を flush してから書く）
     b を解放
  5. smgr.sync_pending()                                失敗は Panic
  6. rec = CheckpointRecord { redo, next_xid, oldest_xid: 3, next_oid, kind, full_page_writes, time }
     ins = wal.insert(rec.builder()); wal.flush(ins.end)
  7. Online / EndOfRecovery:
        control.update(|c| { c.checkpoint_lsn = ins.start; c.redo_lsn = redo;
                             c.next_xid = max(c.next_xid, xid_limit); c.next_oid = max(c.next_oid, next_oid);
                             c.state = InProduction })
     Shutdown:
        control.update_for_shutdown(|c| { c.checkpoint_lsn = ins.start; c.redo_lsn = redo;
                                          c.next_xid = next_xid; c.next_oid = next_oid; c.state = ShutDown })
                                                        ← ここがチェックポイントの完了点
  8. smgr.finish_pending_unlinks(cycle)                 失敗は WARNING
  9. wal.remove_segments_before(redo)                   失敗は WARNING
 10. 前回のチェックポイントレコードの end を覚える（手順 0 用）
```

- **なぜ正しいか**（m3-recovery §2.3）: REDO 点 R より前のレコードの変更は、手順 3〜5 ですべて永続化される（clog はコミットゲートにより、R より前のコミットレコードに対応するビットがすべて手順 3 の時点でメモリに入っている）。R より後の変更は書かれたかどうか分からないが、REDO がページの LSN で判定する。手順 4 の書き出しで torn になったページは、R の後の最初の変更に FPI があるので直る。手順 7 より前に落ちれば、前のチェックポイントからリカバリする（WAL はまだ消していない）。
- 手順 2 の値は REDO 点の後に読むので、R より前のレコードに現れる XID はすべて `next_xid` より小さい。
- 停止時（`Shutdown`）は M2 と同じく全セッションが終わった後で呼ぶ。
- **WAL 量の契機**: チェックポインタは 1 秒ごとに起き、`now - last >= checkpoint_timeout` なら `Periodic`、`wal.bytes_since_redo() >= max_wal_size` なら `WalVolume` で `run` を呼ぶ。
- `CHECKPOINT` 文はトランザクションブロックの中でも実行でき（PostgreSQL と同じ。m3-tx-semantics の実機 #38）、完了を待って `CHECKPOINT` を返す。読み取り専用のトランザクションでも実行できる（未検証: PG17 の `ClassifyUtilityCommandAsReadOnly`）。

### 5.7 停止（M2 §5.7 からの変更）

- smart / fast の手順は M2 と同じ。`cluster.shutdown()` の停止チェックポイントが `CHECKPOINT_SHUTDOWN` レコードを書く。
- immediate（`SIGQUIT`）と `kill -9`、Panic による終了の後は、次の起動でクラッシュリカバリを行う（M2 の「起動を拒否」はなくなる）。
- `--ignore-unclean-shutdown` は削除する（指定したら「不明なオプション」でエラー）。

### 5.8 initdb（M2 §5.8 からの変更）

```
bootstrap::initdb(vfs, opts)
  1〜2. M2 と同じ（ディレクトリ、global/ base/ base/1/ pg_xact/ pg_wal/、YUZHU_VERSION）
  2a. system_identifier を決める。wal = Wal::initialize(vfs, WalConfig { segment_size: opts.wal_segment_size, .. })
  2b. 制御ファイルはまだ書かない（M2 と同じく、最後に書くことで「initdb が完了した」印にする）
  3. template1 のブートストラップ（M2 と同じ）。ファイルの作成は smgr_wal::log_and_create（xid = BOOTSTRAP）、
     行の挿入はヒープの WAL を通す（D26）
  4. 停止チェックポイントに相当する手順を直接行う: 全バッファを書き出す（WAL-before-data）→ clog.flush →
     smgr.sync_pending → CHECKPOINT_SHUTDOWN（redo = 挿入位置、next_xid = 3、next_oid = 16384）を挿入して flush
     （--no-sync なら sync を省く。WAL の flush も sync を省く）
  5〜6. base/1/YUZHU_VERSION、base/1 を base/4 と base/5 にコピー（M2 と同じ。ファイルは手順 4 で書き出し済み）
  7. 制御ファイルを書く（state = ShutDown、checkpoint_lsn = 手順 4 のレコードの start、redo_lsn、
     wal_segment_size、flags = 0b11、next_xid = 3、next_oid = 16384、format_version = 2）
```

- コピーした template0 / postgres のページの LSN は template1 の WAL の位置を指すが、すべて停止チェックポイントの REDO 点より前なので、以後の最初の変更で FPI が付く。コピー自体は WAL に記録しない（M5 の CREATE DATABASE は「チェックポイント → コピー → WAL レコード → チェックポイント」。M2 §6.9.3）。

### 5.9 ロックの順序（M2 §5.9 に追加）

| 順 | ロック | 規則 |
|---|---|---|
| 1 | ライターロック | M2 と同じ。待ちは FIFO（§6.6.3） |
| 2 | `checkpoint_lock` | M2 と同じ |
| 3 | ストレージバリア | M2 と同じ |
| 3a | ★ コミットゲート（`TxnManager.commit_gate: RwLock<()>`） | コミット / アボートは共有で、WAL の挿入から clog の更新と実行中一覧からの削除まで持つ。チェックポイントは手順 1 だけ排他で持つ。**ページのラッチを持ったまま取らない**。チェックポイントはゲートを持ったまま `proc` を取らない（手順 2 はゲートの解放後） |
| 4 | コンテンツラッチ | M2 と同じ。M3 の UPDATE は 2 つのページを同じリレーションのブロック番号の小さい順に取る |
| 5 | リレーション拡張ロック | M2 と同じ |
| 6 | マッピング表のパーティション | M2 と同じ |
| 6a | ★ WAL の flush 用 Mutex（`Wal.flush_lock`） | 持ったまま I/O（セグメントの作成、write、sync）をする。中で挿入 Mutex を短く取る（バッファの取り出し）。挿入 Mutex を持ったまま flush 用 Mutex を取ってはいけない |
| 6b | ★ WAL の挿入 Mutex（`Wal.insert`） | I/O をしない。ページのラッチを持ったまま取ってよい（規約 1 の手順 5） |
| 7 | 葉のロック | M2 の一覧に、`Wal` の `mode`、`InvalidPages`、smgr の unlink サイクルを足す。例外（葉から葉へ取ってよい組）は M2 の 3 つに加え、**コミットゲート（共有）→ proc → Clog の内部**（コミット / アボートの手順 1） |

- `wal.insert` が WAL バッファの閾値を超えたときに呼ぶ `flush` は、挿入 Mutex を外した後で、ページのラッチを持ったまま呼ばれうる（ラッチ → flush 用 Mutex → 挿入 Mutex の順なので矛盾しない）。
- flush 用 Mutex を持つ者は、ゲート・ラッチ・ライターロックを待たない。コミットはゲートの共有を持ったまま flush を待つが、flush の持ち主はゲートを待たないので、チェックポイントの排他待ちと合わせてもデッドロックしない。

## 6. モジュールごとの仕様

### 6.1 util/crc32c（W1）

- M2 の実装（反転多項式 `0x82F63B78`、初期値 `0xFFFF_FFFF`、最後にビット反転）を、`const fn` で作る 8 × 256 の表による slice-by-8 にする（m3-wal §2.10）。`unsafe` は使わない。
- API: `pub fn crc32c(data: &[u8]) -> u32`、`pub fn crc32c_append(state: u32, data: &[u8]) -> u32`（反転前の状態を続ける）、`pub fn crc32c_finish(state: u32) -> u32`、`pub const CRC32C_INIT: u32`。M2 の `crc32c` の値は変えない（制御ファイルの互換）。
- テスト: `crc32c(b"123456789") == 0xE306_9283`、ビットごとの素朴な実装との一致（proptest）、分割して `append` しても一括と一致。

### 6.2 vfs の SimVfs（B）

M2 §4.3 の API に次を足す。

```rust
impl SimVfs {
    /// これまでに行った I/O 操作の数（Read / Write / Sync / SyncDir / Open / Remove / Rename / SetLen を数える）
    pub fn op_count(&self) -> u64;
    /// sync_dir を成功扱いにして何もしない（変異テスト用）
    pub fn set_ignore_sync_dir(&self, on: bool);
}
pub enum FaultOp { /* M2 の値 */ Any }
pub enum FaultEffect {
    /* M2 の値 */
    /// この操作の直前で「ディスクを凍結」する。この操作とそれ以降の操作はすべて EIO を返す。
    /// テストは続けて Cluster::abandon と crash(mode) を呼ぶ
    CrashFreeze,
}
pub enum CrashMode {
    DropUnsynced,
    TornSectors { sector: usize, keep_probability: f64 },  // sector = 1 なら任意のバイト境界
    KeepAll,
    /// 未 sync の各操作を独立に確率 p で残す（順序の入れ替わりも再現される）
    RandomSubset { keep_probability: f64 },
}
```

- `FaultRule { op: Any, nth: Some(n), effect: CrashFreeze }` で「n 番目の I/O の直前でクラッシュ」を表す。操作の番号は `SimVfs` の生成（または `crash` で作った新しいインスタンス）からの通し番号。
- `TornSectors` / `RandomSubset` はファイルの内容だけでなく、未 `sync_dir` のディレクトリ操作（作成・削除・rename）にも同じ確率で適用する（M2 の模型の延長）。
- 決定性: 乱数はシードから SplitMix64。同じシード・同じ操作列なら同じ結果になる。

### 6.3 wal（W1、W2）

#### 6.3.1 RecordBuilder とエンコード

- `register_block` は `(tag, page, flags)` と空の差分データを記録する。`block_data` は同じ id に追記する。同じ `tag` を 2 回登録したら debug_assert で落とす。
- エンコードは `Wal::insert` の中（挿入 Mutex の中）で行う。各ブロックについて:
  - `need_image = FORCE_IMAGE || (!NO_IMAGE && !WILL_INIT && full_page_writes && page.lsn() <= redo)`
  - `need_image` なら `HAS_IMAGE`。`STANDARD` かつ `page.hole_range()` が Some なら穴を省いて `HAS_HOLE`
  - 差分データは `!need_image || KEEP_DATA` かつ長さ > 0 のときだけ載せる（`HAS_DATA`）
  - `WILL_INIT` なら `WILL_INIT` を立てる
- 判定に使う `page.lsn()` は**変更前の LSN**（呼び出し側は `set_lsn` を `insert` の後に呼ぶので、`insert` の時点のページヘッダの LSN は前回の値のまま）。画像は**変更後**の内容。
- `tot_len > MAX_RECORD_LEN` は内部エラー（クリティカルセクションの中なので Panic に昇格する）。

#### 6.3.2 挿入（writer.rs）

```
insert(rec):
  if mode != Writing: 内部エラー
  if poisoned: Panic
  lock insert
    redo = state.redo
    bytes = encode(rec, redo, prev = state.prev_start)      CRC まで計算する
    pos = state.insert_pos（正規化済み）
    if bytes.len() > seg_end(pos) - pos:
        if seg_end(pos) - pos >= 32: SWITCH（prev = state.prev_start）を pos に置き、prev_start = pos
        バッファに seg_end(pos) まで 0 を足す。次のセグメントのヘッダ領域（32 バイト）も 0 で足す
        pos = 次のセグメントの先頭 + 32
    bytes の prev を state.prev_start に書き直して CRC を計算し直す（SWITCH を置いた場合）
    バッファに bytes とパディングを足す
    start = pos; end = pos + align8(tot_len)
    state.prev_start = start; state.insert_pos = normalize(end)
  unlock
  if バッファの未 flush 量 >= WAL_BUFFER_FLUSH_THRESHOLD: self.flush(end)
  return Inserted { start, end }
```

- WAL バッファは「`buf_base` から始まる LSN の連続した範囲」を表す `Vec<u8>`。セグメントのヘッダ領域にあたるバイトは 0 のプレースホルダで、flush はそこを書かない（ヘッダはセグメントの作成時に書いてある）。
- 実装上の注意: SWITCH の要否は `prev` の確定前に分かるので、「先に位置を決めてから prev を書き CRC を計算する」順にすれば計算し直しは要らない。

#### 6.3.3 flush

```
flush(upto):
  if flushed >= upto: return Ok
  if upto > insert_lsn: 内部エラー
  lock flush_lock
    if flushed >= upto: return Ok                ← 待つ間に他者が flush 済み（素朴なグループコミット）
    lock insert: (base, bytes) = (buf_base, mem::take(buf)); buf_base = base + bytes.len(); unlock
    bytes をセグメントごとに分け、各セグメントについて:
        ファイルを開く（なければ §3.2 の手順で作る）
        ヘッダ領域を除いて write_all_at
        sync_data
    flushed.store(base + bytes.len())
  失敗したら poisoned = true、Severity::Panic（58030 "could not write to WAL segment ..."／"could not fsync ..."）
```

- **すでに永続化したバイトは書き直さない**（WAL ページがないので、末尾のページを書き直す必要がない）。
- 開いたセグメントのハンドルは `FlushState` に 1 つ（現在のもの）だけ持つ。

#### 6.3.4 REDO 点と FPW

- `begin_checkpoint_online`: 挿入 Mutex の中で CHECKPOINT_REDO を挿入し、その `start` を `state.redo` と `redo`（Atomic）に入れる。以後の `insert` は新しい REDO 点で FPW を判定する。
- `begin_checkpoint_quiet`: 挿入 Mutex の中で `redo = insert_pos` にする。
- `full_page_writes = false`（`DebugKnobs::disable_full_page_writes`）は変異テストでだけ使う。

#### 6.3.5 reader

```
next():
  loop:
    if seg_end(pos) - pos < 32: pos = 次のセグメントの先頭 + 32（セグメントを開き直す）
    セグメントを開く。ない → 終わり（MissingSegment）。ヘッダが不正（magic・CRC・system_id・segno・size）→ 終わり（BadSegmentHeader）
    ヘッダ 32 バイトを読む。tot_len == 0 → 終わり（ZeroLength）
    tot_len < 32 または > MAX_RECORD_LEN → 終わり（BadHeader）
    pos + tot_len > seg_end(pos) → 終わり（CrossesSegment）
    残りを読み、decode_record（CRC、ブロック参照の整合）。失敗 → 終わり
    prev_start が Some で rec.prev != prev_start → 終わり（PrevMismatch）
    prev_start = Some(pos); last_record_start = pos
    if SWITCH: pos = 次のセグメントの先頭 + 32; include_switch なら返す; continue
    pos = normalize(rec.end); return Some(rec)
```

- 「終わり」になったら `end_of_wal = (その位置, 理由)` を記録して `Ok(None)` を返す。以後の `next` も `Ok(None)`。
- `MissingSegment` のときの `end_of_wal` は「次のセグメントの先頭 + 32」（そのセグメントは書き込み時に作られる）。
- クラッシュリカバリでは「末尾」と「破損」を区別しない（PostgreSQL と同じ。m3-recovery §4.2）。

#### 6.3.6 リカバリモードと finish_recovery

- `open_for_recovery` の `Wal` は `insert` を内部エラーで拒否し、`flush_to(lsn)` は `lsn <= replayed` なら Ok（REDO で書いたページの LSN は、その時点まで読んだ WAL の位置を超えない。D13 によりその WAL は fsync 済み）、超えていれば内部エラー（Panic）。
- `finish_recovery(end, last_start)`:
  1. `end` のセグメントが存在すれば、`[end, seg_end)` を 0 で上書きして `sync_data`（D19）。存在しなければ何もしない（書き込み時に作る）。
  2. `end` のセグメントより番号の大きいセグメントをすべて消し、`pg_wal/` を `sync_dir`。
  3. `insert_pos = end`、`prev_start = last_start`、`buf_base = end`、`flushed = end`、`redo = チェックポイントの REDO 点`（終了チェックポイントで更新される）にして、書き込みモードに切り替える。

### 6.4 REDO（W2 と各 rmgr の持ち主）

#### 6.4.1 骨格（wal/redo.rs、W2）

- REDO は単一スレッドで、ページはバッファプールを通して読み書きする（追い出しも普通に起きる）。
- `run_redo` の各レコード: `on_record(rec)`（統計と `max_xid`）→ `dispatch(ctx, rec)` → `wal.note_replayed(rec.end)`。dispatch のエラーはそのまま返す（Panic）。
- `assert_no_pins()` を 1000 レコードごとと最後に呼ぶ（REDO 関数のピン漏れの検出）。

#### 6.4.2 rmgr の振り分け（recovery.rs、R）

| rmgr | 関数 |
|---|---|
| Xlog | `wal::xlog::redo` |
| Xact | `txn::xact_wal::redo` |
| Smgr | `storage::smgr_wal::redo` |
| Heap | `storage::heap::wal::redo` |

#### 6.4.3 read_buffer_for_redo（W2）

```
read_buffer_for_redo(ctx, rec, id):
  blk = rec.blocks[id]
  if blk.image.is_some():
      buf = pool.read_buffer_zeroed(blk.tag)           ← ファイルやブロックがなければ smgr が作る / 伸ばす（リカバリモード）
      g = buf.write(); page_mut() に画像をコピー; set_lsn(rec.end) → Restored
  if blk.will_init:
      buf = pool.read_buffer_zeroed(blk.tag) → NeedsRedo(buf)        ← page_lsn の判定はしない（常に初期化して適用）
  if !smgr.exists(rel, fork) || blk.block >= smgr.nblocks(rel, fork):
      invalid.record(rel, fork, block) → NotFound
  buf = pool.read_buffer(blk.tag)                      ← 検査に失敗したら Panic（FPW があれば起きないはずの破損）
  if !knobs.redo_ignore_page_lsn && buf.read().lsn() >= rec.end: Done
  NeedsRedo(buf)
```

- `NeedsRedo` を受けた REDO 関数は、`buf.write()` で排他ラッチを取り、変更して `set_lsn(rec.end)` する（クリティカルセクションは要らない。REDO のエラーはもともと Panic）。

#### 6.4.4 各 rmgr の REDO

| レコード | REDO |
|---|---|
| XLOG `CHECKPOINT_*` | `ctx.next_oid = max(ctx.next_oid, rec.next_oid)`（`next_xid` は REDO ループの `max_xid` と §5.5 の手順 d-11 で扱う） |
| XLOG `CHECKPOINT_REDO`、`NOOP` | 何もしない |
| XLOG `FPI` | 各ブロックを `read_buffer_for_redo`（必ず Restored） |
| XACT `COMMIT` | `clog.set_status_redo(xid, Committed)`。`rels` の各リレーションについて `pool.drop_relation_buffers(rel)` → `smgr.unlink(rel)`（なければ無視）→ `invalid.forget_relation(rel)` |
| XACT `ABORT` | `clog.set_status_redo(xid, Aborted)`。`rels` について COMMIT と同じ削除 |
| SMGR `CREATE` | ファイルがなければ `smgr.create`（D13 の 0 バイトの残骸があれば何もしない） |
| SMGR `TRUNCATE` | `pool.drop_relation_buffers_from(rel, fork, n)` → `smgr.truncate(rel, fork, n)`（ファイルがなければ無視）→ `invalid.forget_from(rel, fork, n)` |
| HEAP `INSERT` | blk0 が `NeedsRedo` なら: `INIT_PAGE` なら `init_heap()`。`add_item(data)` の戻り値が `offnum` と一致しなければ Panic（M2 は行ポインタを再利用しないので常に末尾に入る）→ `set_lsn` |
| HEAP `DELETE` | blk0 が `NeedsRedo` なら: `offnum` のタプルのヘッダに `xmax`・`cmax`・`infomask`・`infomask2` を書く → `set_lsn` |
| HEAP `UPDATE` | 新ページ（blk0）が `NeedsRedo` なら: 必要なら初期化し、新版を `add_item`（`new_offnum` と一致）。`SAME_PAGE` ならそのまま旧版も更新する。旧ページ（blk1、別ページのとき）が `NeedsRedo` なら旧版のヘッダに `old_*` と `ctid = (blk0.block, new_offnum)` を書く。各ページに `set_lsn` |

- `Restored` / `Done` / `NotFound` のブロックには何もしない（メインデータは使わない）。
- REDO 中の smgr の unlink も D13 の方式（0 バイトに切り詰めて残す）で、サイクル番号 0 で積む。終了チェックポイント（`begin_unlink_cycle` で 1 以上になる）の最後に消える。

### 6.5 smgr と buffer（C）

#### 6.5.1 smgr

- **リカバリモード**（M2 §6.2 の予約を実装）: `extend_to` の対象ファイルがなければ作ってから伸ばす（`read_buffer_zeroed` が使う）。短いセグメントの後に次のセグメントがあれば 0 埋めで伸ばす（M2 のとおり）。
- **unlink サイクル**（D17）: `pending_unlink: Mutex<Vec<(RelFileLocator, u64)>>` と `cycle: AtomicU64`（初期値 0）。`unlink` は現在の `cycle` の値で積む。`begin_unlink_cycle` は `cycle` を 1 進め、**進めた後**の値を返す（以後の unlink はこの番号で積まれる。これより小さい番号のものは REDO 点より前に積まれたもの）。`finish_pending_unlinks(upto)` は番号 < `upto` のものだけ消す。例: REDO 中の unlink は番号 0 で積まれ、終了チェックポイントの `begin_unlink_cycle` が 1 を返すので、その最後に消える。
- `truncate(rel, fork, n)`: `nblocks` のキャッシュを更新し、`n` を含むセグメントを `set_len`、それより後のセグメントを削除、`sync_data` と（セグメントを消したら）`sync_dir`。`pending_sync` から消したセグメントを外す。
- `exists` / `nblocks` / `extend` / `write_block` などは M2 のまま。

#### 6.5.2 smgr_wal

- `log_and_create(wal, smgr, xid, rel, fork)`: `RecordBuilder::new(Smgr, SMGR_CREATE, xid)` にメインデータ 16 バイト → `wal.insert`（flush しない）→ `smgr.create(rel, fork)`。
- `log_and_truncate`: レコードを挿入して **flush してから**（切り詰めは取り消せないため。PostgreSQL の `RelationTruncate` と同じ）バッファを捨てて切り詰める。

#### 6.5.3 buffer

- **dirty の時機**（D11）: `page_mut()` を初めて呼んだとき、ヘッダの Mutex の中で `dirty = true; just_dirtied = true` にする。M2 の「Drop でコンテンツラッチを外す前に立てる」はやめる。排他ラッチを持っているので、書き出し（共有ラッチでコピー）と重ならない。
- **flush_frame**（M2 §6.3 の 4）の手順 3: コピーの `pd_lsn` を読み、`wal.flush_to(lsn)`（`skip_wal_before_data` なら省く）。手順 5 の後、`assert_wal_before_data` なら `lsn <= wal.flushed_lsn()` を確かめ、破れていれば panic。
- `set_lsn` なしの Drop の検出（規約 2）。
- `drop_relation_buffers_from(rel, fork, n)`: ブロック番号 ≥ n のフレームを書かずに外す。

### 6.6 txn（E）

#### 6.6.1 xact_wal

- `XactRecord::encode`: §3.7 の形式。`decode` は長さと `nrels` の整合を検査する。
- REDO は §6.4.4。`ctx.ext` から `Arc<Clog>` を取り出す（取り出せなければ内部エラー）。

#### 6.6.2 clog

- `set_status_redo`: ページがメモリになければディスクから読む（ファイルがない・末尾より先なら 0 のページ）。`InProgress → Committed / Aborted` と同じ値の再設定を許す。`Committed ↔ Aborted` は Panic（WAL の矛盾）。
- `load_page_for(xid)`: そのページがメモリになければディスクから読む（なければ 0）。リカバリの後で R が `next_xid` について呼ぶ。理由: リカバリで `next_xid` が `Clog::open` のときの値より進むと、M2 の「以後に割り当てる XID のページは常に新しいページ」の前提が崩れ、`ensure_page_for` がディスクに中身のあるページを 0 で作り直しうるため。
- clog のページは LSN を持たない。同期コミットなので、clog の COMMITTED は常にコミットレコードの永続化の後に立つ。ABORTED がレコードより先にディスクに出ても、もともと中断扱いなので害はない。

#### 6.6.3 ライターロック（FIFO と中断）

```
begin_write(session_id, wait):
  lock writer { owner: Option<u64>, queue: VecDeque<u64> }
  queue.push_back(session_id); started = now
  loop:
    if owner.is_none() && queue.front() == Some(session_id): queue.pop_front(); owner = Some(session_id); break
    (g, _) = cv.wait_timeout(g, 50ms)
    if let Err(e) = wait.interrupts.check(): queue から自分を外す; cv.notify_all(); return Err(e)
    if let Some(t) = wait.lock_timeout && now - started >= t:
        queue から自分を外す; cv.notify_all(); return Err(55P03 "canceling statement due to lock timeout")
  unlock writer
  XID の割り当て（M2 §6.7.1 の (2)）
```

- 解放（M2 §6.7.1）は `owner = None; cv.notify_all()`。先頭の待ち手だけが取れる。
- `is_blocked_by(sid, among)`: `queue.contains(sid) && owner.map_or(false, |o| among.contains(&o))`。
- `lock_timeout` と `statement_timeout` の両方が効く場合は、先に来た方のエラーになる（PostgreSQL と同じ）。

#### 6.6.4 コミットゲート

- `commit_gate: RwLock<()>`。`commit` / `abort` の手順 1 で共有、チェックポイントの手順 1 で排他（`commit_gate_exclusive`）。M2 規約 7 のとおり poison は Panic。
- アボートもゲートを取る（アボートレコードが REDO 点より前で clog の ABORTED がチェックポイントに入らなくても害はないが、経路をそろえて単純にする）。

#### 6.6.5 checkpoint.rs

- §5.6 の手順の唯一の持ち主。`Cluster::checkpoint`・`shutdown`・リカバリ終了・チェックポインタスレッドはこれを呼ぶだけ（M2 と同じ）。
- チェックポインタの I/O エラーの扱いは M2 と同じ（Panic でなければログに出して次の周期で再試行）。

### 6.7 heap（D）

- §5.1 の手順。`hio.rs` の挿入先の選択は M2 のまま（FSM なし）。
- UPDATE の手順 4〜7 のために、`hio` に「ラッチを取らずにピンだけ返す」関数 `fn find_target(&self, rel, len) -> Result<PinnedBuffer>` を足す（ページに入るかの最終判定はラッチを取った後で行う）。
- `heap/wal.rs` の REDO は §6.4.4。`add_item` は M2 の `Page::add_item` をそのまま使う（ページの検査・行ポインタの規則が通常の経路と同じになる）。
- タプルのバイト列を WAL に載せる前に `t_ctid` を最終値にしておく（挿入は自分、更新の新版は自分）。

### 6.8 recovery と engine と bootstrap（R）

- `recovery::startup` は §5.5 の手順 4。`Cluster::open` は手順 1〜3 と 5〜8。
- ログの文言（`tracing` の info。PostgreSQL の文言に合わせる。未検証: 細部）:
  - `database system was shut down at <time>`（clean）
  - `database system was interrupted; last known up at <time>`（クラッシュ）
  - `redo starts at %X/%X` / `redo done at %X/%X` / `invalid record length at %X/%X: ...`（終わりの理由）
  - `checkpoint starting: end-of-recovery immediate wait` / `checkpoint complete: ...`
  - `database system is ready to accept connections`
- `bootstrap::initdb` は §5.8。

### 6.9 control と datadir（B）

- `format_version = 2`。読み込みで 1 なら FATAL `database files are incompatible with server`、DETAIL `The database cluster was initialized without WAL (format version 1), but the server requires format version 2.`、HINT `Re-run yuzhu-initdb.`。
- `single_slot_control_file`（変異）: 書き込みを常にスロット A に行い、スロット B は無効のまま。
- `datadir::sync_data_directory(vfs: &dyn Vfs) -> Result<()>`: `global/`、`base/<oid>/`、`pg_xact/`、`pg_wal/` の各ファイルを `ReadOnly` で開いて `sync_all`、各ディレクトリとデータディレクトリ自身を `sync_dir`。`yuzhu.pid` と `xlogtemp.*` は対象外。失敗は Panic（起動を止める）。

### 6.10 型と関数（F）

| 対象 | 仕様 |
|---|---|
| `void`（2278） | `typtype = p`、`typlen = 4`、`typalign = i`、`typcategory = P`（pg_type.dat に合わせる。未検証）。値は `Datum::Void` だけ。出力は空文字列。入力は `0A000` |
| `int4[]`（1007） | `typelem = 23`、`typcategory = A`、`typlen = -1`。int4 の `typarray = 1007` にする。入力は一次元の `{1,2,NULL}` 形式だけ（空白は許す。`{}` は空配列）。不正は `22P02 malformed array literal: "..."`。出力は `{1,2,NULL}`。演算子・キャストは持たない（unknown からの入力だけ）。カタログの列には使わない |

- `executor/eval.rs` は `FnKind::Runtime` を `ctx.runtime` で呼ぶ。

### 6.11 session と settings（S）

#### 6.11.1 トランザクションの特性

- session は `TxnCharacteristics { isolation: Isolation, read_only: bool, deferrable: bool }` を「現在のトランザクション」と「既定（`default_transaction_*`）」の 2 つ持つ。BEGIN の modes、`SET TRANSACTION`、`SET transaction_isolation` / `transaction_read_only` が現在の方を、`SET SESSION CHARACTERISTICS AS TRANSACTION` と `SET default_transaction_*` が既定の方を変える。トランザクションの開始時に既定から写す。
- `Isolation` は `ReadCommitted` / `ReadUncommitted`。`REPEATABLE READ` / `SERIALIZABLE` は BEGIN・SET TRANSACTION・`default_transaction_isolation` のどれでも `0A000 transaction isolation level "repeatable read" is not supported yet`（M1 の文言を流用）。どちらの値でも動作は Read Committed、`SHOW transaction_isolation` は指定した名前を返す（PostgreSQL の read uncommitted と同じ）。
- `SET TRANSACTION ...` をブロックの外で実行したら `WARNING 25P01 SET TRANSACTION can only be used in transaction blocks` を出して何もしない（未検証: PG17 で WARNING であること）。
- ブロック内でスナップショットを取る文（SELECT / VALUES / DML / DDL）を実行した後の `SET TRANSACTION ISOLATION LEVEL` は `25001 SET TRANSACTION ISOLATION LEVEL must be called before any query`。同じく `READ WRITE` への変更は `25001 transaction read-write mode must be set before any query`（未検証: 文言）。
- **READ ONLY**: 書き込む文（§5.2 d）は `25006 cannot execute <タグ> in a read-only transaction`（タグは `INSERT`、`UPDATE`、`DELETE`、`CREATE TABLE`、`DROP TABLE`）。ライターロックも XID も取らない。`CHECKPOINT` は許す。

#### 6.11.2 AND CHAIN

| 状態 | `COMMIT AND CHAIN` | `ROLLBACK AND CHAIN` |
|---|---|---|
| ブロック内 | コミットして、同じ特性で新しいブロックを始める。タグ `COMMIT` | アボートして同じく。タグ `ROLLBACK` |
| Failed | アボートして同じ特性で新しいブロック。タグ `ROLLBACK`（未検証） | 同じ |
| ブロック外（暗黙のブロック中を含む） | `ERROR 25P01 COMMIT AND CHAIN can only be used in transaction blocks`（m3-tx-semantics の実機 #18） | `ERROR 25P01 ROLLBACK AND CHAIN can only be used in transaction blocks` |

#### 6.11.3 セーブポイント（D22）

| 状態 | `SAVEPOINT x` | `RELEASE [SAVEPOINT] x` | `ROLLBACK TO [SAVEPOINT] x` |
|---|---|---|---|
| ブロック外（単一文、暗黙のブロック） | `ERROR 25P01 SAVEPOINT can only be used in transaction blocks` | `ERROR 25P01 RELEASE SAVEPOINT can only be used in transaction blocks` | `ERROR 25P01 ROLLBACK TO SAVEPOINT can only be used in transaction blocks` |
| ブロック内 | `ERROR 0A000 SAVEPOINT is not supported yet` → Failed | `ERROR 3B001 savepoint "x" does not exist` → Failed | `ERROR 3B001 savepoint "x" does not exist` → Failed |
| Failed | `25P02` | `25P02` | `ERROR 3B001 savepoint "x" does not exist`（Failed のまま） |

- パーサは 3 つの文を `TransactionKind::{Savepoint, Release, RollbackTo}(name)` として受け付ける（M1 のパーサの `not_supported` をやめる）。`PREPARE TRANSACTION` は `0A000` のまま。

#### 6.11.4 タイムアウト

- `statement_timeout`: 文ごと（D31）。§5.2 の a と f。期限の検査は `check_interrupts`（行ごと）、ライターロックの待ち、`pg_sleep`。
- `lock_timeout`: ライターロックの待ちだけに効く（M3 にほかのロック待ちはない）。
- `idle_in_transaction_session_timeout` / `idle_session_timeout`: §5.10。session は `fn idle_timeout(&self) -> Option<Duration>` を公開する。
- `deadlock_timeout`: 受け付けて保存するだけ（M3 ではデッドロックが起きない。m3-tx-semantics §5.4）。

#### 6.11.5 設定項目の追加・変更

| 名前 | 値 | 備考 |
|---|---|---|
| `transaction_isolation` | 現在のトランザクションの値（既定 `read committed`） | SET できる（§6.11.1 の制約つき） |
| `default_transaction_isolation` | `read committed` | `read uncommitted` も可 |
| `transaction_read_only` | `off` | SET できる |
| `default_transaction_read_only` | `off` | reported（M1 から ParameterStatus に含まれる） |
| `transaction_deferrable` / `default_transaction_deferrable` | `off` | 受け付けるだけ |
| `idle_session_timeout` | `0` | ★ |
| `deadlock_timeout` | `1s` | 受け付けるだけ |
| `synchronous_commit` | `on` | `on`/`off`/`local`/`remote_write`/`remote_apply` を受け付け、表示は設定した値。動作は常に同期（D27） |
| `full_page_writes` | `on` | SHOW のみ |
| `wal_segment_size` | `16MB` など | SHOW のみ |
| `wal_sync_method` | `fdatasync` | SHOW のみ |
| `max_wal_size` | `1GB` | SHOW のみ（起動時の値） |
| `checkpoint_timeout` | `5min` | M2 と同じ |

#### 6.11.6 RuntimeInfo の実装

- `Session` が文の実行中に `RuntimeInfo` を実装する小さな構造体（`backend_pid`、`Arc<TxnManager>`、`Arc<InterruptFlag>`）を作り、`EvalCtx.runtime` に渡す。`backend_pid` は `Session::new` で `cluster.next_session_id()` から取った値を i32 に収めたもの（`i32::MAX` を超えたら 1 に戻らず、接続を `53300` で拒否する。事実上起きない）。

### 6.12 yuzhu-server（J）

- **BackendKeyData**: pid は `session.backend_pid()`、秘密鍵は M1 と同じ乱数。登録表（M2 の `shutdown.rs`）に `(pid, secret, Arc<InterruptFlag>, TcpStream の clone)` を持つ。
- **CancelRequest**: §5.10。`connection.rs` の M1 の「読んで閉じるだけ」を置き換える。
- **アイドルのタイムアウト**: §5.10。
- **終了コード**: 正常停止 0、起動の失敗（リカバリの失敗を含む）1、Panic 3（M2 と同じ）。
- **CLI**: `--max-wal-size`（例 `1GB`）を足し、`--ignore-unclean-shutdown` を消す。`yuzhu-initdb` に `--wal-segment-size <MB>`（2 の冪、2〜1024）を足す。
- **`yuzhu-waldump -D <dir> [--start LSN] [--end LSN] [--stats]`**: `WalReader`（`include_switch`）でレコードを読み、`wal::dump` の形式で 1 行ずつ出す。例: `rmgr: Heap len: 111 xid: 1234 lsn: 0/01000120 prev: 0/010000E8 desc: INSERT off 5 blkref #0: rel 1663/5/16384 blk 3`。終わりに `end of WAL at %X/%X: <理由>`。データディレクトリのロックは取らない（読むだけ）。

| `session/lock_timeout_2conn.slt` | `connection a`: `BEGIN; UPDATE t SET v = 1 WHERE id = 1`、`connection b`: `SET lock_timeout = '100ms'; UPDATE t SET v = 2 WHERE id = 1` が 55P03 → a で COMMIT → b で再実行が成功（PostgreSQL では行ロック待ち、yuzhu ではライターロック待ちで、どちらも 55P03） |

### 7.2 クラッシュをまたぐテスト（`tests/restart/m3/`）

- M2 の再起動テスト（§7.2）の仕組みに **`--crash`** を足す: フェーズの間で `tests/yuzhu.sh crash`（`kill -9` → 同じデータディレクトリで起動 → 待ち受けを待つ）と `tests/pg.sh crash`（`docker kill -s KILL` → `docker start` → 待つ）を使う。
- シナリオ:
  1. CREATE / INSERT / UPDATE / DELETE をコミット → クラッシュ → すべて残る
  2. `connection other` で BEGIN → INSERT（コミットしない）、本体で別の行をコミット → クラッシュ → コミットした行だけ
  3. DROP TABLE をコミット → クラッシュ → ない。同名で CREATE できる
  4. BEGIN → CREATE TABLE → INSERT → ROLLBACK → クラッシュ → ない
  5. 大きな表（プールを小さくしたサーバで）を全行 UPDATE してコミット → CHECKPOINT → さらに UPDATE をコミット → クラッシュ → 最後の値
  6. 2 回続けてクラッシュ（リカバリ直後にもう一度 `kill -9`）→ シナリオ 1 の値が残る

### 7.3 分離性テスト（`tests/isolation/`）

### 7.5 クラッシュ試験 層 1（`yuzhu-core/tests/crash_sim/`、T）

**仕組み**:

- `TestCluster`（`testing.rs`）が `SimVfs` の上で initdb し、`background_checkpointer = false`、`shared_buffers = 16`、`wal_segment_size = 2 MiB` で起動する。ワークロードは **1 スレッドで複数の `Session` を順番に操作する**（プロトコルを通さない。スレッドの実行順に左右されない）。チェックポイントは「k 文ごと」に手で呼ぶ。
- クラッシュ点: 起動後の I/O の通し番号 N を選び、`FaultRule { op: Any, nth: Some(N), effect: CrashFreeze }` を仕掛ける。凍結後のエラーで Panic になったら（または ワークロードが終わったら）`cluster.abandon()` → `vfs.crash(mode)` → `Cluster::open`（リカバリ）→ 不変条件を検査。
- 網羅: 小さいワークロード（I/O が数百回）では N を 0 から最後まですべて試す（`DropUnsynced` と `KeepAll`）。大きいワークロードはシードで N と `RandomSubset` / `TornSectors { sector: 512 / 4096 }` を選ぶ。制御ファイルには `TornSectors { sector: 1 }` も使う。
- 確定の記録: テストは `Session` の COMMIT が `Ok` で戻ったトランザクションを「確定」、COMMIT を呼んだが Panic で戻ったものを「不明」として記録する。
- 失敗したら `seed`、`mode`、`N`、ワークロード名を出し、`YUZHU_SIM_SEED=... YUZHU_CRASH_AT=...` で 1 件だけ再実行できるようにする。

**ワークロード**（m3-recovery §9.3）: (1) 銀行振込（10 口座、合計一定、一部 ROLLBACK、一部はクラッシュ時に実行中のまま）、(2) 追記ログ（トランザクションごとに k 行。行数は 0 か k）、(3) 少数の行の UPDATE の繰り返し（同じページへの多数の変更とチェックポイントをまたぐ。FPW の経路）、(4) DDL の混在（CREATE / DROP / ROLLBACK される CREATE）、(5) 8 フレームのプールで追い出しと steal を頻発させ、5 文ごとにチェックポイント。

**不変条件**（m3-recovery §9.5 の I1〜I12）: 各ワークロードの後に `invariants.rs` の関数で検査する。I4（モデルとの一致）は `BTreeMap` のモデルに「不明」なトランザクションの任意の部分集合を加えたもののどれかと一致すること。I5 はヒープの全走査で xmin / xmax の最大値と `next_xid` を比べる。I7 は `WalReader` で保持されている WAL を読み、コミットレコードのある XID が clog で COMMITTED であること。I8 は全ページの `verify`、行ポインタ、`page_lsn <= WAL の末尾`、制御ファイルがチェックポイントレコードを指すこと、カタログにあるリレーションのファイルが存在すること。

**変異テスト**（`mutation.rs`。ハーネスが壊れを検出できること）:

| 変異 | 方法 | 検出されるべき不変条件 |
|---|---|---|
| FPW なし | `disable_full_page_writes` + `TornSectors` | I4 か I8（または起動時の XX001） |
| コミットで flush しない | `skip_commit_flush` + `DropUnsynced` | I1 |
| WAL-before-data を破る | `skip_wal_before_data`（`assert_wal_before_data = false`）+ `DropUnsynced` | I2 か I4 |
| チェックポイントで clog を書かない | `skip_clog_flush_at_checkpoint` | I1 か I7 |
| 制御ファイルを 1 スロットで上書き | `single_slot_control_file` + `TornSectors { sector: 1 }` | 起動不能を検出 |
| REDO の LSN 判定を外す | `redo_ignore_page_lsn` | I4（二重適用。insert の REDO の offnum 不一致による Panic も可） |
| ディレクトリの fsync を省く | `SimVfs::set_ignore_sync_dir(true)` + `DropUnsynced` | I1 か I8（新しいテーブルやセグメントが消える） |

- 各変異について「既定のシード集合のうち少なくとも 1 つで検出する」ことをテストにする（検出できなければテスト失敗）。
- CI では固定シードの層 1 を `cargo test` で毎回（合計 60 秒以内を目安）。長時間のランダム実行は `#[ignore]`（夜間ジョブ）。

## 10. 確認事項

ユーザーの不在中に仮決めしたことです。仮決めのままでよいか確認してください。ディスク形式に関わるもの（★）は、実装の前に決めるのが望ましいです。

- **M3-Q1 M3 の範囲**: M2 で MVCC・コミットログ・単一ライターを前倒ししたので、M3 は WAL・チェックポイント・クラッシュリカバリ・クラッシュ試験と、残りのトランザクションの意味論（READ ONLY、AND CHAIN、セーブポイントのエラー、タイムアウト、キャンセル）に絞ります（D1）。
- **★M3-Q2 WAL の形式**: PostgreSQL の WAL とは互換のない、yuzhu 独自の単純な形式にします（8KB の WAL ページを持たず、レコードはセグメントをまたがない。レコードヘッダは 64 ビットの XID を持つ 32 バイト）。PostgreSQL の `pg_waldump` などのツールは使えません。代わりに `yuzhu-waldump` を用意します（D2、D3）。
- **★M3-Q3 1 レコードに載せられるページ数**: M4 の B+Tree の分割を 1 つのレコードで書けるよう、上限を 32 ページ（PostgreSQL と同じ）、レコードの最大を 1 MiB にします。そのため WAL セグメントの最小は 2 MiB です（既定は 16 MiB）（D4）。
- **M3-Q4 ヒントビットを M3 でも使わない**: 可視性の判定のたびにコミットログ（メモリ上）を引きます。ページチェックサムが常に有効なため、ヒントビットを入れるには WAL にページ画像を書く仕組みが必要になり、M5 の VACUUM と一緒に入れます（D7、M2-Q5 の回答）。
- **M3-Q5 孤児ファイルを掃除しない**: クラッシュで中断したトランザクションが作ったファイルや、削除の途中のファイルが残ることがあります。PostgreSQL と同じく自動では消しません（D15）。
- **M3-Q6 チェックポイント**: PostgreSQL と同じファジー方式です。契機は 5 分ごと（`checkpoint_timeout`）と、WAL が 1GB（`max_wal_size`）たまったとき、`CHECKPOINT` 文、停止、リカバリの終了です。PostgreSQL のような書き出しの時間的な分散（`checkpoint_completion_target`）は入れないので、チェックポイントの間は I/O が集中します。
- **M3-Q7 セーブポイント**: 実装しません。`SAVEPOINT` はブロック内で「未対応（0A000）」、`RELEASE` / `ROLLBACK TO` は PostgreSQL と同じく「セーブポイントが存在しない（3B001）」、ブロック外では PostgreSQL と同じ 25P01 を返します。psql の `ON_ERROR_ROLLBACK`、Django の入れ子の `atomic()` など、セーブポイントを使うツールは動きません（D22）。
- **M3-Q8 分離レベル**: `READ COMMITTED` と `READ UNCOMMITTED`（PostgreSQL と同じく Read Committed として動く）だけを受け付け、`REPEATABLE READ` / `SERIALIZABLE` はエラー（0A000）のままです（M5 で対応）。`READ ONLY` と `AND CHAIN` は M3 で PostgreSQL と同じにします。
- **M3-Q9 タイムアウトとキャンセル**: `statement_timeout`、`lock_timeout`、`idle_in_transaction_session_timeout`、`idle_session_timeout`、CancelRequest（psql の Ctrl+C）を M3 で実装します。書き込みロックを持ったまま放置されたセッションの救済のためです。PostgreSQL 17 の `transaction_timeout` は実装しません（D24）。
- **M3-Q10 分離性テストのための追加**: PostgreSQL の分離性テストと同じ方法で「待ち」を判定するため、`pg_isolation_test_session_is_blocked`、`pg_backend_pid`、`pg_sleep` と、それに必要な `int4[]`（入出力だけ）と `void` 型を足します（D23）。
- **M3-Q11 `synchronous_commit`**: `SET synchronous_commit = off` などは受け付けますが、どの値でもコミットごとに WAL を fsync します（非同期コミットは M6 以降）（D27）。
- **M3-Q12 データディレクトリの作り直し**: M2 で作ったデータディレクトリは M3 のサーバでは起動できません（制御ファイルの形式の版を 2 に上げます）。initdb をやり直してください（D25、M2-Q20 の方針どおり）。
- **M3-Q13 テスト用の隠しスイッチ**: クラッシュ試験が「わざと壊した実装」を検出できることを確かめるため、FPW やコミット時の fsync を無効にする隠しスイッチをコードに置きます。既定は無効で、コマンドラインや設定ファイル、SQL からは変えられません（D29）。
- **M3-Q14 クラッシュリカバリの前の全ファイルの fsync**: クラッシュ後の起動では、REDO の前にデータディレクトリの全ファイルを fsync します（PostgreSQL と同じ）。データが大きいと起動に時間がかかります（D13）。
- **M3-Q15 WAL の書き込み失敗**: WAL の書き込みか fsync が失敗したら、サーバは直ちに終了し（終了コード 3）、次の起動でリカバリします。そのとき COMMIT を送っていたクライアントからは、コミットされたかどうかが分かりません（PostgreSQL と同じ）（D30）。
- **M3-Q16 WAL セグメントを再利用しない**: 新しいセグメントは毎回 16 MiB を 0 で埋めてから使い、古いものは消します。PostgreSQL の再利用より I/O は増えますが、古い WAL を誤読する余地がなくなります（D18）。
- **M3-Q17 クラッシュ時に実行中だったトランザクション**: コミットログには何も書かず、「実行中でもコミット済みでもない」ので中断として扱います（PostgreSQL と同じ）。
- **M3-Q18 `kill -9` の試験の頻度**: 実プロセスの `kill -9` の試験は時間がかかるので、通常の CI では動かさず夜間のジョブで動かします。毎回の CI では、プロセス内の決定的な障害注入の試験を動かします。
- **M3-Q19 書き込みロックの待ちの順序**: 書き込みロックを待つセッションは到着順（FIFO）に取得します。
- **M3-Q20 PostgreSQL との既知の差（M5 まで残るもの）**: 別の行への同時の INSERT / UPDATE も待つ、ドキュメントの website の例で DELETE の件数が違う（直列実行と同じ結果）、読み取り中のテーブルの DROP を待たない、同名の CREATE TABLE の同時実行のエラーが 42P07、デッドロックが起きない（m3-tx-semantics §5.6）。共有テストにはこれらに依存するケースを入れません。
- **M3-Q21 異常終了後の起動**: M2 では異常終了の後の起動を拒否していましたが、M3 からはクラッシュリカバリをして起動します。`--ignore-unclean-shutdown` は廃止します（D25 と §5.7）。
- **M3-Q22 1 トランザクションで作成・削除できるテーブルの数**: コミットレコードの大きさの上限（1 MiB）から、1 トランザクションで作成または削除できるテーブルは約 8.7 万個までです（超えると 54000）。

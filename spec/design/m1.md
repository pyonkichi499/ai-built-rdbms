# yuzhu M1 基本設計（Rust 実装）

M1 のゴールは、`psql` と主要ドライバ（Simple Query を使うモード）が yuzhu-server に接続し、メモリ上のテーブルに対して CREATE TABLE / INSERT / SELECT を実行できることです。この文書は、並列に動く実装者全員が従う**契約**です。モジュールの境界、公開する型、関数のシグネチャ、振る舞いを定めます。

- 要件定義: <https://claude.ai/code/artifact/9381e901-9f2a-49a4-9bb2-479295dde6e2>
- 調査資料（根拠）: `spec/research/`
  - `research-pg-protocol.md` プロトコル、ParameterStatus、ドライバの挙動
  - `research-pg-types.md` 型 OID、キャスト、演算子の解決、SQLSTATE
  - `research-rust-db-arch.md` モジュール構成、Executor の設計、バッファプールの注意点
  - `research-slt.md` sqllogictest ランナー、テストの運用
- 迷ったら **PostgreSQL 17 と同じ挙動**を選ぶ。判断が分かれる点は推奨案で進め、リポジトリ直下の `QUESTIONS.md` に記録する。

## 1. M1 の範囲

### 1.1 SQL

| 分類 | M1 で対応するもの |
|---|---|
| DDL | `CREATE TABLE [IF NOT EXISTS] name (col type [constraints], ..., [table_constraint])`、`DROP TABLE [IF EXISTS] name [, ...]` |
| 列制約 | `NOT NULL`、`NULL`、`DEFAULT expr`、`CHECK (expr)`、`CONSTRAINT name ...` |
| 表制約 | `CHECK (expr)`、`CONSTRAINT name CHECK (...)` |
| DML | `INSERT INTO t [(cols)] VALUES (...), (...)`、`INSERT INTO t [(cols)] SELECT ...`、`DEFAULT` キーワード（VALUES 内）、`INSERT ... DEFAULT VALUES` |
| 問い合わせ | `SELECT [DISTINCT] targets [FROM table [AS alias]] [WHERE] [ORDER BY expr [ASC/DESC] [NULLS FIRST/LAST], ...] [LIMIT n] [OFFSET n]`、FROM なしの SELECT、`*` と `t.*`、列の別名、ORDER BY での出力列番号と別名の参照、`VALUES (...), (...)` 単体 |
| 式 | リテラル（整数、小数、文字列、`E'...'` は任意、`TRUE`/`FALSE`/`NULL`）、列参照（`col`、`t.col`）、算術 `+ - * / %`、単項 `+ -`、比較 `= <> != < <= > >=`、`AND OR NOT`、`IS [NOT] NULL`、`IS [NOT] TRUE/FALSE`、`||`、`CAST(x AS t)` と `x::t`、`BETWEEN`、`IN (list)`、`LIKE`/`NOT LIKE`、`CASE`（単純形と検索形）、`COALESCE`、`NULLIF`、括弧 |
| 関数 | `version()`、`current_database()`、`current_schema()`、`current_user`（キーワード形）、`length(text)`、`lower`、`upper`、`abs`（各整数・float8） |
| トランザクション | `BEGIN [TRANSACTION|WORK]`、`START TRANSACTION`、`COMMIT [WORK|TRANSACTION]`、`END`、`ROLLBACK [WORK|TRANSACTION]`、`ABORT` |
| セッション | `SET name {TO|=} value[, ...]`、`SET name TO DEFAULT`、`SET SESSION name ...`、`SET LOCAL`（M1 は SESSION と同じ扱い）、`SET TIME ZONE value`、`RESET name`、`RESET ALL`、`SHOW name`、`SHOW ALL` |

**M1 では対応しないもの**（文法上は認識してよいが、実行すると `0A000 feature_not_supported`）: UPDATE、DELETE（M2）、JOIN、集約、GROUP BY、サブクエリ（M4）、インデックス、PRIMARY KEY・UNIQUE・FOREIGN KEY（M4/M5）、RETURNING、EXPLAIN。

なお PRIMARY KEY と UNIQUE はアプリが多用するので、M1 では **構文だけ受け付けて `0A000` を返す**。黙って無視してはいけない。

### 1.2 型

| SQL 名 | 内部名 | OID | typlen | 備考 |
|---|---|---|---|---|
| `boolean`, `bool` | bool | 16 | 1 | |
| `smallint`, `int2` | int2 | 21 | 2 | |
| `integer`, `int`, `int4` | int4 | 23 | 4 | |
| `bigint`, `int8` | int8 | 20 | 8 | |
| `real`, `float4` | float4 | 700 | 4 | |
| `double precision`, `float8`, `float` | float8 | 701 | 8 | `float(p)` は p ≤ 24 なら float4、それ以外は float8 |
| `text` | text | 25 | -1 | |
| `varchar(n)`, `character varying(n)` | varchar | 1043 | -1 | typmod = n + 4。n なしは -1 |
| （リテラル用） | unknown | 705 | -2 | 文字列リテラルと NULL の型。出力に残ったら text とみなす |

- 型は **`SqlType { oid: Oid, typmod: i32 }`** で表す。typmod の -1 は「指定なし」。
- `numeric`、`char(n)`、日付・時刻型は M5。キーワードとして来たら `0A000` を返す（`42704 undefined_object` ではなく、未対応であることが分かるようにする）。
- 値の範囲、オーバーフロー（22003）、ゼロ除算（22012）、入力不正（22P02）、文字列が長すぎる（22001）は PostgreSQL と同じにする。詳細は `research-pg-types.md`。

### 1.3 プロトコル

`research-pg-protocol.md` の第 7 節「M1 の最小セット」に従う。要点は次の通り。

- 受信: SSLRequest・GSSENCRequest（`N` を返して続行）、StartupMessage（プロトコル 3.0。3.x の上位マイナー版は NegotiateProtocolVersion で 3.0 に落とす）、CancelRequest（読んで接続を閉じるだけ）、`Q` Query、`X` Terminate。
- Extended Query のメッセージ（`P` `B` `D` `E` `C` `H` `F`）を受けたら `ErrorResponse(0A000)` を返し、`S` Sync まで読み捨て、Sync で ReadyForQuery を返す（接続は切らない）。
- 送信: `R`(AuthenticationOk)、`S`、`K`、`Z`、`T`、`D`、`C`、`I`、`E`、`N`、`v`。
- 認証: trust のみ。
- 接続時の ParameterStatus は次の値で送る: `server_version=16.0`、`server_encoding=UTF8`、`client_encoding=UTF8`、`DateStyle=ISO, MDY`、`IntervalStyle=postgres`、`TimeZone=UTC`、`integer_datetimes=on`、`standard_conforming_strings=on`、`is_superuser=on`、`session_authorization=<user>`、`application_name=<起動パラメータの値か空>`、`default_transaction_read_only=off`、`in_hot_standby=off`。
  - `server_version` を 16.0 にするのは、psql の `\d` 系コマンドが 17 以降で新しいカタログ列を参照するため。後のマイルストーンで追従する。

## 2. クレートとモジュールの構成

```

├── yuzhu-core/src/
│   ├── lib.rs           公開 API の再エクスポート
│   ├── error.rs         Error, SqlState, Result
│   ├── types/           型システム（最下層）
│   │   ├── mod.rs       Oid, SqlType, 組み込み型の OID 定数

│   │   ├── io.rs        テキスト入出力（PostgreSQL のテキスト表現）
│   │   └── ops.rs       算術・比較などの組み込み演算の実装

│   ├── planner/

│   │   └── plan.rs      PhysicalPlan

│   ├── storage/

│   │   └── memory.rs    M1 のメモリ実装
│   ├── txn.rs           M1 のトランザクション（undo ログ方式）
│   ├── settings.rs      SET / SHOW で扱う設定項目
│   ├── engine.rs        Database（全体の所有者）
│   └── session.rs       Session, ResultSink, execute_simple
└── yuzhu-server/src/

    ├── config.rs        TOML とコマンドライン引数
```

**依存の方向**（下位は上位を `use` しない）:
`error`, `types` ← `sql` ← `catalog` ← `analyzer` ← `planner` ← `executor` ← `session`/`engine`。
`storage`, `txn`, `settings` は `error`, `types`, `catalog` の型にだけ依存する。**`sql` はカタログにもストレージにも依存させない。**

**外部クレート**: yuzhu-core は M1 では外部依存なし。yuzhu-server は `clap`（引数）、`serde` + `toml`（設定）、`tracing` + `tracing-subscriber`（ログ）を使ってよい。テスト用の dev-dependency は自由。

```rust
pub struct Error {
    pub severity: Severity,        // 通常は Error
    pub sqlstate: SqlState,
    pub message: String,           // PostgreSQL と同じ文言を目指す（小文字始まり、末尾ピリオドなし）

    pub hint: Option<String>,

    pub fn new(sqlstate: SqlState, message: impl Into<String>) -> Self;
    pub fn with_detail(self, d: impl Into<String>) -> Self;
    pub fn with_hint(self, h: impl Into<String>) -> Self;
    pub fn with_position(self, p: u32) -> Self;
```

- 位置情報: パーサとアナライザは、ソース上の位置を **バイトオフセットの `Span { start: u32, end: u32 }`** で持つ。`Error.position` に入れるときに 1 始まりの文字位置へ変換する（`session` で一括変換してよい）。
- panic はバグ（不変条件の違反）のときだけ。ユーザー入力が原因の異常は必ず `Error` で返す。

### 3.2 types

```rust
pub type Oid = u32;

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct SqlType { pub oid: Oid, pub typmod: i32 }

pub mod oid {
    pub const BOOL: Oid = 16;  pub const INT8: Oid = 20;  pub const INT2: Oid = 21;
    pub const INT4: Oid = 23;  pub const TEXT: Oid = 25;  pub const OID: Oid = 26;
    pub const FLOAT4: Oid = 700; pub const FLOAT8: Oid = 701; pub const UNKNOWN: Oid = 705;
    pub const VARCHAR: Oid = 1043; pub const NAME: Oid = 19;
    pub const FIRST_NORMAL_OBJECT_ID: Oid = 16384; // ユーザーが作るオブジェクトの OID はここから
}

#[derive(Clone, Debug)]
pub enum Datum {
    Null,
    Bool(bool),
    Int2(i16),
    Int4(i32),
    Int8(i64),
    Float4(f32),
    Float8(f64),
    Text(String),   // text, varchar, unknown, name で共通
}
pub type Row = Vec<Datum>;
```

- `Datum` は型を名乗らない。型は式とスキーマ（`SqlType`）が持つ。
- 比較・ソート用に `fn cmp_datum(a: &Datum, b: &Datum) -> Ordering`（同じ型同士。NULL の順序は呼び出し側が決める）。浮動小数点は PostgreSQL と同じく NaN を最大、`-0 == +0` とする。
- `types::io`:
  - `fn output_text(d: &Datum, ty: SqlType) -> Option<String>`（NULL は `None`）。bool は `t`/`f`。float は PostgreSQL の既定（`extra_float_digits = 1`）と同じ最短の往復表現（例: `1e+20`、`0.1`、`Infinity`、`-Infinity`、`NaN`、`-0`）。
  - `fn input_text(s: &str, ty: SqlType) -> Result<Datum>`（`'123'::int4` やキャストで使う。前後の空白の扱い、`' 12 '` が通る点、bool の `'yes'`/`'on'`/`'1'` なども PostgreSQL と同じに）。
- `types::ops`: 組み込み関数・演算子の実体。`pub type BuiltinFn = fn(&[Datum]) -> Result<Datum>;`。strict（引数に NULL があれば結果も NULL）は呼び出し側（executor）が処理するので、実体は NULL を受け取らない前提でよい。

### 3.3 catalog

```rust
pub struct ColumnDef {
    pub name: String,
    pub attnum: i16,                 // 1 始まり
    pub ty: SqlType,
    pub not_null: bool,
    pub default: Option<BoundExprSource>, // 下記
}
pub struct CheckDef { pub name: String, pub expr_sql: String }
pub struct TableDef {
    pub oid: Oid,
    pub schema: String,              // M1 は "public" のみ
    pub name: String,
    pub columns: Vec<ColumnDef>,
    pub checks: Vec<CheckDef>,
}
```

- **DEFAULT と CHECK の式は、SQL テキスト（`expr_sql`）としてカタログに保存する**。使うたびにパースとアナライズをやり直す。PostgreSQL は木を直列化して保存するが、M1 ではテキストが最も単純で、M2 でカタログをテーブル化しても困らない。`BoundExprSource` は `pub struct BoundExprSource { pub expr_sql: String }` とする。
  - CHECK 制約の名前は PostgreSQL と同じ規則で自動生成する（`<table>_<column>_check`、表制約は `<table>_check`。重複したら `1`, `2`... を付ける）。
- 組み込みの表（`catalog/builtin.rs`）は、PostgreSQL と同じ OID を使う静的な配列にする:
  - `BuiltinType { oid, name, typlen, typbyval, category: char, preferred: bool, input/output }`
  - `BuiltinCast { source, target, context: CastContext /* Implicit|Assignment|Explicit */, method: CastMethod /* Function(BuiltinFn)|Binary|InOut */ }`
  - `BuiltinOperator { oid, name: &'static str, left: Option<Oid>, right: Oid, result: Oid, func: BuiltinFn }`
  - `BuiltinFunction { oid, name, args: &'static [Oid], result: Oid, strict: bool, func: BuiltinFn }`
  - M2 では、この表をそのまま `pg_type`、`pg_cast`、`pg_operator`、`pg_proc` テーブルの初期データとして書き出す。
- `CatalogReader` トレイト（analyzer と planner が使う、読み取り専用のビュー）:

```rust
pub trait CatalogReader {
    fn table(&self, schema: Option<&str>, name: &str) -> Option<Arc<TableDef>>;
    fn table_by_oid(&self, oid: Oid) -> Option<Arc<TableDef>>;
    fn type_by_oid(&self, oid: Oid) -> Option<&'static BuiltinType>;
    fn type_by_name(&self, name: &str) -> Option<&'static BuiltinType>;
    fn casts_from(&self, source: Oid) -> &[BuiltinCast];                // または find_cast(source, target)
    fn operators_named(&self, name: &str) -> Vec<&'static BuiltinOperator>;
    fn functions_named(&self, name: &str) -> Vec<&'static BuiltinFunction>;
    fn current_database(&self) -> &str;
}
```

- `TableDef` は `Arc` で共有し、不変にする。DDL は新しい `Arc<TableDef>` に差し替える。

### 3.4 storage と txn

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug, PartialOrd, Ord)]
pub struct RowId(pub u64);          // M2 では (PageId, slot) を詰めた TID に置き換わる

pub trait TableStore: Send + Sync {
    fn create_table(&self, table_oid: Oid) -> Result<()>;
    fn drop_table(&self, table_oid: Oid) -> Result<()>;
    fn insert(&self, table_oid: Oid, row: Row) -> Result<RowId>;
    fn delete_row(&self, table_oid: Oid, id: RowId) -> Result<()>; // undo 用（M2 で DELETE 文にも使う）
    fn scan(&self, table_oid: Oid) -> Result<Vec<(RowId, Row)>>;   // M1 は全件コピーで可（M2 でカーソルにする）
}
```

- M1 のメモリ実装は、テーブルごとに挿入順の `Vec<Option<Row>>` を持つ（ヒープと同じく挿入順に読める）。
- **M1 のトランザクションは undo ログ方式**とする（M3 で MVCC に置き換える）。
  - `Transaction { undo: Vec<UndoEntry>, statement_start: usize }`、`enum UndoEntry { Inserted { table_oid, row_id }, CreatedTable { table_oid }, DroppedTable { def: Arc<TableDef>, rows: Vec<Row> } }`
  - 文が失敗したら、その文の分だけ undo する（`statement_start` 以降を巻き戻す）。これで「複数行 INSERT の 3 行目で CHECK 違反」でも、それまでの行が残らない。
  - ROLLBACK と、失敗したトランザクションブロックの終了時には、全体を undo する。
  - 他のセッションからは、コミット前の行も見えてしまう（ダーティリード）。M1 の既知の制約として許容し、M3 で解消する。
- 同時実行の制御: M1 は `Database` 内の 1 つの `Mutex` で、文の実行全体を直列化してよい。

### 3.5 session と ResultSink（yuzhu-server との境界）

```rust
pub struct StartupParams { pub user: String, pub database: String, pub application_name: Option<String>, pub options: Vec<(String, String)> }

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum TransactionStatus { Idle, InBlock, Failed }  // ReadyForQuery の 'I' 'T' 'E'

pub struct ColumnDesc {
    pub name: String,
    pub table_oid: Oid,     // 列参照そのものなら元テーブルの OID、それ以外は 0
    pub column_attnum: i16, // 同上。それ以外は 0
    pub type_oid: Oid,
    pub type_len: i16,
    pub type_modifier: i32,
}

pub struct Notice { pub severity: Severity, pub sqlstate: SqlState, pub message: String, pub detail: Option<String>, pub hint: Option<String> }

pub trait ResultSink {
    fn row_description(&mut self, columns: &[ColumnDesc]) -> std::io::Result<()>;
    /// values は ColumnDesc と同じ順序。テキスト形式への変換は types::io::output_text で行う
    fn data_row(&mut self, values: &[Option<String>]) -> std::io::Result<()>;
    fn command_complete(&mut self, tag: &str) -> std::io::Result<()>;
    fn empty_query(&mut self) -> std::io::Result<()>;
    fn error(&mut self, err: &Error) -> std::io::Result<()>;
    fn notice(&mut self, notice: &Notice) -> std::io::Result<()>;
    fn parameter_status(&mut self, name: &str, value: &str) -> std::io::Result<()>;
}

pub struct Database { /* catalog, storage, settings の既定値など */ }
impl Database {
    pub fn new(config: DatabaseConfig) -> std::sync::Arc<Database>;
}
pub struct DatabaseConfig { pub database_name: String /* 既定 "yuzhu" */ }

pub struct Session { /* db, 設定, トランザクション状態 */ }
impl Session {
    pub fn new(db: Arc<Database>, params: StartupParams) -> Result<Session>; // 存在しない DB 名は 3D000 で拒否
    /// 接続直後に送る ParameterStatus の一覧
    pub fn initial_parameter_status(&self) -> Vec<(String, String)>;
    /// Simple Query を 1 つ処理する。エラーは sink.error で通知する。
    /// Err を返すのは sink への書き込みが失敗したとき（クライアントの切断）だけ。
    pub fn execute_simple(&mut self, sql: &str, sink: &mut dyn ResultSink) -> std::io::Result<()>;
    pub fn transaction_status(&self) -> TransactionStatus;
}
```

- `data_row` には変換済みのテキストを渡す（server が型ごとの変換を知らなくて済むようにする）。M5 でバイナリ形式に対応するときに、ここを拡張する。
- M1 の `Database` は 1 つだけ。起動パラメータの `database` が `DatabaseConfig.database_name` と違えば、`3D000 invalid_catalog_name`（`database "x" does not exist`）で拒否する。テストランナーやドライバの既定値に合わせ、`database_name` の既定は **`postgres`** とする。

## 4. 処理の流れ

```
Session::execute_simple(sql)
  ├─ sql::parse(sql) -> Result<Vec<Statement>>       構文エラーなら 1 つの ErrorResponse で終了
  ├─ 空（コメントや空白だけ）なら EmptyQueryResponse
  ├─ 文ごとに:
  │    ├─ Failed 状態なら ROLLBACK/COMMIT 以外は 25P02
  │    ├─ ユーティリティ文（BEGIN/COMMIT/SET/SHOW/CREATE/DROP）は session で直接処理
  │    └─ それ以外: analyzer::analyze -> planner::plan -> executor::build -> next() ループ
  │         └─ RowDescription → DataRow* → CommandComplete
  └─ エラーが起きたら、残りの文は実行しない
```

### 4.1 Simple Query のトランザクション意味論（PostgreSQL と同じ）

- 明示的な BEGIN の外では、**1 つの Query メッセージ全体が 1 つの暗黙トランザクション**になる。途中でエラーが起きたら全体を巻き戻す。Query の途中に BEGIN があっても区切らず、**それより前の文も同じトランザクションに取り込まれる**（暗黙のブロックが明示的なブロックに変わる）。Query の途中の COMMIT/ROLLBACK はそこでトランザクションを終え、後続の文は新しい暗黙トランザクションで実行する。
- ブロック内（BEGIN の後）でエラーが起きたら Failed 状態にする。以降は ROLLBACK まで 25P02（`current transaction is aborted, commands ignored until end of transaction block`）。Failed 状態での COMMIT は ROLLBACK として扱い、タグは `ROLLBACK` を返す。
- ブロック外の COMMIT/ROLLBACK は警告（`WARNING 25P01 there is no transaction in progress`）を NoticeResponse で返し、タグはそのまま返す。ブロック内の BEGIN は警告（`25001 there is already a transaction in progress`）。

### 4.2 CommandComplete のタグ

`SELECT n`、`INSERT 0 n`、`CREATE TABLE`、`DROP TABLE`、`BEGIN`、`START TRANSACTION`、`COMMIT`（END も COMMIT）、`ROLLBACK`（ABORT も ROLLBACK）、`SET`、`RESET`、`SHOW`。

### 4.3 出力列の名前（PostgreSQL の FigureColname）

- 列参照 → 列名。関数呼び出し → 関数名。`CAST`/`::` → 内側の式に名前があればそれ、なければ型名（`SELECT 1::int4` → `int4`）。`CASE` → `case`。`COALESCE`/`NULLIF` → `coalesce`/`nullif`。それ以外 → `?column?`。
- `current_user`、`current_database()` などもそれぞれの名前。

## 5. モジュールごとの仕様

### 5.1 sql（lexer / parser / ast）

- 手書きの再帰下降。式は優先順位登山法（Pratt）。演算子の優先順位と結合性は PostgreSQL の gram.y に合わせる（`OR` < `AND` < `NOT` < `IS` < 比較 < `BETWEEN`/`IN`/`LIKE` < その他の演算子（`||` を含む） < `+ -` < `* / %` < `^` < 単項マイナス < `::`）。
- 識別子は引用符なしなら小文字に畳み込む。`"Quoted"` はそのまま。予約語は PostgreSQL の予約語一覧に従う（非予約語は列名として使える）。
- 字句: `--` と `/* */`（入れ子あり）のコメント、`'...'`（`''` でエスケープ）、`E'...'`、`$$...$$` は任意、数値リテラル（`1`、`1.5`、`.5`、`1e10`、`0x1F` は不要）、演算子記号、`;` による文の区切り。
- AST はすべてのノードに `Span` を持たせる。AST はカタログに依存しない純粋なデータとする。
- `fn parse(sql: &str) -> Result<Vec<Statement>>`。
- 構文エラーのメッセージは PostgreSQL と同じ形式（`syntax error at or near "xxx"`、末尾なら `syntax error at end of input`）。位置も同じにする。
- AST には M1 で実行しない構文（UPDATE、DELETE、JOIN、GROUP BY など）を入れてもよい。パースできたうえで、アナライザが `0A000` を返す形が望ましい。

### 5.2 analyzer

- 入力: `&Statement` と `&dyn CatalogReader`。出力: 型が確定した `BoundStatement`。
- `BoundExpr { kind: BoundExprKind, ty: SqlType, span: Span }`。列参照は `ColumnRef { index: usize }`（入力行の中の位置）に解決する。
- 型の解決は `research-pg-types.md` の疑似コードに従う。
  - 演算子: 完全一致 → unknown を相手の型とみなした一致 → 暗黙キャストで到達できる候補の絞り込み → 完全一致した引数の数 → preferred 型 → unknown 位置のカテゴリ推定 → 失敗したら 42883 か 42725。
  - 関数: 同様。
  - 共通型（CASE、COALESCE、VALUES の各列、IN のリスト）: `select_common_type` に従う。
  - 代入（INSERT の値 → 列の型）: 代入キャストを使う。そのあと typmod（`varchar(n)` の長さ）を別の段階で適用し、超過したら 22001。ただし明示キャスト `'abcdef'::varchar(3)` は黙って切り詰める。
  - unknown のリテラルは、文脈で型が決まるまで unknown のまま持ち、最後まで決まらなければ text にする。
- キャストの実装は「キャストの種類（関数・バイナリ・入出力経由）」を表で引く。条件分岐への直書きはしない。
- 名前解決: FROM 句の表（M1 は最大 1 つ）を `Scope` に積む。存在しない表は 42P01、列は 42703、曖昧な列は 42702。エラーには位置を付ける。
- `INSERT` の列リスト: 重複は 42701。値の個数が合わなければ 42601（`INSERT has more expressions than target columns` など）。省略された列は DEFAULT 式、なければ NULL。
- DEFAULT と CHECK の式は、カタログに保存された SQL テキストをパースし、表のスコープでアナライズしてから使う。CHECK 式の結果型は bool でなければならない（42804）。CHECK 式の中に列以外の参照があれば、PostgreSQL と同じエラーにする。
- ORDER BY の解決は PostgreSQL と同じにする: 整数リテラルは出力列の番号、単純な名前は先に出力列の別名を探し、なければ入力列として解決する。DISTINCT がある場合、ORDER BY の式は出力列に含まれていなければならない（42P10）。

### 5.3 planner と executor

- `PhysicalPlan`（不変の enum）: `Result { exprs }`（FROM なし）、`Values { rows }`、`SeqScan { table_oid, columns }`、`Filter { input, predicate }`、`Project { input, exprs }`、`Sort { input, keys }`、`Distinct { input }`、`Limit { input, limit, offset }`、`Insert { table_oid, input, column_map, defaults, checks, not_null }`。
- Executor のトレイト:

```rust
pub trait Executor {
    fn next(&mut self, ctx: &mut ExecCtx<'_>) -> Result<Option<Row>>;
}
pub type BoxedExecutor = Box<dyn Executor>;
pub struct ExecCtx<'a> {
    pub catalog: &'a dyn CatalogReader,
    pub storage: &'a dyn TableStore,
    pub txn: &'a mut Transaction,
    pub session: &'a SessionInfo,   // current_user、current_database などの値
}
pub fn build(plan: &PhysicalPlan) -> BoxedExecutor;
```

- `ctx` は executor の構造体に持たせず、`next` の引数で毎回渡す（executor にライフタイムを付けないため）。
- 式の評価: `fn eval(expr: &BoundExpr, row: &Row, ctx: &ExecCtx) -> Result<Datum>`。AND/OR は三値論理。strict な関数と演算子は、引数に NULL があれば呼ばずに NULL を返す。
- Sort: 既定は昇順で NULLS LAST、降順なら NULLS FIRST（PostgreSQL と同じ）。比較は `cmp_datum` を使う。文字列の比較はバイト順（C collation）とする。
- Insert: 行ごとに、列の並べ替え → DEFAULT の評価 → 代入キャストと typmod の適用 → NOT NULL の検査（23502、`null value in column "c" of relation "t" violates not-null constraint`、detail は `Failing row contains (...)`）→ CHECK の検査（23514、`new row for relation "t" violates check constraint "name"`、同じ detail）→ `storage.insert` → undo ログへの記録、の順に処理する。CHECK は結果が NULL なら通す。
- `INSERT ... SELECT` で同じテーブルを読む場合（`INSERT INTO t SELECT * FROM t`）、入力は文の開始時点の内容にする。M1 は `scan` が全件コピーを返すので自然にそうなる。

### 5.4 settings

- 設定項目の表: `name`、既定値、`reported`（変更時に ParameterStatus を送るか）、値の検証。
- M1 で持つもの: 第 1.3 節の ParameterStatus の各項目、`search_path`（既定 `"$user", public`）、`extra_float_digits`（既定 1）、`client_min_messages`、`statement_timeout`、`lock_timeout`、`idle_in_transaction_session_timeout`、`timezone`（`TimeZone` と同じ項目）、`datestyle`、`intervalstyle`、`application_name`、`bytea_output`、`standard_conforming_strings`（`on` 以外は拒否）、`client_encoding`（UTF8 以外は拒否）、`transaction_isolation`（SHOW のみ、`read committed`）、`server_version`、`server_version_num`（`160000`）、`max_connections`、`max_identifier_length`（63）。
- 名前は大文字小文字を区別しない。知らない名前の SET は `42704 unrecognized configuration parameter "x"`。ただし `.` を含む名前（独自パラメータ）は受け付ける（PostgreSQL と同じ）。
- `SHOW` の結果は、列名が設定名（小文字）で型 text の 1 行 1 列。`SHOW ALL` は `name`、`setting`、`description` の 3 列。
- `reported` な設定の値が変わったら、**Query の処理の最後（ReadyForQuery の直前）に、値が実際に変わった項目だけ** `sink.parameter_status` で送る（PostgreSQL 14 以降の ReportChangedGUCOptions と同じ。ROLLBACK で値が戻った場合も、最初の値と違えば送る）。
- M1 の `SET LOCAL` は、トランザクション終了時に元へ戻す（PostgreSQL と同じ）。トランザクションブロック外の `SET LOCAL` は警告（`25P01`）を出して無視する。

### 5.5 yuzhu-server

- 起動: `yuzhu-server [--config path] [--listen 127.0.0.1] [--port 5432] [--max-connections 100] [--log-level info]`。コマンドライン引数が設定ファイルより優先する。
- 待ち受けは `std::net::TcpListener`。接続ごとに `std::thread::spawn`。上限を超えたら、起動処理の後に `FATAL 53300 sorry, too many clients already` を返して閉じる。
- 起動処理: SSLRequest/GSSENCRequest に `N` → StartupMessage → `AuthenticationOk` → `initial_parameter_status` の各値 → `BackendKeyData`（プロセス ID は接続ごとの連番、秘密鍵は乱数）→ `ReadyForQuery('I')`。
- メッセージループ: `Q` → `session.execute_simple` → `ReadyForQuery(status)`。`X` → 閉じる。Extended Query のメッセージは第 1.3 節の通り。不明なメッセージは `FATAL 08P01` で閉じる。
- メッセージ長の上限（例: 1GB）を超えたら `FATAL 08P01`。
- 1 接続で panic が起きても、サーバ全体を落とさない（スレッドの境界で `catch_unwind` するか、スレッドの終了を検知してログに残す）。
- 書き込みは `BufWriter` でまとめ、ReadyForQuery の後に flush する。
- ログ: 起動、接続、切断、エラーを `tracing` で出す。

## 6. テスト

### 6.1 共通の SQL テスト（言語非依存）

- 配置: `tests/slt/m1/<機能>/*.slt`（例: `ddl/create_table.slt`、`select/order_by.slt`、`types/int_overflow.slt`、`txn/rollback.slt`、`session/set_show.slt`）。
- ランナー: **sqllogictest-bin 0.29.1**（`cargo install sqllogictest-bin --locked --version 0.29.1`）。`--locked` は必須（`research-slt.md` 参照）。
- 実行スクリプト: `tests/run.sh --target pg|yuzhu [--port N] [files...]`。`--engine postgres`（Simple Query のみ）を使う。
- 期待値は、本物の PostgreSQL 17（C ロケールで initdb したもの。`docker run -e POSTGRES_INITDB_ARGS='--locale=C --encoding=UTF8' postgres:17`）に流して検証する。**PostgreSQL で通らないテストは置かない。**
- エラーは SQLSTATE で照合する（`statement error (42P01)`）。メッセージの正規表現は補助として短い部分一致に留める。
- 各ファイルは自分で作ったテーブルを最後に DROP し、ファイル間で状態を共有しない（ランナーは接続を共有するので、名前の衝突も避ける）。
- 浮動小数点の出力、NULL（`NULL`）、空文字列（`(empty)`）、bool（`t`/`f`）の表記は PostgreSQL のテキスト出力そのまま。

### 6.2 Rust のテスト

- 各モジュールにユニットテストを置く（lexer、parser、型の入出力、演算、キャストと演算子の解決、executor の各ノード、settings、プロトコルのエンコード・デコード）。
- `yuzhu-server` には、実際にサーバをスレッドで起動し、`tokio-postgres` か `postgres` クレート（dev-dependency）の `simple_query` で接続する結合テストを置く。
- CI（`.github/workflows/ci.yml`）: 既存の fmt・clippy・test に加え、(1) postgres:17 のサービスコンテナに対して slt を流して期待値を検証するジョブと、(2) yuzhu-server をビルドして起動し、slt を流すジョブを追加する。
